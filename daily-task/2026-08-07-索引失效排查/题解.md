# MySQL 索引失效排查：加了索引为什么还是慢

> 原题：MySQL 中使用索引一定有效吗？如何排查索引效果？

## 一句话题目

给字段加了索引，查询就一定会变快吗？不一定 —— 有几种常见写法会让索引「白建了」。这篇讲清楚它们为什么失效，以及怎么用 `EXPLAIN` 一眼看出索引到底有没有生效。

## 为什么会有这个问题

**索引就是书后面的「拼音检索表」。**

一本几千页的字典，你要查「苹」字，不用一页页翻，翻到后面的拼音表找到 `ping` → 第 872 页，直接跳过去。这就是索引：它把字段的值**排好序**单独存了一份，所以能「跳着找」，而不是「挨着翻」。

MySQL 里这个排好序的结构叫 **B+ 树**（可以理解成图书馆的分级指引牌：先看大类 → 再看小类 → 最后到具体书架号，三步就到位，不用逛遍整个馆）。

但检索表能用的**唯一前提**是：你问的东西，跟它排序的方式对得上。

- 你问「拼音是 ping 的字」→ 检索表就是按拼音排的，一秒定位。
- 你问「所有笔画数是 8 的字」→ 检索表按拼音排，笔画数是乱的，只能一页页翻。

索引失效，本质上全是这一个原因：**你把索引赖以排序的「原始值」给弄没了**，B+ 树就不知道该往哪跳，只能退回「一行行翻」，也就是**全表扫描**。

下面四种写法，全是这一条的不同变体。

## 四种「索引白建了」的写法

### 1. 在索引字段上做函数运算

```sql
-- 坏
SELECT * FROM orders WHERE YEAR(create_time) = 2023;
-- 好
SELECT * FROM orders WHERE create_time >= '2023-01-01' AND create_time < '2024-01-01';
```

索引是按 `create_time` 的**原始时间值**排序的。你套一层 `YEAR()`，等于要求「先把每一行的时间算成年份，再比大小」—— 而索引里根本没存年份这一列，只能把 20 万行全捞出来挨个算。

改法很固定：**把函数从字段那一侧挪走**，改写成一个原始值的区间。

Demo 实测：扫描行数 200,000 → 39,968，耗时 12,057us → 4,400us。

### 2. 隐式类型转换（最坑，因为看不出来）

```sql
-- 坏：phone 字段是 varchar，条件却给了个裸数字
SELECT * FROM orders WHERE phone = 13800012345;
-- 好：加上引号
SELECT * FROM orders WHERE phone = '13800012345';
```

MySQL 的规矩是：**字符串和数字比较时，把字符串转成数字**。所以上面那句坏 SQL 实际上等价于：

```sql
WHERE CAST(phone AS SIGNED) = 13800012345
```

看出来了吗 —— 这又变回了「在字段上做函数」，只不过这次函数是 MySQL 偷偷帮你加的。

这个坑在业务代码里特别常见：Java 里手机号用 `Long` 存，拼 SQL 时就漏了引号，本地测试数据少看不出来，上线数据一多就炸。

Demo 实测：扫描行数 200,000 → 2，耗时 13,539us → 34us（差了近 400 倍）。

### 3. 联合索引不遵守「最左前缀」

假设建了联合索引 `idx_user_time (user_id, create_time)`。

**生活比喻**：这就像一本按「省 → 市 → 姓名」顺序排的电话簿。

| 你知道的条件 | 能不能用电话簿 |
|---|---|
| 省 = 浙江 | 能，翻到浙江那一段 |
| 省 = 浙江，市 = 杭州 | 能，而且范围更小 |
| **只知道市 = 杭州** | **不能**，杭州散落在浙江那一段里，但你不知道浙江在哪 |

所以：

```sql
-- 用不上索引（跳过了最左列 user_id）
SELECT * FROM orders WHERE create_time >= '2025-06-01';
-- 用得上（只给最左列也行）
SELECT * FROM orders WHERE user_id = 42;
-- 用得最满（两列都给）
SELECT * FROM orders WHERE user_id = 42 AND create_time >= '2025-06-01';
```

Demo 实测三种写法的扫描行数：200,000 / 800 / 6。

> 补充一个容易误会的点：`WHERE create_time = ? AND user_id = ?` 这种**顺序写反**是没问题的，MySQL 优化器会自动帮你调整条件顺序。真正致命的是**缺列**，不是**写反**。

### 4. LIKE 以 % 开头

```sql
SELECT * FROM orders WHERE phone LIKE '%2345';    -- 用不上索引
SELECT * FROM orders WHERE phone LIKE '13800012%'; -- 用得上
```

还是字典那个比喻：拼音表按**开头**排序。你说「找拼音以 ping 开头的字」，能定位；你说「找拼音以 ing 结尾的字」，只能一页页翻。

`'13800012%'` 之所以能走索引，是因为它等价于一个区间：`phone >= '13800012' AND phone < '13800013'` —— 索引里正好是连续的一段。

Demo 实测：扫描行数 200,000 → 2,000。

> 真需要「包含匹配」怎么办？别硬扛，上 Elasticsearch 这类专门做全文检索的东西。

## 怎么确认索引到底有没有生效：EXPLAIN

改完 SQL 别凭感觉，在 SQL 前面加个 `EXPLAIN` 跑一下，重点看三个字段：

| 字段 | 看什么 | 判断标准 |
|---|---|---|
| **type** | 用什么方式访问表 | `ALL` = 全表扫描（最差）；至少要到 `range`，能到 `ref` / `const` 更好 |
| **key** | 实际走了哪个索引 | 显示 `NULL` 就是**根本没用上**，赶紧查上面四条 |
| **Extra** | 额外做了什么 | `Using index` 最好；出现 `Using filesort` / `Using temporary` 说明有优化空间 |

`type` 从差到好的常见档位：`ALL` < `index` < `range` < `ref` < `const`。

**Extra 里两个词的大白话解释：**

- **`Using index`（覆盖索引）**：你要的列，索引里本来就存着，不用再回头去正文里翻。就像检索表上直接写了「苹：píng，水果」—— 你只想知道读音的话，看检索表就够了，不用翻到第 872 页。这是最省的情况。
  - 反过来，如果你还要 `city` 这种索引里没有的列，就得拿着主键 id 再去正文翻一次，这一步叫**回表**。Demo 实测：只多要一个 `city` 列，扫描行数就从 1,000 涨到 2,000（多出来的正是 1,000 次回表）。
- **`Using filesort`**：这个名字很有误导性，它**不是**「用文件排序」的意思，而是「索引帮不上排序的忙，得把数据捞出来另外排一遍」。比如索引是 `(user_id, create_time)`，你却 `ORDER BY city`，那 city 在索引里是乱的，只能额外排。

## 线上怎么把坏 SQL 捞出来

`EXPLAIN` 是「我怀疑这条慢，来验一下」。可线上几百条 SQL，你怀疑哪条？

**两步走：**

1. **开慢查询日志**（`slow_query_log`）—— 像饭馆门口挂个小本子，只记「上菜超过 1 秒」的那几道菜。阈值 `long_query_time` 按业务定，核心接口可以设到 100ms。
2. **用 `pt-query-digest` 分析这个日志** —— 它把本子里的记录按「SQL 指纹」归类。所谓指纹，就是把具体参数抹成问号：`WHERE user_id = 42` 和 `WHERE user_id = 99` 归为同一条 `WHERE user_id = ?`，然后统计每类的**调用次数 / 总耗时 / 平均耗时**。

**关键在于它是按「总耗时」而不是「单次耗时」排序的。** Demo 里模拟了一段线上流量：

```
calls    total(us)    avg      max      SQL
3        37825        12608    13269    SELECT * FROM orders WHERE YEAR(create_time) = ?
3        748          249      308      SELECT * FROM orders WHERE phone LIKE ?
```

坏写法只跑了 3 次，却吃掉了慢日志里绝大部分时间 —— 这就是该优先治的那条。反过来，一条单次 200ms 但一天只跑两回的 SQL，其实可以先放着。

## 一句提醒

**看到「加了索引但 EXPLAIN 显示 key=NULL」，先别急着怀疑人生 —— 有可能是优化器故意不用的。**

MySQL 走不走索引，是自己算了笔账才决定的，思路很朴素：

- 走索引：命中几行就要「跳着」读几次（还要回表），单次贵；
- 全表扫：从头到尾顺着读，单次便宜。

**表很小、或者命中比例很高**的时候，全表扫反而更划算。Demo 实测了三个场景：

| 场景 | 总行数 | 预计命中 | 优化器选择 |
|---|---|---|---|
| 大表 + 命中很少 | 200,000 | 20 | 走索引 |
| 大表 + 命中一半 | 200,000 | 100,000 | 全表扫描 |
| 小表 | 200 | 120 | 全表扫描 |

这种情况**一般不用管**，优化器是对的。真正要治的，是数据量明明很大、命中很少，`key` 却是 `NULL` 的那些 —— 那才是上面四条写法出了问题。

另外提一句：索引不是越多越好。每加一个索引，`INSERT` / `UPDATE` 就要多维护一棵 B+ 树，写多读少的表堆索引会拖慢写入。
