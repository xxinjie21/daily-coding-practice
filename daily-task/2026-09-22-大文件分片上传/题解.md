# 设计一个文件上传系统：大文件怎么传才不崩

## 一句话说清

用户在网页上点"上传"，文件要从他的电脑跑到你的服务器存起来。传个 10KB 的头像随便传都行，但要传一个 2GB 的视频，网络一抖就得从头再来一遍。这个系统要解决的就是四件事：**传得稳（断了能接着传）、传得快（不重复传）、存得住（换台服务器也能找到）、防得住（别让人传病毒脚本上来）。**

## 为什么会有这个问题

想象你要搬走一个两米高的大衣柜：

- **一趟拉整个柜子**：电梯塞不进去（网关一般会限制单次请求大小），路上磕一下整柜报废（网络中断 = 全部重传）。这就是"直接传整个大文件"的下场。
- **拆成木板分批搬**：每块板单独搬，电梯装得下；哪块掉了补哪块；到了地方再拼起来。这就是**分片上传**。

还有一个坑：**你的服务不止一台机器。** 今天用户的请求打到 A 机器，明天扩容了打到 B 机器。如果文件存在 A 机器的本地硬盘上，B 机器根本找不到这个文件。

所以文件不能存本地，要统一丢进**对象存储**（比如 MinIO、阿里云 OSS）。你可以把它理解成"全公司共用的云盘"——文件有一个统一的地址，哪台机器拿着地址都能取到。

## 先认识这几个角色

| 角色 | 它负责什么 | 生活比喻 |
| --- | --- | --- |
| 前端（浏览器） | 把大文件切成一片片（比如每片 5MB），一片一片传 | 把衣柜拆成木板 |
| 网关 Nginx | 拦在最前面：限制请求大小、挡掉明显恶意的请求 | 小区门卫 |
| 后端服务 | 收分片、记账（登记元信息）、通知合并 | 装修队长 |
| 对象存储 | 真正放文件的地方 | 公共仓库 |
| 数据库 | **只存"元信息"**：文件叫啥、多大、存在哪、指纹是多少 | 仓库的登记本 |
| 消息队列 | 上传完之后的脏活累活排队慢慢做（病毒扫描、转码、生成缩略图） | 待办清单 |

注意这里最关键的一句：**数据库里不存文件本身，只存"关于文件的信息"。** 就像登记本上不会画下整件家具，只写"3 号仓、A 区、大衣柜、2.1 米"。

## 完整流程（7 步走一遍）

### 第 1 步：前端切片，算出"指纹"

前端拿到文件后，按固定大小切成片（真实项目里常用 5MB 一片），同时算一遍整个文件的 **MD5**。

> **MD5 是什么？** 你可以理解成文件的"指纹"：不管文件多大，算出来都是一串固定长度的字符。文件内容只要改一个字节，指纹就完全不同。所以它能当文件的身份证用。

### 第 2 步：先问一句"这文件有人传过吗？"（秒传）

前端拿着指纹去问后端："这个 MD5 你有没有？"

- 有 → 后端直接告诉你"存好了，路径是 xxx"，**文件根本不用传**。这叫**秒传**（比如一份 500MB 的安装包，公司里第 100 个人传的时候，1 秒钟就"传完"了）。
- 没有 → 继续下一步。

### 第 3 步：创建上传任务，登记元信息

后端在数据库里写一条记录，状态是"上传中"：

| 字段 | 例子 | 说明 |
| --- | --- | --- |
| file_id | upload-1001 | 这次上传任务的编号 |
| file_name | 产品宣传片.mp4 | 原始文件名 |
| file_size | 2147483648 | 字节数 |
| total_chunks | 410 | 一共切了多少片 |
| md5 | 9f8e7d... | 整体指纹，用来校验和秒传 |
| storage_path | objects/9f8e7d....mp4 | 以后文件在对象存储里的地址 |
| status | 上传中 | 传完改成"已就绪" |

### 第 4 步：一片一片传

前端按顺序（或并发）把每一片发给后端，后端转手存进对象存储，并在**已上传分片列表**里记下"第 3 片收到了"。这个列表是断点续传的关键。

### 第 5 步：断点续传——网络断了怎么办

假设传到第 3 片，用户的地铁进隧道了，网断了。等他重新连上时，**前端不需要从头传**，而是先问后端一句：

> "我这个文件，已经收到哪几片了？"

后端查一下列表，回答："第 0、1、2 片收到了，还差第 3 到第 409 片。"

前端只补传缺的那几片。这就是**断点续传**：像看视频看到一半退出，下次打开接着看，而不是从第 1 集重新开始。

### 第 6 步：合并 + 校验

所有分片都到齐后，后端发一个"合并"的指令。这一步通常不用自己写拼接代码——**对象存储本身就支持**（阿里云 OSS 叫 multipart upload，所有分片传完发一个 complete 请求就自动合好了）。

合并完再做一次校验：把合并后文件的 MD5 和当初登记的 MD5 比一比。对不上就说明传输过程中文件坏了，标记为"校验失败"，让用户重传。这就像搬完家具之后对一遍清单，确认没有磕坏。

### 第 7 步：脏活累活丢给消息队列

文件存好了不代表事情完了：要扫病毒、要生成缩略图、视频还要转码。这些都很慢，如果都塞在"上传"这个请求里同步做完，用户得等到天荒地老。

所以上传成功后，后端只往消息队列（比如 Kafka）里丢一条消息："有个新文件，快去处理。" 下游的消费者慢慢做，**用户那边早就显示"上传成功"了**。

## 三个最容易考的点

| 考点 | 一句话回答 |
| --- | --- |
| 秒传怎么做？ | 拿整体 MD5 当索引去查库，命中就复用已有文件，不重复占存储 |
| 断点续传怎么做？ | 服务端维护"已收到哪些分片"的列表，前端上传前先查，只补缺失的 |
| 为什么不能存本地磁盘？ | 服务会扩容/重启，本地文件别的机器看不到；必须存对象存储 |

## 一句提醒

- **MD5 只当"指纹"用就好。** 它已经被证明能被人为构造出两个不同文件却指纹相同（碰撞），所以生产环境做安全校验更推荐 **SHA-256**；但用来做"秒传去重"的标识，MD5 依然够用且更快。
- **分片别切太小也别太大**：太小会导致请求次数暴涨（1GB 文件切 1KB 就是 100 万次请求），太大则重传代价高。5MB 左右是常见折中。
- **安全三件套**：文件类型走**白名单**（只允许 jpg/png/pdf/mp4 这类，直接拒绝 `.jsp`、`.exe`）、同一用户上传次数要**限流**、上传目录绝不能有执行权限。
- **临时分片要设过期清理**：有人传了一半就跑了，那些分片会一直占着存储空间。给上传任务加个超时（比如 24 小时未完成就清理）。
