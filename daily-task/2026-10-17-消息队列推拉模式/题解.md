# 消息队列设计成推消息还是拉消息？推拉模式的优缺点？

## 一句话题目

消息队列把消息给消费者，有两条路：**broker（消息队列服务端）主动送来**叫「推」，**消费者自己去取**叫「拉」。没有标准答案，就看你的业务图什么。

## 为什么会有这个问题

用生活比喻：推模式像**外卖送上门**——饭一做好骑手立刻送到你嘴边，新鲜、快，但不管你正忙得吃不过来，堆一桌子；拉模式像**自己去快递柜取**——你哪天有空、拿几件、拿多快都自己定，但要是你三天不去，快递就在柜子里躺三天。

技术上说：

| | 推模式（push） | 拉模式（pull） |
|---|---|---|
| 谁主动 | broker 主动发给消费者 | 消费者自己来取 |
| 实时性 | 好，消息一到就处理 | 取决于轮询间隔，可能慢 |
| 消费者压力 | 容易被压垮 | 按自己节奏来，从容 |
| 浪费 | 一般没有 | 没新消息时还在轮询 = 白打工 |
| 谁攒积压 | 消费者手里堆着 | broker 队列里排着 |
| 典型代表 | RabbitMQ `basicConsume` | RocketMQ 的 pull 模式 |

真实系统大多走**混合路线**：

- **Kafka** 表面是拉（消费者自己 `poll()`），但底层用**长轮询**模拟推送——消费者说「给我来一批，没有也等我一会儿」，等有消息立刻返回。所以既保留了拉的灵活，又有接近推的实时性，这叫「准实时」。
- **RabbitMQ** 是推，但给了 **QoS**（`basicQos`）这个闸门：规定「消费者手里最多留几条没处理完的」，剩下的留在 broker 排队。消费者处理不过来？broker 就不推了，**可控的推**。

所以核心其实是**流量控制**：push 不做限制容易雪崩，pull 轮询太频又浪费 broker 和网络。

## 怎么做（代码里验证了什么）

代码（`code/src/main/java/Demo.java`）用 RabbitMQ 真实 API 连本地 5673 端口的容器，灌 20 条消息，每条都带「生产时刻」以统计端到端延迟，分三个场景对比：

1. **场景A 推模式不限流**：`basicConsume` 之后 broker 一股脑把 20 条全推过来。消费到一半时快照，broker 队列已空——消息全糊在消费者脸上，消费者一旦处理慢甚至挂掉，这一大摞全压在它那里。
2. **场景B 推模式加 QoS=2**：`basicQos(2)` 之后快照，broker 队列里还剩十几条在排队，消费者手里同时只有 2 条没确认。实时性一样好，但积压留在 broker——谁有空谁接，进程重启也不丢（没确认的消息会重新入队）。
3. **场景C 拉模式 200ms 轮询**：`basicGet` 自己来取，没取到就等 200ms。平均延迟明显高于推模式（等待都花在「还没到下次轮询」），收满之后还有几次空转——没新消息时轮询纯属浪费。

选型结论也回到业务：**日志收集这种高吞吐用拉更稳**（消费者按自己能力消化），**订单状态通知这种强实时用可控的推 + 限流**。

## 一句提醒

「推还是拉」在面试里别背答案，抓住**流量控制和负载均衡**这个核心点：推要配 QoS，拉要调轮询间隔和批量大小，最终选型由业务的吞吐、实时性要求说了算。
