# 数据同步断点续传：搬一半崩了，怎么保证两边数据一样

## 一句话题目

把 A 库的数据往 B 库搬（这就叫**数据同步**），搬到一半程序挂了。重启之后，怎么做到既不漏数据、也不重复写？

## 二、为什么会有这个问题

想象你在帮朋友搬家，要把 10 万本书从旧屋搬到新屋。搬到第 3 万本的时候你手机没电了、人也累趴了。

第二天醒来，麻烦来了：

- **从头搬**：前 3 万本又搬一遍 → 新屋里出现两套重复的书（数据重复）。
- **凭感觉接着搬**：记不清搬到哪了，随便从第 4 万本开始 → 中间那 1 万本永远丢了（数据丢失）。

程序也一样。很多人第一反应是"失败了就重试呗"，但**无脑重试正是重复数据的来源**。真正要做的是两件事：

1. **记住我搬到哪儿了** —— 断点续传；
2. **就算重复搬了也不出错** —— 幂等。

> **幂等**：大白话就是"同一件事做一次和做十次，结果一样"。比如电梯按钮，你按一次和连按十次，电梯还是只来一趟。转账就不幂等——按十次真扣十次钱。

## 三、怎么做（四步）

### 第 1 步：先分清是哪种同步

不同场景解法不一样，别一套方案打天下：

| 场景 | 例子 | 特点 |
|---|---|---|
| 单表 / 全量迁移 | 老库整张表搬新库（DataX） | 数据量大、一次性 |
| 增量同步 | 只搬"新变化的那部分"（Canal、Flink CDC） | 持续跑、要盯住位点 |

> **CDC**（Change Data Capture，变更数据捕获）：不去扫全表，而是趴在数据库的日志上听"刚才谁改了哪条"，像门口的登记本，只记进出，不用每次清点全屋。

### 第 2 步：把进度写进"进度表"（状态追踪）

别把进度只放在内存里——程序一挂就没了。要写到外部存储（MySQL 表或 Redis 都行）：

```sql
CREATE TABLE sync_checkpoint (
  task_name       VARCHAR(64) PRIMARY KEY,  -- 任务名，比如 order_sync
  source_position BIGINT,                   -- 源库读到哪了（比如最后一条的主键 ID）
  target_offset   BIGINT,                   -- 目标库确认写了多少条
  status          VARCHAR(16),              -- RUNNING / FAILED / SUCCESS
  update_time     DATETIME
);
```

这就是搬家时贴在门上的便利贴："已搬到第 3 万本"。重启时先看便利贴：
- 上次是 `SUCCESS` → 不用重跑；
- 上次是 `RUNNING`/`FAILED` → 从 `source_position` **接着搬**，前面的一律跳过。

关键顺序（很容易写反）：**先写目标库，成功后再更新进度**。反过来的话，进度更新完程序崩了，那批数据就永远丢了。

### 第 3 步：目标端写入必须幂等 —— 用 upsert 不用 insert

即使断点记得准，网络抖动也可能让同一批数据发两遍。所以写入动作本身要"防重"。

做法是按**主键或业务唯一键**做 **upsert**（有则更新、无则插入）：

```sql
-- MySQL 写法：撞到唯一键就改，不报错也不重复
INSERT INTO orders (order_no, amount, status)
VALUES ('NO_1001', 99.00, 'PAID')
ON DUPLICATE KEY UPDATE amount = VALUES(amount), status = VALUES(status);

-- Oracle / PostgreSQL 用 MERGE INTO，思路一样
```

Flink 里对应的是 Upsert Kafka Sink / JDBC Upsert Sink，本质都是同一句话：**认唯一键，重复来了就覆盖，不新增一行**。

有了它，第 2 步的断点哪怕记偏了、重放了一小段，也顶多是把相同的值再写一遍，结果不变。

### 第 4 步：分批提交，别一次梭哈 10 万条

一次性把 10 万条塞进一个事务提交，失败就全部回滚，10 万条白干。

正确做法是**拆成每批 1000 条，每批独立事务**：

```
[1~1000]   commit ✅  → 更新进度=1000
[1001~2000] commit ✅ → 更新进度=2000
[2001~3000] 崩了 ❌   → 这批回滚，进度还是 2000
重启 → 从 2001 接着来，前 2000 条不再碰
```

最坏情况只丢一批，恢复成本极小。搬家比喻：一趟搬一箱，箱子搬到就在便利贴上加一笔，而不是等 10 万本全搬完才记账。

### 第 5 步（可选）：加一层对账校验

强一致要求高的场景（比如金融），同步完再跑个**校验任务**：分别算源库和目标库的 **checksum**（把一批数据算成一个"指纹"数字，两边指纹一样就说明内容一致，工具如 `pt-table-checksum`），发现对不上就自动补修。

## 四、一句提醒

**顺序千万别写反：先写目标库 → 再更新进度**。先更新进度再写数据，一旦中间崩了这批就静悄悄丢了，而且日志上还显示"成功"，是线上最难查的那类问题。另外，实际工程里**最终一致性**（允许短暂不一致、最后总会对上）就够用了，强一致代价太高，一般只在对账场景才上。
