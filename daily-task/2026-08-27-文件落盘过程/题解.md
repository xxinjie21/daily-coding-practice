# 24. Java 写入文件到磁盘会经历哪些过程？

## 一句话题目（大白话）
你调用 `write()` 写文件时，数据其实没直接进硬盘，中间过了好几道手。这题问的就是：从你写下一行代码，到数据真正躺在磁盘上，中间到底经历了什么？以及，怎么才能确保断电也不丢？

## 为什么会有这问题（先用个生活比喻）
把「写文件」想成你（Java 程序）要把一张纸条存进公司的**保险柜（磁盘）**：

- **你手边的草稿本** = 用户态缓冲区。你先在草稿本上写，还没交给任何人。
- **办公室前台** = 内核页缓存（Page Cache）。你把草稿本交过去，前台先收着，但还没送去档案室。
- **档案室管理员定时巡房** = 脏页回写线程（writeback）。他过一阵才把前台攒的纸条批量送进保险柜。
- **保险柜的「已收到」回执** = 磁盘控制器确认落盘。

所以你 `write()` 一下，纸条可能还停在你草稿本上、或在前台抽屉里，未必真进保险柜。要「断电也不丢」，得有人当场把纸条送进保险柜并拿回执——这就是 `force()`/`fsync()`。

## 怎么做（核心流程 + 调用链）
Java 写文件，数据从你的代码到磁盘，按顺序过这 5 关：

```
你的代码 write()
   │ ① 用户态缓冲（BufferedOutputStream 的 8KB 草稿本）
   ▼
flush() / 缓冲满 → write() 系统调用
   │ ② 内核页缓存 Page Cache（前台抽屉，此时 OS 已「看得到」文件大小）
   ▼
③ 脏页回写 writeback（后台线程把脏页刷向磁盘，受 vm.dirty_ratio 等参数控制）
   │
   ▼
④ 块设备层：VFS → 具体文件系统(ext4) → IO 调度器 → 磁盘控制器
   │
   ▼
⑤ 磁盘控制器真正写入非易失介质，返回确认信号 → 这步才算「落盘」
```

三档「保熟程度」对照表：

| 写法 | 数据停在哪 | 断电会丢吗 | 适合场景 |
|------|-----------|-----------|---------|
| `new FileOutputStream` 直接 write 少量、不 close | 用户态缓冲 / Page Cache | 会丢（没刷下去） | 不推荐 |
| 写完 `close()` / `flush()` | Page Cache（前台抽屉） | 大概率会丢（靠 OS 后台回写，没拿回执） | 普通日志、不重要的临时文件 |
| `FileChannel.write` + `channel.force(true)` | 真正刷到磁盘 + 强制刷元数据 | **不丢**（等价 `fsync()`） | 订单、账单、交易明细等关键数据 |

**关键 API**：`FileChannel.force(true)` 的 `true` 表示连文件元数据（大小、修改时间）一起刷；对应底层 `fsync()` 系统调用。光 `write()` 不 `force()`，数据只是到了 Page Cache，前面说的「脏页回写」是异步的，机器一断电就蒸发。

## 一句提醒（易错点）
- 别以为 `close()` 就等于「落盘」：`close()` 只保证把 Page Cache 里的数据交出去，至于 OS 什么时候真写进保险柜是它说了算。**关键数据必须 `force(true)` 或结束后主动 `fsync`**，否则「写成功了」只是假象。
- 反过来说，也**别对所有写入都强 `force()`**——每次都等回执很慢（随机写性能会掉一个数量级）。普通日志、能重算的缓存文件，交给 OS 后台回写就够了，把 `force()` 留给真正丢不起的数据。
