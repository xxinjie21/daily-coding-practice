# 朋友圈点赞功能设计：几亿人同时点赞，数据库怎么不被打垮

> 原题：朋友圈点赞功能如何实现，简单说说？

## 一句话说清题目

点赞要同时做到两件事：**点得快**（高并发下不卡）和**数得准**（同一个人不能点两次、点赞数不能算错）。题目问的就是这两件事怎么一起办到。

## 为什么这事难？

想象某明星官宣，一条动态瞬间涌进几十万次点赞。

- 如果每次点赞都直接 `UPDATE feed SET like_count = like_count + 1` 打到 MySQL，这条记录的行锁会把所有请求排成一队 —— 就像**奶茶店只开一个窗口，几百人挤在门口**，数据库当场被打垮。
- 如果为了快，把点赞数只放内存里，服务一重启数就没了；多台服务器各记各的，数还会对不上。

所以思路是：**别让数据库直接面对人潮，中间加个"缓冲区"，把脏活累活往后挪。** 这就是原题说的"用空间换时间"。

## 怎么做：四步

### 第 1 步：点赞记录用 Redis 的 Set 去重

Redis 的 Set（集合）就像**一张签到表**：签过一次名字就写上去了，再来签，`SADD` 会告诉你"他已经在表里"（返回 0），这次点赞直接不算数。

```java
// 键名由 likesKey(feedId) / countKey(feedId) 拼出，即 "likes:1001" / "like_count:1001"
long added = jedis.sadd(likesKey(feedId), String.valueOf(userId)); // 1=新点赞，0=已经点过
if (added == 0) {
    return;                                        // 重复点赞，忽略
}
jedis.incr(countKey(feedId));                      // 计数 +1
```

`SADD` 是**原子操作** —— 意思是一万个人同时点，Redis 也保证只有第一个人算成功，不会两个人都以为自己抢到了。

对应代码：`code/src/main/java/Demo.java` 的 `step1NormalLike()` 和 `likeOnce()`。

### 第 2 步：点赞数单独放一个计数器

查"这条动态有多少人赞"是刷首页时最频繁的操作。若每次都 `SELECT COUNT(*) FROM feed_like WHERE feed_id = ?`，几十万条记录每次都要扫一遍。

把计数放在 Redis 的 `like_count:动态ID` 上，读一次是 **O(1)**（不管多少人点赞，耗时都一样），数据库完全不参与。

### 第 3 步：热点动态，点赞事件先扔进消息队列

超热内容的点赞量太大，做法是：**点赞结果先写 Redis（用户立刻看到已点赞），再把"谁赞了哪条"丢进消息队列**，让消费者慢慢按批写库。

```
用户点赞 ──► Redis（去重 + 计数，立刻生效）
                │
                └──► MQ 队列 ──► 消费者攒够 50 条 ──► 一条 INSERT 批量写 MySQL
```

队列在这里干的事叫**削峰**：把"一瞬间 200 次写库"摊平成"4 次批量写库"。实测输出就是 `共 4 批（200 次写库被压成 4 批）`。

> 原题举例用的是 Kafka，角色完全一样（接事件 + 异步落库）。这里换成 RabbitMQ，因为本机已有可用镜像、能真跑起来验证。代码里是 `com.rabbitmq.client` 的真实 API：`basicPublish` 发消息、`basicGet` 拉消息、落库成功后才 `basicAck` 确认。

对应代码：`step2HotFeedByMq()` / `consumeAndSaveInBatch()` / `saveBatch()`。

### 第 4 步：唯一索引兜底 + 列表只展示前几个

- **唯一索引是最后一道闸门**：表上建 `UNIQUE KEY uk_feed_user (feed_id, user_id)`，就算 Redis 判重漏了、消息重复投递了，数据库也写不出第二条。代码用 `INSERT IGNORE`，重复的直接丢掉，不报错。
- **点赞列表别全量拉**：几十万人点赞，页面只显示"共 XX 人赞过"和前 3 个头像，真要看全部再翻页查库。

## 一张小对比表

| 要干的事 | 走哪里 | 为什么 |
|---|---|---|
| 判断"这人点过没" | Redis Set `SADD` | 原子、O(1)，扛得住瞬时高并发 |
| 查点赞数 | Redis 计数器 `GET` | O(1)，不碰数据库 |
| 存点赞记录 | MySQL + 唯一索引 | 要持久化，唯一索引保证不重复 |
| 热点点赞落库 | MQ + 批量 `INSERT` | 削峰，把 N 次写库压成几批 |
| 展示点赞列表 | Redis 取前几个 + MySQL 翻页 | 不把几十万人一次拉进内存 |

## 一句提醒

**别让"缓存里的计数"和"数据库里的记录"长期跑偏。** 点赞这种场景允许短暂误差，但要留一个对账任务定期用 `SELECT COUNT(*)` 校准缓存；如果是**钱**这类绝不能错的场景，就得先落库成功再改缓存，或者干脆不用缓存计数。另外给计数 key 设个过期时间兜底 —— 代码里用的是 `jedis.setex(countKey(feedId), 300, ...)`，5 分钟自然过期一次，防止一旦偏了就永远错下去。
