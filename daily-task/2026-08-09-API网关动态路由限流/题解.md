# API 网关设计：动态路由和限流怎么搞

## 一句话题目（大白话）

API 网关就是所有请求进门的"统一前台"，核心要解决两件事：**请求往哪转**（动态路由）、**别让后端被挤爆**（限流）。

## 为什么会有这问题

打个比方：一栋写字楼里有几十家公司（后端微服务），访客（请求）要是挨家敲门就乱套了。所以大堂得设个总台（网关）：访客先到总台，总台查一下"你要找的人在几楼几号"（路由），再放行。要是某家公司今天访客太多，总台还会发号限流，避免电梯挤爆（限流）。更关键的是——某公司搬楼层了，总台只要改一下登记表就行，不用拆楼重建（这叫**热更新**，不重启服务就能改规则）。

## 怎么做

### 1. 动态路由：把路由表从代码里搬出来

- 路由规则存到配置中心（Nacos / ZooKeeper，可以理解成"一个能实时同步的共享记事本"），网关启动时拉取一份到内存，同时**监听变更**：记事本一改，网关内存里的路由表立刻刷新。
- 例子：`/user/**` → `user-service:8080`。
- 好处：改路由不用重新发版，推一下配置就生效。Spring Cloud Gateway 里的 `RouteDefinitionWriter` 就是干这个的。

### 2. 限流：令牌桶算法

令牌桶像银行的"发号机"：

- 系统每秒往桶里放固定数量的号（令牌），桶满了就不再放。
- 请求来了先抢一个号，抢到才放行；没号了直接返回 `429 Too Many Requests`。
- 单机用 Guava 的 `RateLimiter`（单机版发号机）；分布式环境用 **Redis + Lua** 脚本，按 用户ID / IP 做 key，每台网关共享同一个计数，避免每台各自放号导致总量超标。

### 3. 热更新：不重启改规则

管理后台提供 OpenAPI 接口 → 改完配置推送到配置中心 → 网关监听到变更 → 内存里的路由表/限流规则 reload，全程不用重启。

### 请求经过网关的调用链

```
[请求] → 网关 → ①鉴权(JWT校验) → ②路由匹配(查路由表) → ③限流(令牌桶抢号)
      → ④转发到后端服务 → ⑤记录响应耗时/日志 → 返回结果
```

网关把鉴权、日志这些"脏活累活"扛下来，后端业务服务就能轻装上阵，只管业务逻辑。

### 核心能力一览

| 能力 | 作用 | 典型实现 |
| --- | --- | --- |
| 动态路由 | 决定请求转发到哪个服务 | Nacos/ZooKeeper + 内存路由表 |
| 限流 | 防突发流量打垮后端 | 令牌桶（Guava 单机 / Redis+Lua 分布式） |
| 鉴权 | 拦截非法请求 | JWT 校验 |
| 监控日志 | 记录耗时、异常 | 网关打点上报 |

## 一句线上提醒

网关是所有请求的**单点入口**，它自己必须高可用（多实例 + 负载均衡），否则网关一挂全站不可达；路由和限流规则**一定要支持热更新**，别等线上出事才发版改配置——那会儿你改不动。
