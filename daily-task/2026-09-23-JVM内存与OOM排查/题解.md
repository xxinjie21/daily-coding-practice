# 111. 怎么分析 JVM 当前的内存占用情况？OOM 后怎么分析？

**一句话**：JVM 的内存就像一间仓库，先看「总库存还剩多少」，再看「哪个货架堆满了」，最后在爆仓那一刻把现场拍下来（dump 文件）慢慢查。

## 一、为什么会有这个问题

Java 不用你手动 free 内存，垃圾回收器（GC，可以理解成「仓库的自动保洁」）会帮你收拾。

但保洁也有忙不过来的时候：

- **有人只堆不撒手**：比如一个 `static Map` 当缓存用，只往里放、从不清理，对象一直被引用着，GC 根本不敢收 —— 这叫**内存泄漏**（漏，不是少，是"该扔的没扔"）。
- **堆得比收得快**：仓库满了，再申请内存就报 `OutOfMemoryError`（简称 OOM，内存溢出，程序直接倒下）。

所以排查分成两件事：**没崩之前看趋势**，**崩了之后看现场**。

## 二、没崩之前：三步看内存

对应面试里最常问的三条命令：

| 工具 | 看什么 | 看出什么问题 |
| --- | --- | --- |
| `jstat -gc <pid>` | 年轻代 / 老年代 / 元空间的容量，以及 GC 次数和耗时 | 至少观察 30 秒：GC 是不是太频繁、老年代是不是只涨不跌 |
| `jmap -heap <pid>` | 堆的配置（初始堆、最大堆）和各区实际使用量 | **老年代使用率长期超过 70%，就要警惕了，可能快 OOM** |
| GC 日志 `-Xlog:gc*:file=gc.log` | 每次 GC 前后内存的变化 | 连续几次 Full GC 后内存还是下不来 → 基本就是泄漏了 |

> `pid` 就是进程号，用 `jps` 命令能列出来。`jstat` 里的 `YGC/FGC` 分别是「年轻代回收次数」和「Full GC 次数」。

这些命令背后的数据，其实 Java 程序自己就能读出来（`java.lang.management` 这套接口），`code/Demo.java` 就是这么干的：它把整体堆内存、各区明细、GC 次数与耗时打印出来，还顺便打印出你当前进程的 pid 和可以直接复制粘贴的 `jstat` / `jmap` 命令，方便你对着真机再练一遍。

> 小提示：默认堆很大（几个 GB）时，那个百分比涨得很慢，看着不过瘾。用 `java -Xmx64m Demo`（把堆限制成 64MB）跑一次，就能亲眼看到老年代使用率从 26.7% → 51.7% → 70.5%，然后在 70% 那条警戒线上触发预警。

## 三、崩了之后：OOM 怎么查

核心是**提前加两个启动参数**，让 JVM 在崩的那一刻自动把现场存下来：

```bash
-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/path/to/dumps
```

不加的话，OOM 发生时进程就没了，现场也跟着没了，事后只能干瞪眼（事后诸葛也搞不定）。

拿到 `heap.hprof`（堆快照文件）之后，用 **Eclipse MAT** 或 **JVisualVM** 打开，重点看 **Dominator Tree（支配树，一张按「谁占的内存最多」倒序排的榜单）**。它能直接告诉你：是哪个缓存 Map 扛了几百万个对象 —— 这就叫「定位主导集」。

手动抓一份也可以：

```bash
jmap -dump:format=b,file=heap.hprof <pid>
```

Demo 里用 `HotSpotDiagnosticMXBean.dumpHeap(...)` 做了同一件事，程序跑完会告诉你 dump 文件有多大、放在哪、用什么工具打开。

## 四、一句提醒

- 线上服务**第一件事就是把 `-XX:+HeapDumpOnOutOfMemoryError` 加上**，不然 OOM 现场就永久丢失了。
- dump 是「暂停式」的（会让业务线程停一下），生产上要掂量时机；堆越大，dump 文件越大，别往系统盘写。
- 顺带一提，题目原文还捎带问了 Redis 内存溢出，思路是同构的：先看现象（频繁写 swap 卡死 = 物理内存爆了；大量返回 `OOM command not allowed` = 撞到 `maxmemory` 上限），再用 `info memory` 对比 `used_memory` 和 `used_memory_rss`（差太多说明有内存碎片），最后用 `redis-cli --bigkeys` 揪出超大 key。
