# OAuth2.0 授权服务：Token 怎么发、怎么管才安全

## 一句话说清题目

要做一套「别的应用想借用我们系统的用户身份，但用户**不想把密码交出去**」的授权服务。
核心就两件事：**Token 怎么安全地发出去**、**发出去之后怎么管（能过期、能撤回、能续期）**。

## 为什么会有这个问题

把它想成**去酒店开房**：

- 直接给账号密码 = 把家里钥匙交给陌生人，他配一把你也不知道。
- OAuth2 的做法 = 你去前台登记（登录 + 点「同意授权」），前台给你一张**房卡**（access_token）。
  房卡只能开你这一间房，丢了能挂失作废，退房自动失效。
- 前台先给你一张**取货凭条**（authorization_code），你拿凭条去换房卡。
  换的时候还得出示**会员卡**（client_secret），证明你确实是登记过的客人。
- 房卡快到期了，你不想再排一次队登记 → 用**续住卡**（refresh_token）换一张新房卡。

题目里说的四种角色，对应过来就是：

| 术语 | 大白话 |
|---|---|
| 资源所有者 | 你（用户本人） |
| 客户端 | 想用你身份的那个 App |
| 授权服务 | 酒店前台（发卡的地方） |
| 资源服务 | 你的房间（真正存数据、要验卡的地方） |

## 怎么做

### 第一步：走「授权码模式」——最常用的那条路

```
浏览器            客户端服务器              授权服务                资源服务
  │  点「用 XX 登录」 │                        │                       │
  ├────────────────►│ 重定向到授权页           │                       │
  │                 ├──────────────────────►│                       │
  │  登录 + 点同意   │                        │                       │
  ├───────────────────────────────────────►│                       │
  │  ◄──── 重定向带回 authorization_code ────┤                       │
  ├────────────────►│ 拿 code + client_secret 去换 Token             │
  │                 ├──────────────────────►│                       │
  │                 │  ◄── access_token + refresh_token ──┤         │
  │                 │                        │                       │
  │                 ├────── 带上 access_token 访问资源 ────────────►│
```

**为什么非要绕这一圈？** 因为 access_token 全程**不经过浏览器**，只在两台服务器之间传递，
中间人抓包也抓不到。这是「授权码模式」比其他模式更安全的关键。

### 第二步：Token 怎么管（题目后半句的重点）

主流就两种做法，核心差别是「**能不能随时撤回**」：

| | JWT（自包含 Token） | 自管理随机 Token |
|---|---|---|
| 里面装什么 | 用户信息、过期时间都签在 Token 里 | 只是一串随机字符，信息存在 Redis/DB |
| 资源服务怎么验 | **自己验签名就行，不用查存储** | 每次请求都要查一次存储 |
| 能主动踢人下线吗 | 不能（除非另加黑名单） | 能，删掉记录即刻失效 |
| 性能 | 好，无状态，容易横向扩展 | 1k QPS 左右就可能成为瓶颈 |
| 适合场景 | 读多写少、能容忍「到期才失效」 | 需要强管控（登出、封号、踢下线） |

**JWT 的软肋怎么补？** 两条路，可以一起用：

1. **短期 Token + 频繁刷新**：access_token 只给 15 分钟，过期就拿 refresh_token 换新的。
2. **黑名单**：把要撤回的 Token 编号（jti，就是每张房卡上的卡号）塞进 Redis，
   过期时间设成它**剩余的有效期**，到点自动清理，不占内存。

### 第三步：别忘了几件「小事」

- **client_secret 必须保密**：只在服务端之间传，绝不能写进前端代码、更不能打进日志。
- **全程 HTTPS**：不然 Token 等于明文裸奔，前面做得再规范也白搭。
- **换 code 的接口要限流**：防止有人暴力猜 client_secret。
- **refresh_token 要轮换**：用一次就作废、换发新的，这样万一被偷也只能用一次。
- 生产上骨架可以用 **Spring Authorization Server** 搭，但 client 管理、加密存储、
  限流这些细节都得自己补。

## 一句提醒

**access_token 的生命周期越短越安全，但用户体感越差 —— 所以「短 access_token + 长 refresh_token」是标准答案。**

新手最容易踩的坑是：**JWT 一旦签出去，在过期之前它就是「合法」的。**
如果你需要「用户点了登出就立刻失效」，就一定要配黑名单，别指望 JWT 自己会失效。
