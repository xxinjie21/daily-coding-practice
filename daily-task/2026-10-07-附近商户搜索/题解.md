# 附近商户搜索：100 万商户里，怎么秒级找出离我最近的 5 家

## 一句话说清题目

用户打开 App 点「附近的美食」，你手上有 100 万家商户的经纬度，要在**几十毫秒内**告诉他「最近的 5 家是谁」。

## 为什么会有这个问题

想象你在一个超大型图书馆里找一本书。笨办法是：从第一排书架走到最后一排，把每本书都拿起来看一眼是不是我要的——**书越多越慢，而且没有上限**。

代码里那个笨办法就是：

```java
for (Merchant m : 全部100万家商户) {
    算出它离我多远;   // 每算一次都要做三角函数，很贵
}
再排序取前 5 名;
```

100 万次三角函数 + 一次全排序，再加上「把 100 万行数据从数据库/Redis 搬到应用内存」的传输开销，单次请求轻松几百毫秒。更麻烦的是：**用户每滑动一下地图，就得重算一遍**，服务直接被打垮。

关键洞察是：**我们根本不需要知道每家店离多远，只需要知道最近的那 5 家**。那就没必要「把书全翻一遍」——先想办法把范围缩到一个小角落，再在那个角落里精挑细选。

## 怎么做：粗筛 + 精算，两步走

### 第一步：粗筛——把二维的经纬度压成一维字符串

`geohash` 是一种编码方式：它把「经度 + 纬度」这对二维坐标，压成**一串字符**（比如 `wx4fbxxb9j0`）。

妙处在于：**两个地方离得越近，它们的 geohash 前缀就越像**。

```
附近 m235907 -> wx4fbxxb9j0
附近 m118911 -> wx4fbxxeuu0
附近 m94776  -> wx4fbz822r0
很远的 m266208 -> wx4cv71mvv0   ← 前缀一看就不一样
```

就像图书馆的索书号：`TP311.5/123` 和 `TP311.5/456` 一看就在同一排书架上，而 `I247.5/789` 在完全不同的区域。

有了这个特性，系统就能**只翻「前缀相同」的那一小片格子**，一次砍掉 90% 以上的数据——这就是「粗筛」。上面实测的 5 家附近商户，geohash 公共前缀都是 `wx4fb`，远处那家则是 `wx4cv`。

### 第二步：精算——在小范围里算真实球面距离

粗筛出来的是「大概在附近」，可能还带着十几个商户。这时才用**球面距离公式（Haversine）**精确算一遍真实距离，排序取前 5。

> 为什么要专门用球面距离？因为地球是圆的。拿平面直角坐标去算经纬度，在赤道附近勉强能用，越往高纬度误差越大——北京和广州的「1 度经度」实际长度差了快一半。

### 实际写代码：一条命令搞定

真实生产里不用自己实现 geohash 分块，**Redis 的 GEO 结构原生支持这套逻辑**，一条 `GEOSEARCH` 就把「粗筛 + 精算 + 排序 + 取前 5」全做完了：

```java
GeoSearchParam param = GeoSearchParam.geoSearchParam()
        .fromLonLat(116.40, 39.90)      // 我的位置
        .byRadius(5, GeoUnit.KM)        // 半径 5 公里内
        .withDist()                     // 顺带把距离一起返回
        .asc()                          // 由近到远
        .count(5);                      // 只要前 5 家
jedis.geosearch("merchants", param);
```

写入也一样简单，把商户经纬度灌进去即可（底层是一个有序集合）：

```java
jedis.geoadd("merchants", Map.of("m1", new GeoCoordinate(116.41, 39.91)));
```

### 两种做法实测对比（30 万条商户，完整代码见 `code/src/main/java/Demo.java`）

| | 基线：全量遍历 | 优化：Redis GEOSEARCH |
|---|---|---|
| 取回全部商户编号 | 156 ms | — |
| 计算 + 排序 | 42 ms | 全部在 Redis 内部完成 |
| 网络往返 + 返回结果 | — | 24 ms（只回 5 行） |
| **合计** | **198 ms** | **24 ms** |
| 数据量翻倍时 | 耗时翻倍（O(N)） | 基本不变（只翻附近格子） |

两边返回的 Top 5 完全一致（`m235907 / m118911 / m94776 / m8887 / m147348`），说明优化没有牺牲准确性。

> 数据量再往上、或者需要更复杂的空间分析（比如「这个多边形区域里有哪些店」），可以换 **PostGIS** 或 **Elasticsearch**，它们的空间查询能力更完整。但「先粗筛、再精算」这个思路是一样的。

## 一句提醒

**别把「粗筛」当成「精算」。** geohash 前缀相同只代表「大致在附近」，不代表精确距离——所以必须保留最后那一步 Haversine 精算。

另一个高频坑：**geohash 精度要选对**。字符位数越多格子越小，但太小会导致「明明很近却因为跨了格子边界搜不到」（比如两个人只隔一条街，却分属相邻两个格子）。工程上的通用解法是**搜索时多取一圈相邻格子**（Redis 内部已经帮你做了这件事），或者干脆用 `BYRADIUS` 按半径搜而不是按格子搜。
