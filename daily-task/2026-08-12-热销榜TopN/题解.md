# 热销榜 Top 50：怎么实时知道店里卖得最好的 50 个商品

> 原题：商家想要知道自己店铺卖的最好的 top 50 商品，如何实现这个功能？（来源：source-doc 后端场景面试题 16 / 系统设计题 20）

---

## 一句话题目

店里有几万个商品，每天成千上万笔订单。商家打开后台，想立刻看到「今天卖得最好的 50 个商品是哪些、各卖了多少件」。这个榜单怎么做，才能又准又快？

---

## 为什么会有这问题

先想个小卖部的场景。

老板想知道这个月哪些货最好卖，有两种办法：

- **办法 A**：把这个月所有小票翻出来，一张张数，数完再排序。小票越多越慢，而且每次问都要重新数一遍。
- **办法 B**：墙上贴一张红榜，每卖出一件就在那个商品后面画一道。想看排名？抬头看榜单最上面几行就行。

办法 A 就是 SQL 的 `select * from orders group by item_id order by count desc limit 50`——数据量小的时候没问题，数据量一大就要**扫全表 + 全量排序**，几秒钟才出结果，商家点一下后台就转圈。更要命的是，这个页面通常还是「实时刷新」的，每分钟都有人点。

办法 B 就是我们要做的：**边卖边记，把排序这件事分摊到每一次成交上**，而不是等到查询时才临时算。

---

## 怎么做

### 核心结构：Redis 的 Sorted Set

`Sorted Set`（有序集合，简称 ZSET）大白话就是：**一张自动排好序的榜单**。里面每一行是「成员 + 分数」，你往里塞东西，它自己知道该放在第几名。

放到我们这个场景里：

- 成员（member）= 商品 ID，比如 `item_10086`
- 分数（score）= 销量，比如 `328`

### 写：每卖一单，加一分

```java
// ZINCRBY：给某个成员的分数加上 N（这里 N=1，卖出一件）
redisTemplate.opsForZSet().incrementScore("sales_rank", "item_10086", 1);
```

一条命令搞定。不用先查再改，Redis 单线程执行，天然不会出现「两个人同时卖出，结果只加了 1」的问题。

### 读：直接取前 50 名

```java
// ZREVRANGE：从分数最高的开始，取第 0 名到第 49 名
Set<String> top50 = redisTemplate.opsForZSet().reverseRange("sales_rank", 0, 49);

// 想连销量一起拿到，用带 Score 的版本
Set<ZSetOperations.TypedTuple<String>> withScore =
        redisTemplate.opsForZSet().reverseRangeWithScores("sales_rank", 0, 49);
```

### 为什么它快

ZSET 底层是 **跳表 + 哈希表** 两个结构配合：

- **哈希表**：像书的索引页，给商品 ID 就能瞬间找到它现在多少分（O(1)）。
- **跳表**：可以理解成地铁的「快慢车轨道」——底层是每站都停的慢车，上面几层是只停大站的快车。找位置时先坐快车跳着找，快到了再换慢车，所以是 O(log N)，不是从头挨个数。

对比一下（Demo 里有实测数字）：

| 做法 | 查 Top 50 要碰多少数据 | 10 万商品实测（Demo 实验 2） |
|---|---|---|
| 全量取出来再排序 | 10 万条全碰一遍 | 约 31000 us，且随商品数量线性变慢 |
| ZSET 直接 reverseRange | 只碰 50 条 | 约 100 us，几乎不受总量影响 |

差距的本质不是「Redis 比 Java 快」，而是**排序的活儿已经在每次成交时提前干完了**——每次 `ZINCRBY` 多花约 2 微秒，换来查询时几乎白嫖。

## 三个必须注意的地方

### 1. 别把所有商品塞一个 key 里 —— 按类目分桶

一个 key 装十几万个成员，就成了所谓的**大 key**（一个键里塞了太多数据）。Redis 处理命令是单线程的，一旦有人对这个大 key 执行了耗时操作（比如手滑来了个 `ZRANGE key 0 -1` 取全量），**这段时间所有其他请求全在门口排队**。

做法是按类目拆开：

```
sales_rank:electronics    ← 数码
sales_rank:clothing       ← 服饰
sales_rank:food           ← 食品
```

读写分散到不同 key，单个 key 也小了。要全店总榜？下面第 2 点的合并方法同样适用。

### 2. 想看「今日 Top 50」—— key 上带日期

```
sales_rank:20260812    ← 今天的
sales_rank:20260811    ← 昨天的
```

每天一个新 key，天然隔离。要算「近 7 天热销榜」，用 `ZUNIONSTORE` 把 7 张榜叠加成一张：

```
ZUNIONSTORE sales_rank:week7 7 sales_rank:20260806 ... sales_rank:20260812
```

`ZUNIONSTORE` 大白话就是「把几张榜单摞在一起，同一个商品的分数相加，生成一张新榜」。还能给每天设权重——比如今天算 1.0 分、三天前算 0.5 分，做出「越近越热」的效果。

### 3. 凌晨归档，别让 key 无限堆积

每天一个 key，一年就是 365 个。定时任务在凌晨把昨天的榜单落到 MySQL 存档，然后给 Redis 里的 key 设个过期时间（比如保留 30 天），让它自己消失。

```java
// 落库存档后，给昨天的 key 加个 30 天保质期
redisTemplate.expire("sales_rank:20260811", Duration.ofDays(30));
```

---

## 一句提醒

**退款、取消订单一定要把分数减回去**（`ZINCRBY -1`），否则榜单只涨不跌，越跑越虚。减完如果分数 ≤ 0，顺手 `ZREM` 把它踢出榜单，免得攒一堆 0 分僵尸成员白占内存。

另外记住一句：**Redis 是榜单，MySQL 才是账本。** Redis 可能重启丢数据、可能因为某次网络抖动漏加一分——榜单少算一两件没人看得出来，但如果你拿它当销量结算依据就出大事了。稳妥做法是每天凌晨用数据库的真实订单数据把榜单**重建一遍**，让它和账本对齐。
