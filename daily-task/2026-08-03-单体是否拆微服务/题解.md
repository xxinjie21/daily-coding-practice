# 单体项目 QPS 到 1 万，要不要拆微服务？

> 原题：现在手头上有一个单体项目，系统的整体 QPS 到了 1 万了，要微服务化拆分吗？
> （QPS = Queries Per Second，每秒请求数。1 万 QPS 就是"每秒有 1 万个人来敲你家门"。）

## 一句话回答

**不一定要拆。QPS 高是"性能问题"，先用缓存、异步、读写分离解决；只有当"团队协作打架、发版越来越慢"这种架构腐化出现时，才值得拆微服务。**

---

## 一、先讲个饭馆的故事

你开了一家很火的饭馆（单体项目 = 一家店，前台、后厨、收银、仓库全在一个屋里）。

某天客人暴增，每秒进来 1 万个人（QPS 1 万）。这时候有两个念头：

- 念头 A：**把店拆成十家分店**（微服务化：订单店、用户店、库存店……各开各的门面）。
- 念头 B：**先看看到底堵在哪**——是不是每份菜都现杀现炒（每次都查数据库）？能不能提前备好半成品（缓存）？收银台是不是只有一个（数据库单点）？

绝大多数情况，**念头 B 便宜得多、见效快得多**。

> 现实里很多公司几十万 QPS，早期就是靠"单体 + CDN + 缓存 + 异步化"扛了好几年。
> - **CDN**：把图片、JS 这类不变的东西提前放到离用户最近的机房，用户不用大老远跑到你店里拿。
> - **缓存**：查过一次的结果先记在小本本（Redis/本地内存）上，下次直接念答案，不用再翻数据库大账本。
> - **异步化**：下单成功就先告诉客人"收到了"，发短信、加积分这些慢活儿丢到队列里慢慢做。

## 二、关键认知：拆微服务不是为了"扛流量"

这是最容易搞反的一点：

| | 想解决什么 | 该用什么 |
|---|---|---|
| **性能问题**（慢、扛不住） | 每秒请求太多、接口耗时长 | 缓存 / 异步 / 读写分离 / 加机器（水平扩容） |
| **协作问题**（乱、发版慢） | 改一个功能要十几个人联调、一天发不了一次版 | 微服务拆分（按业务域解耦） |

**判断口诀**：
- 你痛的是**机器**（CPU 打满、数据库慢查询）→ 优化，别拆。
- 你痛的是**人**（代码互相踩、发布排队、谁都不敢动那个 5000 行的类）→ 可以考虑拆。

顺带说一句：单体项目**照样能水平扩容**——同一份代码部署 10 台机器、前面挂个负载均衡（把请求平摊给多台机器的"大堂经理"）就行。**扛流量靠加机器，不靠拆服务**。

## 三、盲目拆分的代价（拆之前必须想清楚）

原来在一个进程里，A 调 B 就是一句 `b.doSomething()`，纳秒级，不会失败。
拆开之后，A 调 B 变成"跨网络打电话"：要序列化、要走网线、可能超时、可能对方没开机。

一次下单如果串起 5 个服务：

```
网关 → 订单服务 → 用户服务 → 库存服务 → 优惠券服务 → 支付服务
```

- **耗时叠加**：每跳哪怕只加 3ms，5 跳就多 15ms，还没算重试。
- **失败率放大**：每个服务可用性 99.9%，串 5 个 = 0.999^5 ≈ **99.5%**，故障率直接翻 5 倍。
- **配套设施必须先上**（这些本身就要人维护）：
  - **链路追踪**（SkyWalking）：给每个请求发一张"通行证编号"，出问题能顺着编号看它在哪一站卡住了。
  - **配置中心**（Nacos）：十个服务的配置总不能改十遍，统一放一个地方。
  - **服务治理 / 熔断限流**（Sentinel）：一个服务挂了，别把上游一起拖死。
  - **分布式事务**：原来一个 `@Transactional` 就能一起回滚，现在跨服务了，得自己写补偿逻辑。

一句话：**拆微服务不是免费的，你是拿"运维复杂度"换"团队解耦"**。人手不够的时候，这笔买卖很亏。

## 四、真要拆，先做"逻辑拆分"

别一上来就物理拆（拆成独立进程独立库）。推荐**两步走**：

**第 1 步：模块化单体（还在一个进程里，但按业务域分包）**

```
com.shop
 ├── order/     订单域   （只允许调 user、inventory）
 ├── user/      用户域   （不允许反过来调 order！）
 └── inventory/ 库存域
```

在编译期/架构测试里管住依赖方向：**谁能调谁，写死成规则，违反就报错**。
好处是——依赖关系提前暴露干净了，将来物理拆的时候，把包搬出去改成 RPC 调用就行，几乎不用重构业务逻辑。

> 生活比喻：先在一间大屋里用**隔断墙**分出订单区、用户区，走门要刷卡；等业务真的证明"需要各自搬家"，再把隔断变成真正的独立房子。隔断都没立就直接搬家，只会搬得一团乱。

**第 2 步：等边界稳定、团队真的被协作拖累了，再物理拆。**

## 五、特殊情况：1 万 QPS 集中在一个热点上

如果这 1 万 QPS 全砸在同一件商品（秒杀），那更该做的是：

- **本地缓存**（Caffeine）：把这一个热点数据存到应用自己的内存里，连 Redis 都不用走。
- **分布式锁 / 库存预扣**：保证不超卖。
- **热点探测**：自动发现"某个 key 突然特别火"，把它推到本地缓存。

这种场景**拆微服务一点忙都帮不上**，反而多了几跳网络。

---

## 六、一句提醒

> **别用"我们要上微服务"来解决"我们不会做缓存"。**

拆分前先问三句：
1. 瓶颈到底在哪？（有没有压测、有没有慢查询日志？）
2. 现在几个人开发、多久发一次版、发版是不是天天冲突？
3. 拆完谁来维护注册中心、链路追踪、分布式事务这一套？

三个问题答不上来，就先老老实实优化单体。
