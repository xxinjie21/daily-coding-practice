# 设计一个线程池：任务来了是先排队，还是先加人

## 一句话说清题目

让你自己设计一个线程池：任务不断提交进来，**什么时候用现成的线程、什么时候排队、什么时候再加线程、什么时候干脆拒绝**——把这几件事的规矩定清楚，就是一个线程池。

## 为什么会有这个问题

把它想成一家**饭店后厨**：

- 客人点单（任务提交）越来越快，你不可能每来一单就新招一个厨师——招人是有成本的，人招太多反而乱。
- 所以先定几个**正式工**（核心线程），他们一直在岗，来单就做。
- 单子多到正式工忙不过来，就先**摆在出单口排队**（阻塞队列），而不是立刻招人。
- 排队口也堆满了（说明真的爆单了），才临时招几个**临时工**顶上（非核心线程）。
- 连临时工都招满、队也排满了，那就只能**拒单**（拒绝策略）。

为什么不让排队口无限长？因为**队排得越长，客人等得越久**，而且单子全堆在内存里，迟早把内存撑爆。所以「有界队列 + 拒绝策略」才是负责任的做法。

## 怎么做

### 一、任务提交进来，按四步走

这是整个线程池的骨架，代码就长这样（`code/src/main/java/Demo.java` 里的 `MiniThreadPool.execute`）：

```java
void execute(Runnable task) {
    // 第 1 步：正式工还没坐满，直接派一个正式工接活
    if (threadCount.get() < coreSize) { addWorker(task, "正式工"); return; }
    // 第 2 步：正式工都忙，先看排队区还有没有位置
    if (queue.offer(task)) return;
    // 第 3 步：排队区也满了，才临时招人顶上
    if (threadCount.get() < maxSize) { addWorker(task, "临时工"); return; }
    // 第 4 步：人数到上限、队伍也满，只能拒绝
    throw new RejectedExecutionException("线程池已满");
}
```

注意第 2 步和第 3 步的**顺序**：是「先排队，排不下了才加线程」，不是「先加线程，加满了才排队」。很多人第一反应会写反。

实跑时 8 个任务进一个「核心 2 / 最大 4 / 队列 2」的池子，分流结果一眼可见：

```
任务 1、2 -> 两个正式工
任务 3、4 -> 进队列排队
任务 5、6 -> 临时招两个临时工顶上
任务 7、8 -> 被拒绝
```

换成 JDK 原生的 `ThreadPoolExecutor`，参数配成一模一样（`2, 4, 60s, new ArrayBlockingQueue<>(2)`），结果同样是**接住 6 个、拒绝 2 个**——说明手写版和真实版的行为是一致的。

### 二、几个关键数字怎么定

| 参数 | 大白话 | 定小了会怎样 | 定大了会怎样 |
|---|---|---|---|
| `corePoolSize` | 正式工数量，常驻不走的 | 平时吞吐不够 | 闲时白占内存和线程 |
| `maximumPoolSize` | 正式工 + 临时工的上限 | 高峰期顶不住 | 突发流量把机器压垮 |
| 队列容量 | 出单口能摆多少单 | 稍微一忙就拒单 | 排队久、堆内存风险 |
| `keepAlive` | 临时工闲多久下班 | 频繁招人裁人 | 闲人常驻 |

线上经验：**队列一定要设容量上限**，再结合业务的 TP99（99% 的请求多久返回）和峰值流量去调，而不是拍脑袋。

### 三、拒绝了怎么办——四种拒绝策略

队列满了、线程也满了，新任务总得有个交代，JDK 直接给了四种现成的（`code/src/main/java/Demo.java` 的 `step3RejectPolicies`，同一个池子连投 3 个任务，实测结果如下）：

| 策略 | 大白话 | 实测表现 |
|---|---|---|
| `AbortPolicy`（默认） | 直接报错，让调用方知道 | 任务 3 抛 `RejectedExecutionException` |
| `DiscardPolicy` | 悄悄丢掉，不吭声 | 任务 3 无声消失 |
| `CallerRunsPolicy` | 谁提交谁自己跑 | 任务 3 由 `Demo.main()` 线程跑掉 |
| `DiscardOldestPolicy` | 丢掉队头最老的那单，腾位置给新的 | 任务 2 被丢，任务 3 顶进去 |

`CallerRunsPolicy` 有个副作用要注意：提交任务的线程会被拖住去干活，等于给上游**自动降速**——有时候这正是你想要的（防止上游继续猛灌），有时候会把上游接口卡死。

### 四、为什么线上别用 `Executors.newFixedThreadPool`

一行代码就能建池子，看着很爽，但坑在队列上：

```java
ExecutorService fixed = Executors.newFixedThreadPool(1);
ThreadPoolExecutor pool = (ThreadPoolExecutor) fixed;
System.out.println(pool.getQueue().getClass().getSimpleName());     // LinkedBlockingQueue
System.out.println(pool.getQueue().remainingCapacity());            // 2147483647
```

`newFixedThreadPool` 用的是 `LinkedBlockingQueue`，**剩余容量是 21 亿**，等于没上限。任务一旦堆积，全塞进内存，堆撑爆就是 OOM。`newCachedThreadPool` 同理，线程数上限是 `Integer.MAX_VALUE`，线程能无限开。

所以线上规范是：**自己 `new ThreadPoolExecutor(...)`，队列用有界的 `ArrayBlockingQueue`，拒绝策略明确写出来**。

## 一句提醒

线程池的参数没有「万能公式」，它是**跟着业务量走的**：先保证队列有界、拒绝策略明确（别让任务无声消失），再按监控里的活跃线程数、队列积压量、拒绝次数去微调。看到「拒绝次数突然上涨」或「队列一直满」，就该调参或扩容了。
