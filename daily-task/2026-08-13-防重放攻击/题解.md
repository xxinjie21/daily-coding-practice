# 接口防重放：怎么拦住「把同一个请求包反复发」的攻击

> 原题：网关层如何防止接口重放攻击？如果攻击者抓取了请求包进行重放，你如何识别和拦截？（来源：source-doc 后端场景面试题 84）

## 一句话题目（大白话）

攻击者把你发出去的合法请求「录下来」，然后一模一样地反复重发（比如把一笔支付提交十遍）。你怎么在网关层认出「这是同一张票刷了第二次」，直接拦掉？

## 为什么会有这问题（生活比喻）

想象你拿一张演唱会二维码门票去检票。正常流程是：扫码 → 票核销 → 进场。重放攻击就像有人用手机拍下你刷码的瞬间，把那一帧画面无限复制，每次都拿去给检票员看。检票员只看「码对不对」，自然每次都放行——你的票被白嫖了无数次。

接口也是一样：支付请求本身就是「合法的」，攻击者不需要破解密码，只要把抓到的包原样重发，服务器就会当成新请求处理。所以必须在「进门之前」（网关层）加一道能识别「这票刚才刷过了」的关卡。

## 怎么做（核心思路）

网关层给每个请求加两道防伪标记，再配一个「已用记录本」：

**1) 时间戳 timestamp**
客户端发请求时带上「我现在的时刻」。网关校验 `|服务器时间 − 请求时间|` 是否在一个小窗口内（比如 ±5 分钟）。偏差太大说明包要么是老了重放、要么被改过，直接扔。
> 时间戳好比门票上的「使用日期」，过期的票再漂亮也不认。

**2) Nonce（一次性随机串）**
每个请求再带一个足够随机、几乎不重复的字符串（像 UUID）。它是「这一张票的唯一编号」。

**3) Redis 去重（关键一步）**
网关收到请求，用 Redis 的 **SETNX**（set if not exist，不存在才写）把 `nonce:xxxx` 写进 Redis，并设过期时间（比如 6 分钟，略大于时间窗口）。
- 第一次来：Redis 里没有 → 写入成功 → 放行，进业务系统。
- 重放来（同一个 nonce）：Redis 里已经有了 → 写入失败 → 判定为重放 → 拦截。
- 这一步是**原子的**：哪怕两个相同请求同一毫秒到达，Redis 也只让一个写成功，另一个必定被拦。这正是「分布式原子写」的价值。

### 调用链（一张图看明白）

```
客户端 ──(timestamp + nonce + 业务参数)──▶ 网关全局过滤器
                                            │
                              ┌─────────────┴─────────────┐
                              │ ① 时间戳在 ±5min 内？       │
                              │    否 → 拦截（太老 / 被改）  │
                              │    是 ↓                    │
                              │ ② Redis SETNX "nonce:xxx"  │
                              │    已存在 → 拦截（重放）    │
                              │    写入成功 ↓               │
                              │ ③ 放行 → 业务系统           │
                              └────────────────────────────┘
```

这套逻辑放在网关的**全局过滤器**里（比如 Spring Cloud Gateway 的 GlobalFilter、Kong 的插件），所有流量统一过一遍，脏活累活由网关扛，业务系统完全不感知。

### 和「只靠时间戳」比一比

| 方案 | 能拦延迟重放（老包）吗 | 能拦「5 分钟内原样重发」吗 |
|------|------|------|
| 只用时间戳 | 能拦（>5min 的旧包） | 拦不了（重发包时间戳依然新鲜）|
| 时间戳 + Nonce + Redis | 能拦 | 能拦（nonce 已存在直接拒）|

## 一句提醒（易错点）

1. **Nonce 一定要足够随机**（用 UUID / 雪花 ID，别用自增数字），不然攻击者猜得出下一个 nonce，去重就废了。
2. **Redis 里 nonce 的过期时间要略大于时间窗口**（比如窗口 5min、过期 6min），否则窗口边缘的请求可能被误放行或误拦截。
3. 进阶还会给请求算一个**签名 sign**（把参数 + timestamp + nonce + 密钥用 HMAC 算一遍）：攻击者哪怕改了包里一个字，签名就对不上——这属于「防篡改」的加餐，本题主干是 **时间戳 + Nonce + Redis** 三板斧。
