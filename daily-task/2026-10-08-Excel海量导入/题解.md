# 百万行 Excel 导入数据库：怎么搬得动又不把服务器压垮

**一句话**：用户上传一个几百 MB、几百万行的 Excel，我们要把它**一行不漏地搬进数据库**，还不能把内存撑爆、不能把数据库拖死。

## 一、先想明白：这事为什么难

把几百万行 Excel 导入数据库，就像把一整仓库的货搬到另一个仓库。

新手最容易犯的错，是**把整仓库的货先全倒在自己身上，再一件件往对面搬**——也就是 `new XSSFWorkbook(file)` 一次性把整个文件读成内存对象。几百万行的对象图轻松吃掉好几个 G，程序还没开始搬就 OOM 了。

正确的做法是学**传送带**：货一件件从眼前过，手上最多同时拿一箱，处理完就放下。整件事其实就两难：**怎么读**（大文件解析）和**怎么写**（海量数据入库）。

## 二、四个关键点

| 关键点 | 一句话做法 | 不做会怎样 |
|---|---|---|
| ① 流式解析 | 用 SAX 事件模式边读边处理 | 全量加载 → OOM |
| ② 攒批入库 | 每 500 行拼成一条 `INSERT` | 一行一次往返 → 慢到没边 |
| ③ MQ 削峰 | 解析和入库解耦，队列当缓冲区 | 上传瞬间把 CPU / 数据库打满 |
| ④ 进度反馈 | 进度写 Redis，随时可查 | 用户盯着转圈，以为卡死了 |

### ① 流式解析：别把整张表读进内存

POI 的 `XSSFWorkbook` 是 DOM 模式（先把整个文件解析成树），百万行必炸。要用**事件模式**：`XSSFReader` + `XSSFSheetXMLHandler`，它按行回调，读完一行就丢一行。

```java
try (OPCPackage pkg = OPCPackage.open(path, PackageAccess.READ)) {
    XSSFReader reader = new XSSFReader(pkg);
    SharedStrings sharedStrings = reader.getSharedStringsTable();

    BatchPublisher publisher = new BatchPublisher(channel);   // 每读满一批就发消息
    XMLReader parser = XMLHelper.newXMLReader();
    parser.setContentHandler(new XSSFSheetXMLHandler(
            reader.getStylesTable(), sharedStrings, publisher, false));

    try (InputStream sheetStream = ((XSSFReader.SheetIterator) reader.getSheetsData()).next()) {
        parser.parse(new InputSource(sheetStream));
    }
}
```

顺带一提，**造样本文件**也得用流式写法 `SXSSFWorkbook(100)`——它只在内存里留 100 行，其余滚到临时文件，否则你自己生成一个百万行文件就先 OOM 了。

### ② 攒批入库：一车一车运，别一件一件跑

一行一次 `INSERT` 意味着 100 万次网络往返，数据库连接和网络都受不了。做法是**攒够一批拼成一条 SQL**：

```java
String placeholders = String.join(", ", Collections.nCopies(rows.size(), "(?, ?, ?, ?)"));
String sql = "INSERT INTO orders(order_id, user_id, amount, status) VALUES " + placeholders;
```

批大小取 **500~1000 行**比较稳：批太小往返多，批太大单条 SQL 过长、事务也太大容易锁表。用 `PreparedStatement` 还能复用执行计划、天然防 SQL 注入。

### ③ MQ 削峰：把「读」和「写」拆开

上传后**立刻返回「已接收」**，真正的解析入库交给后台。中间用消息队列当缓冲垫——解析线程只管往队列里丢，入库线程按自己的节奏消费，谁也不用等谁。

```java
// 解析侧：一批行打成一个消息投出去
channel.basicPublish("", QUEUE, null, encode(batch).getBytes(StandardCharsets.UTF_8));

// 入库侧：收一批、插一批、报一次进度
channel.basicQos(1);          // 一次只推一批，消息不会全堆在客户端内存里
channel.basicConsume(QUEUE, false, new DefaultConsumer(channel) { ... });
```

注意这里**一批 = 一条消息**，而不是一行一条。100 万行只有 2000 条消息，队列压力小得多，入库端还能天然凑成批量 SQL。

### ④ 进度反馈：给用户一根进度条

导入可能跑好几分钟，用户看不到状态会以为系统挂了。每批入库成功后往 Redis 累加一次，前端随便查：

```java
progress.hincrBy(PROGRESS_KEY, "done", rows.size());
```

`HINCRBY` 是原子操作，多个入库线程一起加也不会算错。真实项目里还可以顺带记 `fail` 计数和出错行号，支持「跳过坏行」或「整批回滚重试」。

## 三、实测结果

`code/src/main/java/Demo.java` 起了 MySQL + Redis + RabbitMQ 三个容器，造 10 万行样本实测：

```
流式解析并投递：100000 行，耗时 1646ms（内存占用平稳）
数据库实际入库：100000 行
Redis 进度：{done=100000}
```

从 10 万行推到几百万行，这套写法不用改结构，只是时间线性变长。

## 四、一句提醒

**别只盯着「能不能导进去」，要盯住「中途挂了怎么办」**。最常见的坑是：解析到第 87 万行时数据库抖动，程序直接抛异常退出，前面的数据全白搬。所以一定要有**重试或跳过机制**（Demo 里用 `basicNack` 让失败的消息重回队列重试），并且**导入要幂等**——用订单号这类业务唯一键做 `PRIMARY KEY`，重复导入同一行时不会变成两条。
