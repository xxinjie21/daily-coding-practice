# 缓存预热：核心数据怎么在用户上门之前就摆好

## 一句话题目

系统重启或者上线之后，缓存是空的，第一波用户请求会全部砸到数据库上。
**怎么在用户来之前，先把"最可能被访问的那批数据"提前放进缓存？** 这件事就叫缓存预热。

---

## 一、为什么会有这个问题

先说两个词：

- **数据库**（比如 MySQL）：数据真正存放的地方，可靠但慢。像早餐店的**后厨**，从和面开始做，一份要好几分钟。
- **缓存**（比如 Redis）：内存里的一块临时存放区，快但会丢、会过期。像柜台上的**蒸笼**，客人来了直接拿走。

平时的读取套路叫**缓存旁路（cache-aside）**，说白了三步：

> 先看蒸笼里有没有 → 没有就去后厨拿一份 → 顺手在蒸笼里也放一个（这一步叫**回填**）。

问题就出在"**刚开门**"这一刻。半夜重启了服务、Redis 也重启了，蒸笼是空的。
早上八点第一波客人涌进来，**每个人都得等后厨现做**——数据库瞬间被打穿，接口全部超时。

这就是预热要解决的事：**开门前先把最畅销的那几笼包子蒸好摆上**。

我在 `code/Demo.java` 里做了实测（10 万商品、2 万条早高峰请求、按每 2000 条分一段统计）：

| 第几段请求 | 不预热，回源数据库 | 预热 1000 个热点后 | 少了 |
|---|---|---|---|
| 第 1 段 | 604 次 | 279 次 | **53.8%** |
| 第 2 段 | 439 次 | 295 次 | 32.8% |
| 第 5 段 | 345 次 | 285 次 | 17.4% |
| 第 10 段 | 262 次 | 235 次 | 10.3% |

看这张表能看懂两件事：

1. **不预热的话，第一段最凶**（604 次），后面越来越少——因为系统在边跑边自己回填，慢慢把缓存"焐热"了。
2. 所以**别只看总数**。总回源 3597 → 2746 看起来只降 24%，但真正要命的第一波直接砍掉一半。数据库被打穿就发生在这几秒。

---

## 二、怎么做：盯住三件事

原题说得很准——预热不是"把数据 load 一遍扔进 Redis"就完事，关键是**时机、范围、一致性**。

### 1）时机：低峰期触发，而且必须异步

- **低峰期做**：比如凌晨发布完自动跑一次。因为预热本身也在查数据库，白天高峰去做等于自己给自己加压。
- **异步做**：Spring 里有个 `@PostConstruct` 注解，意思是"这个 Bean 造好之后自动执行一下"，很多人图省事就把预热写在里面**同步**跑——那服务就得等预热跑完才能启动，健康检查直接失败。正确做法是 `@PostConstruct` 里只丢一个后台线程，或者干脆交给 **xxl-job**（一个定时任务调度平台，可以理解成"能在网页上配的闹钟"）去触发。

实测（灌 1.8 万个 key）：

```
同步预热：启动线程被阻塞 31.3 ms，这期间服务起不来
异步预热：启动线程只被阻塞  2.3 ms，服务立刻能接流量
```

内存模拟才是毫秒级。线上一次 MySQL 往返约 1ms、Redis 约 0.2ms，灌 1.8 万个 key 轻松几十秒——**同步做就是几十秒起不来**。

代码上就一句话的区别：

```java
@PostConstruct
public void init() {
    // 别写成 warmUp();  ← 这样启动会被卡住
    new Thread(this::warmUp, "cache-warm-up").start();   // 丢后台，主线程立刻放行
}
```

### 2）范围：只灌热点，别想全量

10 万个商品全灌进去？内存吃不消，而且大部分灌了也没人看。
**只加载高频访问的那一小撮**——爆款商品、TOP 1000 用户信息之类。

怎么知道哪些是热点？**数历史访问日志**。真实项目里靠**埋点**（在代码里记一笔"谁访问了什么"）+ **Flink**（一个实时计算引擎，可以理解成"边来数据边记账的算盘"）算出热度榜，把清单存到配置中心，预热任务启动时先去拉最新清单。

原理不神秘，就是"数正字"。实测不同规模的性价比：

| 想预热 | 占全部商品 | 能盖住明天的流量 | 平均每个 key 挡下几次请求 |
|---|---|---|---|
| 100 | 0.1% | **70.5%** | 141.0 |
| 1000 | 1.0% | **84.6%** | 16.9 |
| 5000 | 5.0% | 90.6% | 3.6 |
| 18170 | 18.2% | 94.0% | 1.0 |

**只灌 1% 的商品，就能挡住 85% 的请求**——这就是为什么"范围要精准"。
再往后急剧不划算：key 数从 1000 加到 1.8 万（18 倍），流量只多盖十几个点，每个 key 的性价比掉了一个数量级。

> ⚠️ 一个容易踩的坑：**验证覆盖率要用"明天的真实流量"，不能用"算清单那份日志"自己验自己**。用同一份日志验，数字必然虚高（我第一版就跑出个 100% 的假象）。

### 3）加载动作：批量查，别逐条

原题给的核心代码就两行：

```java
List<Data> hotData = dataMapper.selectByHotKeys(hotKeyList);   // 一次 IN 查询捞一批
hotData.forEach(d -> redis.set(d.getKey(), d, 3600));          // 逐个塞进 Redis，注意那个 3600
```

为什么一定要 `selectByHotKeys` 这种批量查（SQL 里的 `where id in (...)`），而不是 for 循环里 `selectById`？
因为**一次数据库查询的成本，大头是那趟网络往返**，读一行还是读五百行差别没那么大。实测：

```
逐条 selectById    ：查数据库 1000 次，耗时 53.2 ms
批量 selectByHotKeys：查数据库    2 次，耗时  1.5 ms   ← 快约 35 倍
```

去后厨一趟能端 500 个盘子，就别来回跑 1000 趟。
但也别一次塞太多，**500~1000 一批**分批循环最稳，IN 里塞几万个 key 会让 SQL 自己变慢。

### 4）一致性：灌完了不能放任不管

这是最容易被忽略的一条。预热只是"提前把复印件摆出来"，摆完之后**照常走正常的读写逻辑**：

- **读**：还是缓存旁路，没命中就回源 + 回填。
- **写**：更新数据库之后**必须把缓存删掉**。删了缓存，下一个来读的人自然会去数据库拿到新值再回填。

忘了删缓存会怎样？实测：

```
只改库、不删缓存：运营把价格改成 99 分，用户依然读到 1007 分   ← 脏数据，而且一直错
更新库 + 删缓存  ：改成 99 分后立刻读到 99 分                  ← 正确
```

柜台价签是后厨价格的复印件。后厨改价就得把旧价签**撕掉**，下一个客人来时自然会拿到新的那张。

### 5）TTL 一定要给

`redis.set(key, value, 3600)` 里的 **3600 就是 TTL**（Time To Live，存活时间，说白了就是**保质期标签**，到点自动消失）。

为什么必须给？因为总有些改动**不走你的删缓存逻辑**——运维直接改库、老系统绕过你写库。这时候缓存里的旧值就成了**僵尸缓存**：一直错，而且永远没人来纠正。有 TTL 就等于有了兜底，到期自动回源一次，自己把自己纠正过来。实测：

```
不设 TTL   ：数据库已经是 555 分，缓存还是 1008 分，会一直错下去   ← 僵尸缓存
设 1 秒 TTL：到期后再读，自动回源数据库读到 555 分               ← 自己纠错了
```

## 三、整个链路串起来

```
凌晨低峰 / 发布后
      │
      ▼
 xxl-job 或 @PostConstruct  ──丢后台线程──▶ 服务立刻启动，开始接流量
      │
      ▼
 拉最新热点清单（配置中心，由埋点+Flink 算出）
      │
      ▼
 分批 selectByHotKeys(500 个一批)  ──▶  redis.set(key, value, 3600 + 随机秒)
      │
      ▼
   预热完成
      │
      ▼
白天正常跑：读 → 缓存没有就回源+回填
           写 → 更新数据库 + 删缓存
           TTL 到期 → 自动回源纠错
```

---

## 四、一句提醒

**TTL 千万要打散。**

如果几万个 key 都写死 `3600`，那它们是在同一秒被灌进去的，也会在**同一秒集体过期**——请求瞬间全砸到数据库，这就是**缓存雪崩**，比不预热还惨。

正确写法是加个随机抖动：

```java
int ttl = 3600 + new Random().nextInt(600);   // 3600~4200 秒之间随机
redis.set(key, value, ttl);
```

另外记住一句话：**Redis 里是复印件，MySQL 才是原件。** 预热只是让复印件提前摆好，不能因为预热过就以为缓存里的数据一定对。

`code/Demo.java` 里六个实验，都可以直接跑（编译运行：`javac -encoding UTF-8 --release 17 Demo.java && java Demo`）：
