# 深度分页：LIMIT 1000000, 20 为什么慢，怎么救

## 一句话题目

翻订单列表翻到第 5 万页，SQL 写成 `LIMIT 1000000, 20`，只要 20 条数据，结果卡了好几秒。为什么？怎么改？

## 为什么会有这个问题

想象你手上有一本没有页码的《新华字典》，别人让你「翻到第 100 万个字，往后读 20 个字」。

你只能一个字一个字地数：数到 100 万，前面数过的全部作废，然后才开始读那 20 个字。

MySQL 干的就是这个事。`LIMIT 1000000, 20` 里的 `1000000` 叫 **offset（偏移量）**——"跳过前面多少行"。但数据库**没有能力"一步跳过去"**，它只能真的把前 100 万行一行行读出来、再一行行丢掉。

- 读第 1 页 `LIMIT 0, 20`：读 20 行，眨眼就好
- 读第 5 万页 `LIMIT 1000000, 20`：读 100 万行，扔掉 999980 行

`code/Demo.java` 里跑出来的实测（模拟 100 万行订单表）：

| offset | 实际扫描行数 | 有效返回 | 耗时 |
|---|---|---|---|
| 0 | 20 | 20 | 0 ms |
| 10000 | 10020 | 20 | 0 ms |
| 500000 | 500020 | 20 | 18 ms |
| 999980 | 1000000 | 20 | 31 ms |

**病根一句话：这种分页依赖「物理偏移」，跳过的行越多就越慢，跟你最终要几条数据完全无关。**

## 怎么做

### 方案一（首选）：游标分页 —— 别说"跳过多少行"，改说"从哪之后开始"

不问"第 5 万页在哪"，而是**记住上一页最后一条的 id**，下一页直接从它后面开始：

```sql
-- 原来（慢）
SELECT * FROM orders ORDER BY id LIMIT 1000000, 20;

-- 改成（快，且不管翻多深都一样快）
SELECT * FROM orders WHERE id > 2000962 ORDER BY id LIMIT 20;
```

为什么快？因为主键 id 上有 **索引**——索引就像字典前面的音序检索表，按顺序排好，能直接翻到目标位置，不用从第一页数起。所以 `id > 2000962` 是"查字典定位"，复杂度 O(log n)；而 offset 是"一个字一个字数"。

实测：翻到第 5 万页附近，游标分页**只扫了 20 行、耗时 6 微秒**（对比上表的 31 毫秒，差了几千倍），而且**翻到第几页都是这个数**。

> **易错点**：主键常有"空洞"（删过数据、或用雪花 id），第 21 行的 id 未必是 21。Demo 里那张表第 1 行 id=1001，第 21 行 id=1042。所以**千万别用「页码 × 每页条数」去算 id**，必须老老实实把上一页真实的最后一条 id 带回来。

### 方案二：真要"跳到第 N 页"，用延迟关联兜一下

产品经理如果坚持要页码跳转，游标分页就没法用了（你没法凭空知道第 500 页的起点 id）。这时候用**延迟关联**：先只在索引上扫 id，最后才拿这 20 个 id 去取完整数据。

```sql
SELECT o.* FROM orders o
JOIN ( SELECT id FROM orders ORDER BY id LIMIT 999980, 20 ) t
  ON o.id = t.id;
```

这里的关键词是 **回表**——索引里只记了 id 和排序字段，其他字段（买家名、金额、地址…）还得再跑一趟主表去取，就像"仓库提货"。普通写法要为 100 万行每行都提一次货再扔掉；延迟关联只提最后那 20 次货。

实测对比：

| 写法 | 回表取完整行次数 | 耗时 |
|---|---|---|
| 普通 LIMIT offset | 1000000 | 40 ms |
| 延迟关联 | 20 | 0 ms |

但要清醒：**延迟关联只是"少搬货"，索引上那 100 万行还是要数一遍**，数据量再涨还是会慢。它是次优解，不是银弹。更推荐的是**说服前端改成"加载更多"/无限滚动**，这样天然适配游标分页。

### 方案三：热点榜单直接放 Redis ZSET

首页热榜、Feed 流这种"数据量不大但访问巨多"的场景，别让 MySQL 硬扛。丢进 Redis 的 **ZSET（有序集合）**——可以理解成一个自动按分数排好队的排行榜，每个成员挂一个 score（分数，比如发布时间戳），Redis 帮你一直维持顺序：

```
ZADD feed:hot 1700000001 内容#1
ZREVRANGE feed:hot 20 29     -- 按分数从高到低，取第 3 页
```

Demo 里 1000 条榜单取第 3 页，全程没碰数据库。注意：这里能放心用 offset，是因为**总量小且全在内存**，跟扫 100 万行磁盘数据是两码事——数据一旦大起来，Redis 里同样得回到游标那套。

## 一句线上提醒

**按创建时间排序时，游标一定要带上 id 做"第二把钥匙"。**

同一秒可能下了好几单，`createTime` 完全相同。如果游标只写 `WHERE create_time > 上一页最后的时间`，那些和边界同一时刻的订单会被整批跨过去——**数据凭空消失，还不报错**。Demo 实验四里 6 条数据只翻出 5 条，id=103 就这么没了。

正确写法：

```sql
WHERE create_time > ?
   OR (create_time = ? AND id > ?)
ORDER BY create_time, id
LIMIT 20;
```
