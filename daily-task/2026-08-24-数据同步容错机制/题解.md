# 如何设计一个高可用的数据同步系统？需要考虑哪些容错机制？

**一句话题目（大白话）：** 把 A 库的数据实时搬到 B 库，路上会塌方（网络断）、会车坏（下游挂）、还会有人把同一批货来回搬（循环复制）——怎么保证货**不丢、不重、不绕圈**？

**为什么会有这问题？**
想象北京仓和上海仓每天要对账搬货。理想情况是一条流水线顺顺当当；可真实世界里，高速会封路、上海仓会临时关门、搬运工还可能把同一批货来回搬。数据同步系统要解决的不是「搬得动」，而是「搬不丢、搬不重、崩了能接着搬」。重点不在功能，在**容错兜底**。

**怎么做？核心就 5 道保险——**

1. **断点续传**：搬货时每搬一批就在小本子上画个勾（记录「运到哪一车了」）。车半路坏了，回来从勾的位置继续，不重搬、不漏搬。技术上就是**把读取位点（如 MySQL 的 binlog 位点、Kafka 的 consumer offset）和这批数据一起原子落盘**，重启后从最后确认的位点恢复。Canal、Flink CDC 都这么干。
2. **缓冲层（消息队列）**：上海仓暂时关门，北京的货先堆在「中转仓库」（Kafka 这类消息队列），等上海开门再慢慢送进去，货不丢。下游挂几小时也没事，恢复后慢慢重放。
3. **重试 + 指数退避 + 死信队列**：送货失败别一下猛拍门（会把对方拍垮）。等 1 秒、再等 2 秒、4 秒……最多 5 次；还不行就放进「问题货区」（死信队列 DLQ）等人处理。RocketMQ、Pulsar 内置这套机制。
4. **循环复制标记**：每批货贴个「北京发」的标签（消息头加 sync-id）。北京收到带自己标签的货就直接扔掉，否则 A→B→A 会无限绕圈刷数据。
5. **对账补数**：每天盘一次两仓的账，发现上海少了几件，立刻补发。这是最后一道防线（滴滴 DTS、阿里 Otter 都带这能力）。

**对照表（一眼看清每道保险管什么）：**

| 风险 | 兜底机制 | 一句话 |
| --- | --- | --- |
| 同步中途崩了 | 断点续传（位点 checkpoint） | 从小本子的勾继续搬 |
| 下游临时挂了 | 消息队列缓冲 | 货先堆中转仓，开门再送 |
| 下游偶尔抖 | 指数退避重试 | 别拍门，等会儿再试 |
| 下游彻底坏 | 死信队列 DLQ | 进问题区等人修 |
| A→B→A 绕圈 | sync-id 标记过滤 | 自己发的自己丢 |
| 长期静默丢数 | 定期对账补数 | 每天盘账兜底 |

**一句线上提醒：** **「位点」和「数据」必须一起原子提交**——只更新了数据没记下位点，重启后会重复消费；只记了位点没写进数据，会静默丢数。这个顺序写反，是数据同步最常见也最隐蔽的 bug。
