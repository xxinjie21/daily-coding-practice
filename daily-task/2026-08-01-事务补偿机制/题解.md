# 分布式事务补偿机制：一步出错怎么兜底，补偿又失败了怎么办

**① 一句话题目（大白话）**
你在网上买东西，下单、扣库存、扣钱分属三个不同的系统。它们没法像"一个数据库"那样一起回滚，所以得用"补偿"：哪一步失败了，就把前面已经成功的步反过来做一遍，把账补平。

**② 为什么会有这问题？**
打个比方：去餐厅吃饭，先点菜（下单）、厨房做菜（扣库存）、最后结账（扣钱）。如果结账时你会员卡没钱（扣款失败），前面点的菜和占的锅就得"退掉 / 撤销"——这就是补偿。可现实里退菜也可能失败（菜已经下锅了），所以"补偿"本身也会失败，必须有兜底方案。

**③ 怎么做（核心四招）**

**招1：每步都记账，补偿前先查状态（幂等）**
像 Seata 那样维护一张"事务日志表"，记录「全局事务ID + 每步的状态」。补偿不是无脑反向操作，而是先查状态——只有"已成功、还没补偿过"才执行。这样即使同一条补偿消息被重复投递，也不会把库存退两次、钱扣两遍。
> 生活比喻：退菜前先问前台"这道菜退过没？"，退过了就别再退。

**招2：补偿失败要重试，但别死循环**
用消息队列做延迟重试（比如 RocketMQ 事务消息 / Kafka 重试主题）。第1次失败→发条 5 秒后的延迟消息重试，最多 3 次；3 次还失败就丢进「人工干预队列」让运维处理。

**招3：留好对账和修复入口**
再周全也会出极端情况。每天定时跑"对账"：比如发现"订单已取消但余额没退"，就手动触发修复或导出异常单给运维。

**招4：补偿链别太长**
超过 5 个服务的长事务，拆成多个短事务，每段独立补偿。否则一环卡住，整条链都动不了。

（核心数据流：`正向 ①→②→③` 某步失败 → `反向补偿 ③←②←①`，每步先查状态再执行 → 失败则 MQ 延迟重试 → 仍失败进人工队列）

**④ 一句提醒**
别指望一次就成。接受"最终一致性"——监控、日志、重试、对账，这套基建缺一个都不稳。
