# RPC 框架设计：怎么让"调远方的服务"像"调本地方法"一样简单

> 原题：让你设计一个 RPC 框架，怎么设计？（来源：后端系统设计面试题 #35）

## ① 一句话说清题目

RPC（Remote Procedure Call，远程过程调用）就是：你在代码里写 `userService.getUser(1)`，看起来像调用本地方法，实际上这个方法跑在另一台服务器上。RPC 框架要做的，就是把中间"跨网络"的脏活全部藏起来。

## ② 为什么会有这个问题

打个比方：你在家想吃楼下餐馆的菜。

- **本地调用**：菜就在自家冰箱，伸手就拿。
- **远程调用**：菜在餐馆，你得知道餐馆地址、打电话点单、说清楚要什么菜、等外卖送到。

微服务时代，用户服务、订单服务分别部署在不同机器上，互相"点菜"是家常便饭。如果每次调用都自己写网络代码（连接、传参、等结果），程序员会累死。RPC 框架就是那个"外卖平台"——你只管点菜，找店、下单、配送它全包了。

## ③ 怎么做：四个核心问题 + 一条调用链

按原题思路，RPC 本质是搞定四件事：**调哪儿、传什么、怎么传、结果怎么拿**。

```
消费者代码                                        提供者机器
userService.getUser(1)
   │
   ▼
[1] 动态代理拦截 ──► [2] 序列化成字节 ──► [3] Netty 网络发送 ──► [4] 服务端反射执行真方法
   ▲                                                                │
   └──── [6] 按请求ID唤醒等待线程 ◄── [5] 结果序列化传回 ◄──────────┘
```

### 1）服务暴露与发现 —— "调哪儿"

服务启动时，把自己的接口名、IP、端口登记到**注册中心**（如 ZooKeeper、Nacos——可以理解成"商家黄页"，谁开店了就登记一条）。消费者启动时去黄页拉一份可用商家列表，**缓存在本地**，避免每次调用都翻黄页。

### 2）动态代理拦截调用 —— 让调用"看起来像本地"

你代码里的 `userService` 只是个接口，根本没有实现类。框架用 **JDK 动态代理**（可以理解成"替身演员"：长得和真人一样，但每个动作其实都被导演接管了）生成一个代理对象。你一调方法，就进到 `InvocationHandler`（导演的剧本），它把**方法名、参数**抓出来打包成请求。

### 3）网络通信与序列化 —— "传什么、怎么传"

- 对象没法直接在网线上跑，得先**序列化**（把 Java 对象变成一串字节，就像把家具拆成平板包装再快递）。可选 Protobuf、Hessian、JSON —— Protobuf 体积小、速度快、跨语言。
- 传输层一般选 **Netty**（一个高性能网络框架，异步非阻塞——像餐厅服务员点完单不站在桌边干等，先去服务别桌，菜好了再端来）。

### 4）请求唯一 ID + 异步等待 —— "结果怎么拿"

网络是异步的：请求发出去，响应不知道啥时候回来，而且可能同时有几百个请求在飞。怎么对上号？

- 每个请求发出前打一个**唯一 ID**（用原子递增计数器，像取号机不会发重号）。
- 把"ID → 等待器"放进一个 `ConcurrentMap`（线程安全的字典，多人同时读写不打架）。
- 调用线程用 `CountDownLatch`（一个"门闩"：数到 0 门才开）挂起等结果。
- 响应回来时，按 ID 从字典里找到对应门闩，放行并把结果交给等待的线程。

这就像海底捞等位：进门先取号，你拿着 42 号坐着等；叫到 42 号，你才起身入座——号码就是请求 ID。

### 5）容错与负载均衡

- 某个提供者挂了 → **重试**换一台，配合负载均衡策略（随机、轮询、一致性 Hash）挑下一家。
- **超时必须设**：不设超时，提供者卡死会把消费者的线程全拖死（外卖 2 小时没到就该退单换店，不能干等一晚上）。

### 关键取舍小表

| 决策点 | 常见选择 | 为什么 |
|---|---|---|
| 注册中心 | ZooKeeper / Nacos | 服务动态上下线，手工配 IP 维护不动 |
| 序列化 | Protobuf 优先 | 体积小、快、跨语言；JSON 可读性好但胖 |
| 传输 | Netty | 异步非阻塞，几千并发连接不虚 |
| 等结果 | ID + Map + Latch | 异步网络里"对号入座"的标准解法 |

## ④ 一句提醒

先把"能通"做到位（代理 → 序列化 → 网络 → 对号返回），再逐步加路由、限流、熔断这些"脏活累活"；**超时时间永远是第一优先级配置**，漏配一次就可能拖垮整条调用链。
