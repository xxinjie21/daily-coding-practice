# 接口调用量统计：怎么知道每个接口这一分钟被调了多少次

> 原题：如果让你统计每个接口每分钟调用次数怎么统计？（来源：source-doc 后端场景面试题 19 / 系统设计题 23）

---

## 一句话题目

线上有几十个接口，我想随时知道「`/user/get` 这一分钟被调了 8000 次、上一分钟 6500 次」，这个数该怎么统计出来？

---

## 为什么会有这问题

想象你开了家便利店，门口装了个计数器。你不关心「开业到现在一共来过多少人」——那个数只会一直涨，看不出问题。你真正想知道的是：**「刚刚这一分钟涌进来多少人？」** 因为只有这个数，才能告诉你现在是不是被挤爆了。

接口也一样。总调用量没用，**每分钟的量**才有用：

- 突然从 6000 涨到 60000 → 可能被刷了，该限流了
- 突然从 6000 掉到 0 → 上游挂了，该报警了

而难点在于：**接口每秒可能被调几千次，这个"计数"动作本身不能拖慢业务**。你不能为了数个数，让每个请求都排队等锁。

---

## 怎么做

### 第 1 步：按分钟"分桶"，一分钟一个格子

思路很土但极其好用：**把时间切成一分钟一格，每格放一个计数器**。

怎么算"当前是第几分钟"？用时间戳除以 60000（一分钟 = 60000 毫秒）：

```java
long minute = System.currentTimeMillis() / 60000;   // 得到一个整数，比如 29123456
String key = "api:/user/get:" + minute;             // 这一分钟、这个接口，专属的格子
```

> **什么是"桶"（bucket）？** 就是个格子。像超市理货，把每分钟来的人塞进当分钟那个筐里，筐和筐互不干扰。时间一到，自动换新筐。

然后把计数器放进一个 `ConcurrentHashMap` 里：

```java
ConcurrentHashMap<String, AtomicInteger> counter = new ConcurrentHashMap<>();
counter.computeIfAbsent(key, k -> new AtomicInteger()).incrementAndGet();
```

三个陌生名词，各配一句大白话：

| 名词 | 大白话 |
|---|---|
| `ConcurrentHashMap` | 一个**多人同时写也不会写坏**的字典。普通 HashMap 多线程一起写可能把数据搞乱，它不会 |
| `AtomicInteger` | 一个**不会卡壳的取号机**。100 个人同时按，出来就是 100 个不重复的号，不会两个人拿到同一个号 |
| `computeIfAbsent` | "**没有就新建，有就直接拿**"。第一次访问这一分钟时自动建格子，之后直接用 |

就这三行，核心逻辑全在里面了。

### 第 2 步：别用 synchronized，用 CAS

新手最容易写成这样：

```java
synchronized (this) { count++; }   // ❌ 别这么写
```

`synchronized` 是**加锁**——像只有一把钥匙的厕所，后面的人全排队。接口一秒几千次调用，全卡在这一把锁上，业务直接被拖慢。

`AtomicInteger` 走的是 **CAS**（比较并交换）：它不排队，而是"我看一眼现在是 100，我改成 101；如果发现已经被别人改成 101 了，那我重试一次改成 102"。**没人排队，谁快谁先过**。

> 生活比喻：`synchronized` 是排队打卡机，一次一个人；CAS 是自助扫码闸机，大家同时刷，冲突了重刷一下就行。

本文 Demo 实测（8 线程各加 50 万次，共 400 万次）：两者**结果一样准**，但 `synchronized` 耗时约是 `AtomicInteger` 的 **2.5 倍**（120ms vs 49ms）。而且线程越多、锁里的活儿越重，差距拉得越大。

### 第 3 步：过期的桶要清掉，不然内存会炸

一分钟一个格子，一天就是 1440 个；再乘以 50 个接口 = 7 万多个格子。放着不管，跑几天内存就撑不住了。

做法：**只保留最近 5 分钟，剩下的定时清掉**。

```java
// 每分钟跑一次：把"分钟号 < 当前分钟 - 4"的格子全删掉
long oldestKeep = currentMinute - 5 + 1;
buckets.keySet().removeIf(key -> parseMinute(key) < oldestKeep);
```

> 为什么留 5 分钟而不是 1 分钟？因为监控采集、报警判断往往要看「连续几分钟的趋势」，只留当前分钟就没法对比了。

### 第 4 步：量再大，就"本地攒着、批量上报"

如果你有 20 台机器，每台都想把数据写到 Redis 里汇总——**每次调用都写一次 Redis，等于把网络请求量翻倍**，Redis 先扛不住。

正确做法：**本地先攒，每 10 秒打包发一次**。

```
请求 → 本地 AtomicInteger +1（纳秒级，零网络）
                ↓
        每 10 秒 flush 一次
                ↓
        Redis INCRBY key 8000   ← 一次网络请求顶 8000 次
```

这就是 Sentinel（阿里的流量治理组件，专门做限流/熔断的）的做法：**本地滑动窗口统计，异步线程批量上报**。Demo 里实测：3 台机器打了 3 万次点，flush 之后 Redis 里一分不差是 30000，但**总共只发了 1 次网络请求**。

### 第 5 步：要跨机器精确统计，才上 Redis INCR + EXPIRE

如果需求是「全集群加起来这一分钟到底多少次」，且要求**一次都不能差**（比如防刷、按次计费），那就直接写 Redis：

```
INCR   api:/user/get:29123456     # 原子自增，20 台机器一起写也不会算错
EXPIRE api:/user/get:29123456 300 # 5 分钟后自动删，不用自己写清理任务
```

`EXPIRE` 就是**给这个 key 贴张便利贴：5 分钟后自动销毁**，省了清理逻辑。

⚠️ 但注意：`INCR` 和 `EXPIRE` 是两条命令，中间如果崩了会留下**永不过期的 key**。生产上用 Lua 脚本把两条命令打包成一个原子操作。

### 三种方案怎么选

| 方案 | 准不准 | 快不快 | 什么时候用 |
|---|---|---|---|
| 纯本地内存桶 | 单机准，集群要自己汇总 | 最快（纳秒级，零网络） | 监控大盘、看趋势 |
| 本地攒批 + 批量上报 | 准（有几秒延迟） | 快 | **绝大多数场景，推荐** |
| 每次都写 Redis INCR | 最准，实时 | 慢（每次一次网络） | 防刷、计费这种一次都不能错的 |

---

## 一句提醒

**清理任务千万别忘了写。** 线上见过太多"计数功能上线两周后 OOM"的事故——不是计数逻辑错，是分钟桶只进不出，Map 越涨越大最后把堆撑爆。

另外一个易错点：算 key 时不要用 `LocalDateTime` 拼字符串（慢且有时区坑），就用 `System.currentTimeMillis() / 60000`，一次整数除法搞定。
