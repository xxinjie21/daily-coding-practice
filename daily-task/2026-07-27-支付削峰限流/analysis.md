# 拆解：消息队列削峰 + Redis 令牌桶统一控速

## 一、先把题读透：这题到底在考什么

题目给的数字很关键：**进口 200/秒，出口 100/秒**。进得快、出得慢，中间必然要有个"蓄水池"，不然多出来的 100 笔/秒直接怼到第三方，人家立刻把你限流拒绝。

所以这题的本质就两件事：

1. **削峰填谷**：高峰期把多余的请求先存起来，慢慢消化——就像水库，上游山洪暴发时先蓄水，再按下游河道能承受的流量匀速放水；
2. **流量整形**：出口速度必须精准卡在 100/秒——既不能超（会被封），也不能低（浪费额度）。

原题文档给出的方案是：**消息队列（Kafka/RocketMQ）做缓冲 + Redis 令牌桶做全局速率控制 + Worker 幂等消费 + 监控积压**。下面逐个讲清楚。

## 二、整体架构：一条流水线

```
下单请求(200/秒)
     │
     ▼
[接入层] 订单校验后立刻写入消息队列，马上返回"支付排队中"
     │
     ▼
[消息队列 Kafka]  ←—— 蓄水池：持久化存储，先进先出
     │
     ▼
[支付 Worker 集群]  多台机器同时消费
     │  每次干活前，先去 Redis 令牌桶"取号"
     ▼
[Redis 令牌桶]  ←—— 全局水龙头：每秒只发 100 个令牌
     │  拿到令牌才放行
     ▼
[第三方支付渠道]  稳定收到 ≈100 笔/秒
```

**消息队列**（第一次见这个词的话：它就像银行门口的取号排队机 + 等候区，请求先领号坐下，柜员按号叫人，谁也别挤）在这里干三件事：

- **缓冲**：200 进 100 出，每秒多出来的 100 笔先在队列里排着；
- **FIFO**：Kafka 的"分区"（partition，可以理解成一条独立的队伍）内部天然先进先出。想要严格全局有序，就把支付消息发到同一个分区；想要吞吐量，可以按"商户号"或"用户号"分队伍——同一个用户的订单在同一条队伍里排，互相之间不乱序，这在支付场景通常就够了；
- **持久化**：消息落磁盘、多副本，机器宕机了订单也不丢（对比放内存里排队：一断电全没了）。

## 三、最核心的难点：多台 Worker 怎么"合起来"刚好 100/秒

这是本题的胜负手。假设你起了 5 台 Worker，如果每台自己限速 100/秒，加起来就是 500/秒——超限 5 倍，直接被第三方拉黑。

**错误做法**：每台机器配置 100 ÷ 5 = 20/秒。看着行，实际很脆：加一台机器就超限，挂一台机器就浪费 20/秒的额度。

**原题给的正确做法：Redis 实现全局令牌桶。**

先解释**令牌桶**（token bucket）：想象景区门口有个发票口，管理员**每秒往桶里丢 100 张门票**，游客进门前必须先抢到一张票，桶空了就原地等。这样无论门口挤了多少游客（多少台 Worker），**进门速度永远不超过发票速度**。

为什么用 Redis？因为 Redis 是所有 Worker 共享的"同一个桶"——它是个独立部署的内存数据库，单线程处理命令，天然适合做全局计数。5 台还是 50 台 Worker 都来抢同一个桶里的票，总速率恒定 100/秒，**机器随便加减，速率不变**——这就是"统一速率控制器"的意义。

### 令牌桶的关键实现细节

1. **补令牌的方式**：不需要真的开个定时器每秒塞 100 个。惰性计算即可——每次有人来取令牌时，算一下"距离上次取令牌过去了多久 × 每秒 100 个 = 该补多少"，补上再扣。
2. **原子性**：判断"桶里有没有票"和"扣一张票"必须一气呵成，不然两台 Worker 同时看到"还剩 1 张"，都认为自己抢到了，就超发了。Redis 里用 **Lua 脚本**（Redis 保证一段 Lua 脚本执行期间不插入其他命令，相当于把几步操作打包成"一步"）来实现。
3. **桶容量别太大**：桶容量决定"最多攒多少张票"。攒太多的话，空闲一阵后突然来流量，瞬间放出一大波请求冲击第三方（毛刺）。支付场景建议桶容量 ≈ 100～200（1～2 秒的量）。
4. **拿不到令牌怎么办**：Worker 原地小睡几十毫秒再试，**不要疯狂轮询**打爆 Redis。

### 为什么不用简单计数器？

原题特别提醒：**要用滑动窗口思想，别用固定窗口计数器**。固定窗口的毛病：第 1 秒的最后 100 毫秒发了 100 笔，第 2 秒的前 100 毫秒又发了 100 笔——按"每个整秒"统计都合规，但实际 200 毫秒内怼了 200 笔，第三方按自己的滑动窗口一测，你就超限了。令牌桶按"匀速补票"天然就是平滑的，没这个毛病。

## 四、可靠性：丢单和重复扣款都不能忍

**丢单**：队列持久化 + 多副本解决。Worker 的消费位点（记录"消费到哪了"的书签）要在**业务处理成功后再提交**，这样 Worker 处理到一半宕机，消息会被别的 Worker 重新消费，不丢。

**重复扣款**：上面"重新消费"带来了新问题——同一笔订单可能被处理两次；调第三方超时后重试也可能重复。所以 Worker 必须做**幂等**（idempotent，大白话：同一件事做一遍和做十遍，结果一样，就像电梯按钮按多少次也只叫来一台电梯）：

- 以**订单号**为唯一键，处理前先查支付流水表，这单已发起过就直接跳过；
- 数据库给订单号加唯一索引兜底，并发插入时第二条必然失败；
- 调第三方时带上唯一的"商户订单号"，第三方那边也会按这个号去重——**超时不代表失败**，重试前先调第三方的查单接口确认状态。

## 五、监控与兜底：队伍越排越长怎么办

算笔账：进 200/秒、出 100/秒，队列每秒净增 100 笔。这架构**只能扛短时高峰**，如果 200/秒是常态，队列积压会无限增长，用户等待时间越来越长——这不是技术 bug，是**产能不足**。

所以监控必须盯三个指标：

1. **队列积压量**（还有多少人在排队）；
2. **出队速率**（是否稳定贴着 100/秒——低了说明令牌浪费或 Worker 不够）；
3. **失败率**（第三方是不是在拒单）。

发现**长期积压**，技术上无解，出路是业务决策：

- **申请提额**：找第三方把 100/秒的限额买大；
- **多渠道分流**：接第二家支付渠道，各自一个令牌桶；
- **降级/拒载**：高峰期对新请求快速失败（"当前排队人数过多，请稍后再试"），保护存量订单的体验。

## 六、方案要点回顾

| 需求 | 对应手段 |
|------|---------|
| 200 进 100 出不崩 | Kafka 消息队列做缓冲，削峰填谷 |
| FIFO | 分区内天然有序；按用户/商户分区保证局部有序 |
| 全局不超 100/秒 | Redis + Lua 全局令牌桶，所有 Worker 共抢一个桶 |
| 用满 100/秒 | 令牌匀速生成，Worker 拿到就干活，不空转 |
| 宕机不丢单 | 队列持久化多副本 + 处理成功后再提交消费位点 |
| 不重复扣款 | 订单号幂等 + 唯一索引 + 第三方查单确认 |
| 长期积压 | 监控告警 + 提额/多渠道/降级 |
