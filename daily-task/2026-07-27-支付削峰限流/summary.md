# 踩坑与拓展

## 一、线上真实踩坑点

### 1. "每台机器各限各的"——分布式限流最常见的翻车

单机限流工具（比如 Guava 的 RateLimiter）只能管住自己这台机器。5 台 Worker 每台限 100/秒，合计 500/秒，第三方直接把你拉黑。**分布式环境必须有全局共享的桶**（Redis），机器数量变来变去，总速率纹丝不动。

### 2. 固定窗口计数器的"毛刺"陷阱

用"每个整秒计数、到点清零"的简单计数器，会出现两个窗口交界处 200 毫秒内打出 200 笔的尖峰。你自己统计"每秒都没超"，第三方按滑动窗口一算就是超限。**用令牌桶或滑动窗口**，让流量平滑，而不是"账面合规"。

### 3. 拿到令牌就猛冲

一台 Worker 攒了一批消息，抢到令牌后瞬间把请求打出去，微观上仍是一波脉冲。原题特别提醒：**哪怕令牌拿到了也要匀速发**。实操上把桶容量调小（1~2 秒的量），单台 Worker 每次只取少量消息，发送之间留点间隔。

### 4. 超时 ≠ 失败，盲目重试 = 重复扣款

调第三方超时后，那笔支付可能已经成功了。直接重试就是给用户扣两次钱，客诉直接上门。正确姿势：**先调第三方查单接口确认状态，未支付才重试**；同时自己这边用订单号做幂等 + 数据库唯一索引兜底。

### 5. 先提交消费位点、后处理业务——宕机丢单

Worker 拉到消息就告诉队列"我消费完了"，然后才去调支付；中途宕机，这笔订单谁也不会再处理。顺序必须是**业务处理成功 → 再提交位点**，宁可重复消费（有幂等兜着），不可丢。

### 6. Redis 挂了，全体停摆还是全体裸奔？

令牌桶依赖 Redis，Redis 抖一下，所有 Worker 拿不到令牌。要提前想好降级策略：短暂不可用时 Worker 退回到"保守本地限速"（比如每台 100/N 的静态配额），并立刻告警，而不是全停（额度全浪费）或不限速（超限被封）。

### 7. 积压监控缺位，用户等到发疯

200 进 100 出，队列每秒净增 100 条。没有积压告警的话，等用户投诉"付款半小时没反应"才发现队列里躺了几十万条。**上线第一天就要有积压量、出队速率、失败率三块监控大盘**，并设阈值告警。

## 二、同类场景拓展

这套"**队列缓冲 + 全局令牌桶限流 + 幂等消费**"是个万能组合拳，能平移到很多场景：

| 场景 | 相同点 | 差异点 |
|------|--------|--------|
| 短信/邮件发送平台 | 运营商通道也有 QPS 上限，用队列缓冲 + 令牌桶控速 | 短信可容忍秒级延迟，可再按"营销/验证码"分优先级队列 |
| 秒杀下单 | 同样是入口流量 >> 后端产能 | 秒杀多数请求注定失败，先在入口层拦截（库存预扣、随机丢弃），不像支付要"每单必达" |
| 爬虫抓取对方网站 | 对方有反爬限速，令牌桶控制抓取频率 | 失败可放弃或延后，无需严格 FIFO |
| 调用大模型/开放平台 API | 按 QPS/配额计费，要"用满但不超" | 可加优先级：在线请求先走，离线批处理捡漏 |
| 银行代扣/批量代发 | 渠道限流 + 严格不可重复扣款 | 通常是定时批处理，实时性要求低，更看重对账 |

## 三、演进路线（从能跑到好用）

1. **第一步（能跑）**：单 Kafka 分区 + Redis 令牌桶 + 一组 Worker，严格全局 FIFO，先把"不超限、不丢单、不重付"三件事做扎实。
2. **第二步（提吞吐）**：按用户/商户号哈希到多分区，局部有序代替全局有序，Worker 水平扩容。
3. **第三步（保体验）**：加优先级——大额订单、VIP 商户走高优队列；普通订单排常规队列。
4. **第四步（谈业务）**：积压持续增长时，推动提额或接入第二支付渠道做分流，每个渠道独立一个令牌桶；入口层加排队人数提示与快速失败。
