# 使用 LIMIT OFFSET 分页同步时，发现数据丢失了，可能是什么原因？如何解决？

## 一句话题目（大白话）

你用 `LIMIT offset, size` 一页一页把数据搬到另一张表（做同步 / 导出），搬着搬着发现：要么少了几条、要么同一条出现了两次。这题问——为什么会丢，怎么改才稳。

---

## 一、为什么会有这个问题（用搬家比喻）

想象你在图书馆按书架顺序搬书（这就是「数据同步」）。你计划：第 1 趟搬第 1–1000 本，第 2 趟搬第 1001–2000 本……这里的「第几本」就是 `offset`（偏移量）。

问题来了：你刚搬完第 1 趟，**管理员（别的程序）又往最前面塞了一本新书**。现在整排书整体往后挪了一位——你第 2 趟按「第 1001 本起」去拿，其实拿到的是原本第 1002 本，**中间那本被挤进了你已经搬过的第 1 趟范围**：它既没被当新的再搬一次，又不在你第 2 趟的窗口里 → 这本书就这么「丢了」。同时边界那本还会被你搬两次（重复）。

数据库（比如 MySQL 的 InnoDB 表）里这事儿更隐蔽：你按「时间」排序分页，但**同一秒可能有多条记录，时间相同的情况下谁排前面并不固定**（非唯一索引排序不稳定），offset 一错位就漏。

---

## 二、怎么做：放弃 offset，改用游标（cursor）

核心思路一句话：**别数「第几条」，改成「从哪条之后开始拿」**。

给每条数据一个「单调且唯一」的游标（通常用 **时间 + 主键 id** 组合，保证不重也不跳）。每次记住上一批最后一条的 `(时间, id)`，下一批只捞「比它更老（或更新）且严格在它之后」的：

```sql
-- 按时间倒序分页：每次把最后一条的 (ts, id) 当接力棒
SELECT id, ts, data
FROM t
WHERE (ts < 上次最后的时间) OR (ts = 上次最后的时间 AND id < 上次最后的id)
ORDER BY ts DESC, id DESC
LIMIT 1000;
```

每次把最后一条的 `(ts, id)` 传给下一页。这样**每条数据只会被遍历一次，插在中间 / 前面都不会错位**。Kafka、Elasticsearch 的 `search_after` 本质也是这招。

### 两种写法对照表

| 写法 | 怎么定位下一页 | 中途插数据 | 适合场景 |
|---|---|---|---|
| `LIMIT offset, size` | 数「跳过几条」 | 会漏 / 会重复 | 前端翻页、数据不变的小表 |
| 游标分页（cursor） | 记住「上一条的 `(ts,id)`」 | 稳，不重不漏 | 数据同步、增量导出、CDC |

### 同步一页接一页的调用链

```
源库 --(WHERE (ts,id) < 游标)--> 取一批(≤1000)
  |                                   |
  |  记下本批最后一条 (ts,id) 作为新游标 |
  v                                   v
写入/处理目标库 <----------- 还有数据? 是 -> 用新游标再取一批
                                    否 -> 同步完成
```

---

## 三、一句线上提醒

游标能稳，前提是排序字段**单调 + 唯一**（时间可能重复，所以一定再拼上主键 id）。如果你非要用 offset 还想要一致性，只能加锁或快照读（snapshot），但性能扛不住——真要保一致，游标分页是唯一靠谱的选择。代码版演示见 `code/Demo.java`：实验一复现 offset 丢数据+重复，实验二 / 三证明游标分页一条不重不漏。
