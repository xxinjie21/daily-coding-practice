# 设计一个消息队列：收、存、发三步怎么落地

## ① 一句话题目（大白话）

让你从零设计一个消息队列（MQ），核心就三个字：**收、存、发**——生产者的消息要收得进来，存得不丢，消费者要拉得出去。面试官想听的是：这三步分别用什么手段做到高吞吐、低延迟、不丢消息。

## ② 为什么会有这个问题（生活比喻）

把 MQ 想象成**小区门口的快递柜**：

- 快递员（生产者）把包裹塞进柜子就走，不用等收件人（收）；
- 包裹在柜子里暂存，不会丢（存）；
- 收件人有空了自己扫码取件，一次取一个或一批（发）。

直接让快递员上门等收件人，就是「同步调用」——双方互相拖累。快递柜把双方解耦开，这就是 MQ 的价值。

## ③ 怎么做（五步，对应原题五条思路）

### 第 1 步：网络层用 Netty Reactor 多线程收消息

成千上万个生产者同时连进来，如果一个连接一个线程地等，线程全耗在「空等」上。
Netty 的 Reactor 模型像**银行大厅**：一个引导员（boss 线程）只负责迎客，客户坐下后由多个窗口（worker 线程）并行办理，IO 不阻塞。

```java
bootstrap.group(boss, worker)   // boss 1 线程 accept，worker 多线程读写
        .channel(NioServerSocketChannel.class)
        .childHandler(new ChannelInitializer<>() { /* 按行解码 + 转发给 broker */ });
```

### 第 2 步：topic 拆成多个 partition，按 key 哈希分散写

一个 topic（比如 `orders`）的所有消息堆一个队列，就是单车道——并发上不去。
Kafka 的做法是拆成多条**分区**（partition），相当于多车道。
发送时按 key 取哈希选车道：`Math.floorMod(key.hashCode(), 分区数)`。
好处是**同一个 key 永远进同一条分区**，顺序天然有保证。

### 第 3 步：内存 RingBuffer + 原子指针，异步刷 WAL

消息直接写数据库太慢。正确做法是**先写内存，再异步落盘**，中间靠 WAL（Write Ahead Log，预写日志）保命：

- 每个分区一块固定大小的环形数组（RingBuffer），加一个**原子指针** `AtomicLong`。
  `getAndIncrement()` 一步完成「占坑并拿号」，多个生产者同时写也不重号——这就是原题给的 `SimpleQueue` 思路；
- 写消息只动内存，几乎零成本；
- 后台守护线程每隔 200ms 把没落盘的消息批量追加进日志文件（`offset|message`），
  停服前再强制补刷一次——这就是「不丢消息」的底线。

```java
long produce(String message) {
    long offset = writePos.getAndIncrement();     // 原子占位，不重号
    ring[(int) (offset % ring.length)] = message; // 写环形数组槽位
    publishedPos = offset;                        // volatile 写，读者立即可见
    return offset;
}
```

### 第 4 步：消费用 Pull + offset，支持回溯重放

消费模型首选 **Pull（拉）** 而不是 Push（推）：消费者自己决定一次拉几条、什么时候拉，不会被生产速度压垮。
每条消息有一个 offset（分区内序号），消费者记住「我消费到哪了」，就是自己的进度。
想重放？把 offset 传 0 从头再拉一遍即可。

消费者组（group）的进度要落盘（Demo 里追加写 `offsets.log`），否则重启后又从第一条重刷。

### 第 5 步：重启恢复 = 扫 WAL + 读 offset

 broker 挂了重启，两样东西要从磁盘找回来：

1. **消息**：扫各个分区的日志文件，把 `offset|message` 读回内存 RingBuffer；
2. **消费进度**：读 `offsets.log`，恢复每个消费者组上次提交的 offset。

Demo 场景4 实跑验证：重启后查询 g1 的进度 = 2（重启前提交的值），从 offset 2 续拉只拿到新生产的消息。

## ④ 一条线上提醒

原题还提到**副本同步**（双写或 Raft，等两个节点落盘才返回成功）和 **ZooKeeper/Nacos 管路由元信息**——这两件套解决的是「多台 broker 不丢数据、互相发现」。
它们会明显拉高延迟和复杂度，**是否开启要看业务**：日志类可以容忍丢，支付类一台都丢不起。
Demo 聚焦单机核心机制，多机部分了解取舍即可。
