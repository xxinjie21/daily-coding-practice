# 五分钟内重复登录检测：用什么数据结构能一秒揪出「刚登过又登」的 QQ 号

## 一句话说清题目

一堆 QQ 号的登录记录不断涌进来，要立刻判断出「某个号在 5 分钟内登录了两次」。该用什么数据结构？

## 为什么会有这个问题

先看最容易想到的做法：拿一个 `HashMap`，键是 QQ 号，值是它上次登录的时间。

这就像**用一张纸登记每个客人的「最后一次进门时间」**。新客人来了，翻纸对照一下：上次进门距今不到 5 分钟？那就是重复登录。

问题是这张纸只记了「最后一次」。如果 QQ 1001 在 10:00、10:02、10:04 各登了一次，纸上的记录只会被反复覆盖，你**丢掉了中间过程**——风控想看「这 5 分钟里到底登了几次、几次算异常」，就查不出来了。

而且如果每次都往 map 里堆时间，数据会无限涨、还得定期清理，很别扭。

## 怎么做：只保留「窗口内」的记录

关键思路叫**滑动时间窗口**：每个 QQ 号只保存**最近 5 分钟内**的登录时间，更早的直接扔掉。新登录进来时，先扔旧的，再看还剩下几条。

打个比方：**给每个客人一个小本子，只记最近 5 分钟内的进门时间，写满 5 分钟的旧记录就撕掉**。新客人进门，先撕掉过期的，本子上还有字 → 说明他 5 分钟内来过，判定重复。

两种落地方式，按部署形态选：

| | 方案一：本地 Map + Deque | 方案二：Redis Sorted Set |
|---|---|---|
| 数据结构 | `Map<QQ号, Deque<时间戳>>` | `ZSET`，member 是登录流水，score 是时间戳 |
| 清过期 | 从队头 `pollFirst()` 踢掉 | `ZREMRANGEBYSCORE` 按分数删 |
| 判重复 | 队列非空 | `ZCOUNT` 数窗口内条数 |
| 适合 | 单机、量不大 | 多台机器共用一份数据（网关集群、风控） |

**为什么 Sorted Set 特别合适**：它天生按 score（也就是时间戳）排序，取某个时间区间的元素是 `O(log N)`，不用自己维护顺序。这正是「按时间窗口筛选」的天然数据结构。

单机版的判定逻辑（完整代码见 `code/src/main/java/Demo.java`）：

```java
static boolean isDuplicateLoginLocal(String qq, long now) {
    Deque<Long> times = userLogins.computeIfAbsent(qq, k -> new ArrayDeque<>());
    while (!times.isEmpty() && now - times.peekFirst() > WINDOW_MS) {
        times.pollFirst();            // 队头是最老的，过期就从这头踢
    }
    boolean duplicate = !times.isEmpty();
    times.addLast(now);               // 本次登录从队尾进
    return duplicate;
}
```

分布式版用 Jedis 真实调用 Redis，三步走：

```java
static boolean isDuplicateLoginRedis(Jedis jedis, String qq, long now) {
    String key = "login:qq:" + qq;
    jedis.zremrangeByScore(key, 0, now - WINDOW_MS);          // 1. 清掉 5 分钟前的
    jedis.zadd(key, now, now + "-" + seq.incrementAndGet());  // 2. 记下本次登录
    jedis.expire(key, 600);                                   // 3. 兜底过期
    return jedis.zcount(key, now - WINDOW_MS, now) >= 2;      // 4. 窗口内次数 >= 2 即重复
}
```

跑起来的样子（`docker compose up -d` 起 Redis 后 `mvn exec:java`）：

```
QQ 1001 在第 0s 登录 -> 首次登录
QQ 1001 在第 60s 登录 -> 重复登录！     ← 间隔 60 秒，命中
QQ 1002 在第 0s 登录 -> 首次登录
QQ 1002 在第 400s 登录 -> 首次登录      ← 间隔 400 秒 > 5 分钟，不算
Redis 中 QQ 1002 窗口内记录数 = 1（旧的 0s 记录已被 ZREMRANGEBYSCORE 清掉）
```

## 一句线上提醒

**同一个用户的多台机器登录，必须共用一份数据。** 本地 `HashMap` 只认自己这台机器上的登录记录，用户被负载均衡甩到另一台网关就漏判了——生产上要么用 Redis 的 ZSET 集中存，要么把登录事件统一投到风控服务里判。另外别忘给 key 设过期（`expire`），否则几千万个只登过一次的冷用户会把 Redis 内存撑满。
