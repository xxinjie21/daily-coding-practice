# JVM 内存分析与 OOM 排查：内存去哪了，怎么抓现行

> 原题：**111. 怎么分析 JVM 当前的内存占用情况？OOM 后怎么分析？**（来源：后端场景面试题）

## 一句话题目

线上服务内存越用越多，最后直接 `OutOfMemoryError` 崩了。**在它崩之前，我怎么看出苗头？崩了之后，我怎么知道是谁吃掉了内存？**

## 为什么会有这个问题

先说个生活场景。

你租了个房子（这就是 JVM 的**堆内存**，Java 对象都住在里面）。每天都有快递进来，也有垃圾要扔。好在有个免费保洁阿姨（**GC**，垃圾回收器），会定期上门把没人要的东西清走。

正常情况下，屋子再乱，阿姨来一趟就能恢复清爽。

出问题的情况是：**你把一堆没用的东西锁进柜子里，钥匙自己揣着**。阿姨看得见但不敢扔——万一你还要用呢？于是柜子越塞越满，屋子越来越挤，直到某天连快递都放不下了，房东直接把你轰出去（OOM，进程挂掉）。

这就是**内存泄漏**：不是 GC 无能，是你的代码一直攥着引用不撒手。

最常见的三种"柜子"：

| 柜子 | 例子 | 为什么危险 |
| --- | --- | --- |
| `static` 集合 | `static Map<String, User> cache = new HashMap<>()`，只 put 不 remove | static 变量的生命周期 = 整个程序，GC 永远不敢动 |
| 没关掉的资源 | 连接、流、线程池忘了 close/shutdown | 一个连接可能牵着一大串缓冲区 |
| 监听器/回调 | 注册了没反注册 | 注册中心攥着你的对象不放 |

所以排查的核心问题就两个：**现在内存什么状况？谁在占着？**

## 怎么做

### 第一步：看整体分布 —— `jstat -gc <pid>`

`pid` 就是进程号，用 `jps` 能查到。这条命令实时打出各内存区的用量和 GC 次数、耗时。

```bash
jstat -gc 12345 1000 30    # 每 1 秒采一次，连采 30 次
```

**关键是"连着看"，别只看一眼。** 单看一眼内存 60%，你根本不知道它是稳在 60% 还是正往上飙。一定要看趋势。

先认识几个抽屉（JVM 把堆切成几块分类放对象）：

- **Eden（伊甸区）**：新对象出生的地方，像"新生儿病房"。绝大多数对象活不过一次 GC。
- **Survivor（幸存区）**：从 Eden 活下来的对象暂住，像"观察病房"。
- **Old Gen（老年代）**：反复活下来的对象才搬进来，像"长期住户楼"。**排查泄漏主要盯这里。**
- **Metaspace（元空间）**：放类的信息，不在堆里。OOM 有时是死在这，别只盯着堆。

### 第二步：看堆的家底 —— `jmap -heap <pid>`

```bash
jmap -heap 12345
```

这条看堆的配置和使用率：最大能长到多大、现在用了多少、老年代占了百分之几。

**经验阈值：老年代使用率长期超过 70%，就该警惕了。** 为什么盯老年代？因为能搬进老年代的对象都是"反复活下来"的，正常业务对象（一个请求用完就丢）根本熬不到那儿。它一直涨，说明有东西被谁攥着。

### 第三步：判定是不是真泄漏 —— 看 Full GC 之后降不降得下来

这是全篇最重要的一句话：

> **内存涨了不可怕，Full GC 之后降不回去才可怕。**

业务高峰内存涨到 80% 很正常，一次 Full GC（把整个堆彻底清一遍）就降回 30% 了。但如果连着几次 Full GC，内存始终降不下来，那就是有东西被锁在柜子里了。

Demo 里做了 A/B 对照实验，两组分配同样多的内存，唯一区别是留没留引用：

```
[A 组 · 泄漏] 每轮分配 8MB 塞进 static 集合
ROUND    ALIVE_AFTER_GC(MB)    OLD_GEN(MB)
1                         8              9
2                        16             18
3                        24             26
...
6                        48             50      <- 一路往上爬

[B 组 · 正常] 每轮同样分配 8MB，但用完撒手
ROUND    ALIVE_AFTER_GC(MB)    OLD_GEN(MB)
1                         0              2
...
6                         0              2      <- 纹丝不动
```

中场还做了个证明：把 A 组的 static 集合 `clear()` 掉再 GC 一次，**老年代 50MB 立刻掉到 2MB**。可见 GC 一直都有能力回收，只是我们自己不撒手。

### 第四步：抓现行 —— `jmap -dump` + Eclipse MAT

确认是泄漏之后，抓一份堆快照（heap dump），把当时堆里所有对象存成文件：

```bash
jmap -dump:format=b,live,file=heap.hprof 12345
```

`live` 表示只抓存活对象，文件会小很多。

然后用 **Eclipse MAT**（一个免费的堆分析工具）打开。MAT 最有用的功能叫 **Dominator Tree（主导树）**，它回答一个问题：**"干掉这个对象，能顺带释放多少内存？"**

这里要分清两个概念：

| 概念 | 含义 | 书架比喻 |
| --- | --- | --- |
| **shallow size** | 对象自己占几个字节 | 书架本身没多重 |
| **retained size** | 干掉它能连带回收多少 | 搬走书架，上面 500 本书也跟着走 |

**看 shallow 永远找不到元凶，看 retained 一眼就能看到。** 一个 `HashMap` 对象自己才几十字节，但它挂着 100 万条数据。Demo 实验5 手写了个迷你版主导树，输出是：

```
OBJECT                    shallow(KB)     retained(KB)
SessionCache                        1           400001    <- 元凶
ConfigHolder                        1             2001
ThreadPool                        120             3120
```

三个对象 shallow 差不多，但 SessionCache 的 retained 是 40 万 KB。MAT 就是靠这个直接把它顶到第一行。

还有个细节：Demo 里的 `SharedDictionary`（50MB）被两个根同时引用，所以它不算进任何一方的 retained——**删掉其中一个引用它也不会消失**。MAT 里这种归到"共享"部分，也在提醒你：光断一处引用没用。

### 第五步：OOM 后怎么办 —— 提前埋好后悔药

**OOM 一发生进程就没了，什么线索都不剩。** 所以关键是提前加启动参数，让 JVM 在 OOM 那一刻自动抓一张快照：

```bash
-XX:+HeapDumpOnOutOfMemoryError
-XX:HeapDumpPath=/data/dumps
-Xlog:gc*:file=/data/logs/gc.log:time,uptime:filecount=10,filesize=50M
```

这三行**新项目上线第一天就该加上**，平时零成本，出事时救命。

GC 日志则能回溯 OOM 之前的征兆。日志长这样：

```
[41.902s][info][gc] GC(9) Pause Full (Ergonomics) 1900M->1810M(2048M) 733.118ms
                                                   ↑GC前   ↑GC后  ↑堆总大小
```

只看箭头右边那个数字（GC 后残留）随时间怎么变：

```
【疑似泄漏】1180 -> 1520 -> 1810 -> 1990    残留一路走高，且 FREED 越来越少 = 泄漏
【健康】    300  -> 312  -> 298             每次都能回落到低位 = 只是业务忙
```

Demo 实验6 用正则把这个规则写成了自动判定，十几行代码就能挂到监控上。

### 整个流程串起来

```
内存告警
   |
   v
jstat -gc  连看 30 秒 ------> 用量能降回去？ --是--> 只是业务忙，考虑调大堆
   |                                |
   |                               否
   v                                v
jmap -heap 看老年代 >70%?      判定为泄漏
   |                                |
   +--------------------------------+
                    |
                    v
        jmap -dump 抓快照（先摘掉负载均衡！）
                    |
                    v
        MAT 打开，按 retained size 排序
                    |
                    v
        第一行就是元凶，右键 Path to GC Roots 看是谁攥着它
```

## 两句提醒

1. **抓 dump 会 STW（Stop The World，全世界暂停）。** 几个 G 的堆可能卡住服务好几秒。线上一定要**先把这台机器从负载均衡里摘出来再抓**，不然排查动作本身就成了新的事故。

2. **不是所有 OOM 都是堆的问题。** `java.lang.OutOfMemoryError` 后面那句话才是重点：`Java heap space` 是堆满了；`Metaspace` 是类加载太多（常见于反射/动态代理生成类失控）；`unable to create native thread` 是线程建太多，跟堆一点关系没有——这种情况你把 `-Xmx` 调大反而更糟，因为留给线程栈的内存更少了。**先读完那行错误信息再动手。**
