# 大表在线加索引：给一亿条数据的大表加索引，怎么不把业务卡死

## ① 一句话题目（大白话）
一张已经有一亿条数据的大表，现在要给它加个索引（比如按 `user_id` 查得快一点），**怎么加才能不把线上业务卡死？**

## ② 为什么会有这问题（先讲个生活比喻）
给大表加索引，最笨的办法是直接 `ALTER TABLE ... ADD INDEX`。这就像给一本 **100 万页的字典重新排「拼音检字表」**——为了排这个表，你得把整本书从头到尾翻一遍。

翻的这几十分钟里，**谁都别想查这本字典**（表被锁住了），所有要读这张表的请求全得排队干等，业务直接瘫痪。一亿条数据的大表，这么干可能要锁好几个小时。

所以问题的本质不是「怎么加索引」（那一行 SQL 谁都会写），而是 **「加索引的过程中，怎么让线上业务还能正常读写」**。

## ③ 怎么做（两种办法对比）

| | 直接 `ALTER TABLE` | 在线改表（`gh-ost` / `pt-osc`） |
|---|---|---|
| 做法 | 一条 SQL 让 MySQL 扫全表建索引 | 建一张带索引的「影子表」，后台慢慢搬数据，最后秒切 |
| 对业务影响 | 期间锁表，读写全卡（小时级） | 全程几乎无感，只在最后做一次毫秒级切换 |
| 适合场景 | 小表、能停机维护时 | 大表、不能停的线上业务 |
| 难易 | 一行命令 | 用成熟工具，自己几乎不用写代码 |

**真正靠谱的做法是「影子表方案」**，这也是 `gh-ost`、`pt-online-schema-change` 这类工具的底层原理。把流程拆开看，一共五步（工具都帮你自动做了，理解这五步就懂了它在干嘛）：

1. **建影子表**：新建一张结构跟原表一模一样、但**已经带好新索引**的空表。相当于先准备好那本排好拼音检字表的新字典。
2. **后台搬历史数据**：把原表的一亿条数据慢慢拷进影子表，顺手把索引建好。这步是后台慢慢扫，**不锁原表**，业务照常跑。
3. **搬运期间的变更记下来**：搬数据要好一阵子，这期间业务还在不停写新数据。这些「新变更」靠 MySQL 的 **binlog**（可以理解为数据库自己的「流水账本」）先记下来，保证一条不丢。
4. **追平**：历史数据搬完后，把 binlog 里这段时间积攒的增量，重放到影子表上，让影子表和原表变得一模一样。
5. **切流（改名）**：最后只做一个很快的「表改名」操作——业务从此读这张带索引的影子表。这一步是毫秒级，用户基本无感。

> 技术名词小卡片：**binlog**（binary log）是 MySQL 记录「谁改了什么」的日志，像超市收银条的存根。主从同步、数据恢复、还有我们这里的在线加索引，全靠它。

如果你不想用工具、非要自己撸，思路也一样：建新表 → 加索引 → 导数据 → 双写同步 → 切流 → 下线旧表。但这堆脏活累活工具都封装好了，**生产环境别自己手写，直接用 `gh-ost`**。它的命令其实就一行：

```bash
gh-ost \
  --host=localhost \
  --database="test" \
  --table="large_table" \
  --alter="ADD INDEX idx_user(user_id)" \
  --execute
```

它会在后台默默干活，还能看进度、限速、随时暂停，控制得很细。

> 补充：MySQL 5.6 之后自带「在线 DDL」，加索引默认走 `INPLACE` 模式，不重建整张表。但**哪怕这样，大表还是要扫一遍聚簇索引来建二级索引**，该耗时还是耗时，所以大表依旧推荐影子表方案。

## ④ 一句线上提醒
**索引不是越多越好**——每多一个索引，写数据就慢一分。先拿慢查询日志找出最该加的那个再加；并且这种生产操作，**一定先在备库或测试环境演练一遍**，出一次问题运维能记你一年。
