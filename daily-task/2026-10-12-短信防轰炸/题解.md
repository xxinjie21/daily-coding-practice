短信验证码如何防止被恶意轰炸？如果有人不断请求发送验证码，你会如何限制？

## 一句话说清

「短信轰炸」就是有人拿脚本不停地调你的「发送验证码」接口，让你的短信费哗哗地烧、还把真实用户挤得发不出短信。
防它不能只靠一句 `if (太频繁) 拒绝`，得**层层设卡、把攻击成本抬高**。

## 为什么光靠业务逻辑拦不住

想象你家楼下有个公用电话，谁都能打。有人拿它一秒钟拨 100 个号，你站在旁边喊「别打了」是没用的 —— 他根本不理你。
短信接口就是那部公用电话：它是**公开的、不需要登录的**，脚本一秒钟能请求上千次。
所以思路必须是：

> 不指望「拦住那一个人」，而是**给每一次请求加门槛**，让机器脚本很难批量通过，让真人基本无感。

## 怎么做：请求进来过四道闸门

按顺序校验，任何一道不过就拒掉。`code/src/main/java/Demo.java` 里的 `requestSms()` 就是这个顺序：

**闸门1 · IP 黑名单** —— 已经被封的 IP，后面的检查全都不用做了，直接拒。

**闸门2 · 图形验证码票据** —— 用户点「发送验证码」前，先过一次滑块/图形验证码（人点一下就行，脚本很难批量过）。
服务端验证通过后，给这个手机号下发一张「一次性票据」，发送接口必须带着它才能过。
这里用 `GETDEL` 取票据，**取和删是一步完成的**，脚本没法拿同一张票据反复重放：

```java
String ticketKey = "sms:captcha:" + phone;
if (!"pass".equals(jedis.getDel(ticketKey))) {
    return new Result(false, "请先完成图形验证码");
}
```

**闸门3 · 手机号三级频控** —— 同一个号，1 分钟最多 1 次、1 小时最多 5 次、1 天最多 10 次。
这就是最核心的一层，用的是 Redis 的 `INCR`（自增，多人同时来也不会算错）：

```java
static long countOnce(Jedis jedis, String key, int ttlSeconds) {
    long count = jedis.incr(key);
    if (count == 1) {
        jedis.expire(key, ttlSeconds);   // 只在第一次设过期
    }
    return count;
}
```

注意那个 `if (count == 1)`：**过期时间只设一次**。如果每次请求都 `expire` 一遍，等于把窗口无限往后推，
用户一直点就一直不清零，那就永远拦不住了。

**闸门4 · IP 计数封禁** —— 攻击者可以换手机号，但往往来自同一批 IP。
所以再按 IP 计数，10 分钟内超 5 次就直接把 IP 拉黑 10 分钟：

```java
long ipCount = countOnce(jedis, "sms:ip:count:" + ip, 600);
if (ipCount > 5) {
    jedis.set(banKey(ip), "1", SetParams.setParams().ex(600));
    return new Result(false, "IP " + ip + " 请求过于频繁，已封禁 10 分钟");
}
```

四道闸门的效果（实测输出，见 `Demo.java` 的四个场景）：

| 场景 | 结果 |
|---|---|
| 同一手机号 1 分钟内连点 3 次 | 只有第 1 次发出，后 2 次被闸门3 拦下 |
| 没过图形验证码直接发 | 被闸门2 拦下：「请先完成图形验证码」 |
| 同一 IP 换 6 个手机号刷 | 前 5 个放行，第 6 个触发封禁，之后再发直接被闸门1 拒 |
| Java 版 vs Lua 版计数（7 次、阈值 5） | 两边计数、判定、TTL 完全一致，第 6 次起都拒绝 |

## 一个容易踩的坑：`INCR` 和 `EXPIRE` 是两条命令

上面 `countOnce()` 的写法有个极小的窗口：万一 `INCR` 执行完、`EXPIRE` 还没执行，进程就被 kill 了，
这个 key 就**永远不过期**，那个手机号从此被永久限死。所以 `Demo.java` 里另外用真实 Lua 写了一份原子版并做了交叉验证：

```java
String script = """
        local count = redis.call('INCR', KEYS[1])
        if count == 1 then
            redis.call('EXPIRE', KEYS[1], ARGV[1])
        end
        return count
        """;
long count = (Long) jedis.eval(script, 1, key, String.valueOf(ttlSeconds));
```

Redis 执行 Lua 是单线程原子的，`INCR` 和 `EXPIRE` 中间不可能被打断。**生产上直接用这一版。**

## 一句提醒

这四道闸门是**叠加**的，不是四选一：闸门1、4 挡批量 IP，闸门2 挡自动化脚本，闸门3 挡单号滥用。
真实系统里再补一条「新设备首次请求 / 短时间内切换大量手机号」的行为风控（如网易易盾那类），基本就够用了。
另外别忘了**给短信服务商侧也配上每日预算上限**——万一真被绕过，至少不会一夜之间把预算烧穿。
