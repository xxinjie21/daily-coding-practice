# 接口变慢排查：一条链路怎么找出慢在哪

> 一句话版本：一个接口从用户点下去到结果回来，中间要路过网关、应用、缓存、数据库、第三方服务……任何一站堵了，用户都只感觉到一件事——**慢**。排查就是"拿着秒表，沿着这条路一站一站量，看谁最拖"。

---

## 一、先看个比喻：食堂打饭为什么慢？

你去食堂打饭，排了 20 分钟。原因可能是：

- **窗口太少**（资源不够，机器 CPU 打满）
- **阿姨手慢**（应用代码里有个笨循环）
- **前面那个人刷卡刷不上**（外部依赖：支付/第三方接口卡住）
- **菜没了，阿姨跑去后厨现做**（缓存没命中，只能回数据库现查）

你不会一上来就骂阿姨手慢吧？得先**看队堵在哪**。

接口变慢完全一样：**它不是"一个问题"，而是"系统某个环节亮了红灯"**。所以排查的核心不是猜，而是**分层测量**。

---

## 二、一次请求都路过哪些站？

```
用户点击
   │
   ▼
[网关] 限流 / 鉴权            ← 第 1 站：可能被限流、鉴权慢
   │
   ▼
[应用服务] 本地计算 / 业务逻辑  ← 第 2 站：笨代码、死锁、GC 停顿
   │
   ├──────────► [Redis 缓存]   ← 第 3 站：缓存击穿（key 同时过期 / Redis 挂了）
   │
   ├──────────► [MySQL 数据库] ← 第 4 站：慢 SQL、没索引、连接池打满（最常见！）
   │
   └──────────► [第三方 HTTP]  ← 第 5 站：对方抖动，你没设超时就陪着一起死
```

**排查的本质就是：把这 5 站各自的耗时记下来，谁占大头就查谁。**

---

## 三、原因逃不开这四类

| 类别 | 常见表现 | 典型凶手 |
|---|---|---|
| **应用代码** | 单次调用就慢，CPU 高 | 慢 SQL（DB 占 80% 时间）、循环里查库、死锁、大对象序列化 |
| **外部依赖** | 平时正常，突然全站卡死 | Feign / RestTemplate **默认不设超时**，对方一抖，线程池打满，整个应用堵死 |
| **中间件瓶颈** | 突发性雪崩 | 缓存击穿：Redis 挂了或热点 key 过期瞬间，请求全直奔数据库 |
| **基础设施** | 周期性毛刺 | Full GC 频繁（间隔 < 10 分钟要警惕内存泄漏）、CPU 打满、网络/磁盘 IO、机器负载高 |

---

## 四、排查步骤：从全局往下钻，别一上来翻代码

### 第 0 步：先看四个大盘指标

**CPU、RT（响应时间）、QPS（每秒请求数）、错误率**。

这四个里有两个同时异常飙升，再往下钻。一上来就翻代码，等于没看地图就钻胡同——**盲人摸象**。

### 第 1 步：用 APM 看链路，定位是哪一站

SkyWalking / Prometheus 这类工具会给你画出一张"火焰图/调用链"，直接告诉你：
哪个服务 → 哪个接口 → **甚至哪一行代码**耗时突增。

如果发现数据库那一格占了大部分时间（真实线上经常是 80%，本地 Demo 实测是 54%），
那问题多半就是 SQL 慢查询，加个索引可能就解决了。

### 第 2 步：按大头分别下钻

| 哪一站慢 | 怎么查 | 常用工具 |
|---|---|---|
| 数据库段 | 慢查询日志 → `EXPLAIN` 看有没有走索引 | 慢日志、pt-query-digest、Arthas |
| 外部调用段 | 查对方响应时间 + 看自己有没有配超时熔断 | Sentinel / Hystrix、链路追踪 |
| 本地代码段 | 定位到具体方法的耗时 | **Arthas `trace` 命令**（能看到方法内部每一步花了多久） |
| 周期毛刺 | 看 GC 是否频繁 | `jstat -gc`、GC 日志、Arthas `dashboard` |
| 直接卡死不动 | 查线程是不是互相锁住了 | `jstack`，看到 `Found one Java-level deadlock` 就实锤了 |

### 第 3 步：对症下药

- **外部依赖**：配超时 + 熔断降级。这是**最该做、也最容易被漏掉**的一条。
- **中间件**：本地缓存兜底，Redis 挂了也不至于把数据库打死。
- **基础设施**：GC 频繁先查内存泄漏（对象该放没放）；CPU 高看是不是在计算密集型逻辑。

> 代码演示见 `code/Demo.java`：6 个实验分别演示"链路耗时怎么拆""慢 SQL 加索引前后差多少""不设超时怎样拖死整个应用""缓存击穿怎么兜底""死锁长什么样以及怎么自动发现""为什么平均耗时正常但用户还是喊慢"。

## 五、一句提醒（三个最容易踩的坑）

1. **别一上来就查代码。** 先看 CPU / RT / QPS / 错误率四个大盘，两个异常再往下钻。
2. **平均耗时正常 ≠ 没问题，要看 P99。** 1000 次请求里 990 次 2ms、10 次 800ms，平均才 10ms，看着挺好——但那 10 个用户感受到的是 800ms。GC 停顿、偶发慢 SQL 都是这种"毛刺"，平均值会把它们抹平，**P99 / P999 才是真实用户体验**。
3. **调第三方一定要设超时。** Feign 和 RestTemplate 默认是没有超时时间的，对方要是 30 秒不回，你的线程就陪着等 30 秒；几十个请求一来，线程池全被占满，**连跟这个第三方毫无关系的接口也一起堵死**。配超时 + 熔断，是投入最小、救命最大的一条。

## 附：死锁为什么会让接口"变慢"到卡死

死锁（两个线程互相握着对方要的锁）是"应用代码"类原因里最极端的一种——它不是慢，是**永久卡住**。
产生需要四个条件同时满足：**互斥、占有并等待、不可抢占、循环等待**。

只要让两个线程**以相反的顺序**去抢两把锁，就能稳定触发：

```
线程1：先拿 lockA → 再要 lockB
线程2：先拿 lockB → 再要 lockA
结果：线程1 等 lockB，线程2 等 lockA，谁也不松手 → 死锁
```

JVM 不会主动干预这种等待。排查靠 `jstack`，它会直接打印 `Found one Java-level deadlock`。
（代码里用 `ThreadMXBean.findDeadlockedThreads()` 做了程序版自动检测，见 `Demo.java` 实验 5。）
