# 请求耗时优化：一条 1 秒的接口，怎么压到毫秒级

## 一句话说清

一个接口要等 1 秒才返回，想压到 1 毫秒，靠单一手段是做不到的 —— 得从**网络、计算、存储、架构**四层挨个把瓶颈敲掉。

## 为什么会有这 1 秒

想象你点了一份外卖套餐，里面有主食、配菜、饮料、甜点，分别在四个窗口取。

- 你**一个一个窗口排队**，每个窗口 250ms，四个下来就是 1 秒 —— 这就是"串行调用下游"。
- 而且每个窗口还要**重新排一次队**（每次请求都建一次连接、查一次库），时间全耗在"等"上。

接口慢，九成不是 CPU 算得慢，而是**在等别人**：等网络、等数据库、等下游服务。所以优化的本质是：**把等待变短、把等待并行、把等待直接省掉**。

## 怎么做：四层依次击破

| 层 | 问题 | 手段 | 效果 |
|---|---|---|---|
| 网络层 | 跨机房 RTT 20~50ms，HTTPS 握手 3 次往返 | CDN / 边缘节点、长连接复用、HTTP/2 多路复用 | 建连开销从几十毫秒降到接近 0 |
| 计算层 | 一个 for 循环查 10 次库，纯等 | 批量查询、`CompletableFuture` 并行、响应式编程 | 多次等待合并成一次 |
| 存储层 | 数据库一次主从延迟就 10~50ms | 多级缓存：本地 Caffeine（<100μs）→ Redis（1~2ms）→ 才回源 DB | 高频读几乎不碰数据库 |
| 架构层 | 复杂逻辑现算 | Flink 预计算特征、限流（Sentinel）、降级、熔断 | 接口只读结果，不被雪崩拖慢 |

**注意顺序**：先做最省事、收益最大的（缓存 > 并行 > 换网络 > 改架构）。别一上来就上响应式编程 —— 学习成本高，不是所有场景都值得。

## 代码里演示了哪两层

`code/src/main/java/Demo.java` 用「商品详情要凑 4 份数据」这个场景，把**计算层**和**存储层**两招跑给你看：

```java
// 路线2：四份数据互不依赖，丢线程池并行取 —— 总耗时约等于最慢的那一个
CompletableFuture.supplyAsync(() -> slowSource(key), pool)

// 路线3：三级取数，越靠前越快，命中就不碰网络
String value = localCache.getIfPresent(key);          // 一级：本地，几十微秒
if (value == null) {
    value = jedis.get(key);                           // 二级：Redis，1~2ms
    if (value == null) {
        value = slowSource(key);                      // 三级：回源，最慢
        jedis.setex(key, 30, value);                  // 回填 Redis
    }
    localCache.put(key, value);                       // 回填本地
}
```

跑一遍能看到耗时一路往下掉：**串行 ≈ 1000ms → 并行 ≈ 250ms → 冷缓存 ≈ 250ms → 热缓存几微秒**。

先起 Redis 再跑：

```bash
docker compose -f code/docker-compose.yml up -d
```

## 一句提醒

**缓存是拿一致性换速度，别忘了给它设过期时间和失效策略。** 数据改了却不删缓存，用户看到的就是旧数据 —— 提速的前提是结果还对。另外，热点 key 别全压在一台 Redis 上，那会从"慢"直接变成"挂"。
