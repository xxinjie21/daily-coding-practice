# 数据库不停服迁移：一边跑业务，一边把数据搬到新库

## 一句话说清

线上数据库要换（换机器、换库、换表结构），但业务**一秒都不能停**，怎么把数据安全搬过去？答案是：**双写 + 边搬边追 + 比对修复，最后悄悄把读切过去**。

## 为什么会有这个问题

想象一栋老房子要整体搬到新房子，但住户还在里面正常生活。

- 你不能把人赶出去再搬（= 停服）；
- 也不能只搬一次就走，因为人还在进进出出、家里东西还在变（= 业务还在写数据）。

所以只能：**先在两个房子都放一套东西（双写），慢慢把老房子已有的家当搬过去（全量迁移），新添的东西也同步跟过去（增量追平），搬完清点一遍看有没有漏（数据比对），确认没漏再让住户正式搬到新房子（切读），最后老房子彻底停用（下线双写）。**

## 怎么做：六步走

| 步骤 | 做什么 | 一句话理解 |
|---|---|---|
| ① 结构兼容改造 | 老库、新库表结构要能共存 | 新库多加了字段，必须给默认值，否则老代码双写时会报错 |
| ② 开启双写 | 代码同时写老库和新库，**读仍只读老库** | 新库此时是「影子库」，出问题也不影响用户 |
| ③ 历史迁移 + 增量追平 | 全量搬历史数据，再按 `update_time` 水位追新产生的增量 | 真实场景用 Canal 监听 binlog 实时追，效果一样 |
| ④ 数据比对与修复 | 抽样比对两边数据，不一致的补上 | 双写不是原子的，这一步是兜底 |
| ⑤ 切读流量 | 确认一致后，把读请求切到新库 | 用户无感，页面照常打开 |
| ⑥ 下线双写 | 读稳定后，只写新库，老库归档 | 收工 |

**关键点：①~④ 阶段读一直走老库**，所以哪怕新库还没搬完、有脏数据，用户也看不到——这就是「不停服」的本质。

### 结构兼容改造（为什么必须先做）

新库多了一个 `email` 字段，如果写成 `NOT NULL` 又没默认值，老代码双写时只写老库那几列，插入新库就会直接失败。所以：

```sql
-- 新库多出来的字段，一定要带默认值
email VARCHAR(64) NOT NULL DEFAULT ''
```

### 双写为什么不是原子的

两个库是两个独立连接，只能各自 `commit`，做不到「要么都成功、要么都失败」。所以万一中间出错（比如异步发消息丢了），就会出现「老库有、新库没有」的行——这正是第 ④ 步必须存在的原因。

### 数据比对怎么做

真实场景用 DataDiff 这类工具抽样比对。代码里用更朴素的真实 SQL：先比「行数 + 关键字段的 CRC32 校验和」，再用一条跨库 JOIN 把不一致的行挑出来。

```sql
-- 校验和：两边一样，数据基本就一致
SELECT COUNT(*) c, COALESCE(SUM(CRC32(CONCAT_WS('#',id,name,phone,status))),0) s FROM t_user;

-- 挑出不一致的行：老库有、新库没有，或关键字段对不上（真实跨 schema JOIN）
SELECT o.id FROM demo.t_user o LEFT JOIN demo_new.t_user n ON o.id = n.id
WHERE n.id IS NULL OR n.name <> o.name OR n.phone <> o.phone OR n.status <> o.status;
```

挑出来后，用老库的值覆盖新库，差异就补齐了。

## 跑一遍看看

先起好 MySQL 容器（宿主机 3307，root/root）：

```bash
cd code && docker compose up -d
```

再跑演示（完整代码见 `code/src/main/java/Demo.java`）：

```bash
mvn -q exec:java
```

实测输出（老库 `demo`、影子新库 `demo_new` 在同一个 MySQL 实例里）：

```
== ① 结构兼容改造 ==
老表 5 列，新表 6 列（多 email，NOT NULL DEFAULT ''），双写不会因缺字段失败

== 准备：老库预置 5 条历史数据 ==
老库现有 5 行

【双写前】读 1003 走老库 -> user1003 / 13800000003
== ② 开启双写 ==
老库 8 行，新库 2 行（1008 只在老库）

【双写中】读 1006 仍走老库 -> user1006 / 13800001006
== ③ 历史迁移 + 增量追平 ==
全量搬历史数据 8 行
追增量 3 行（含只在老库的 1008），新库现有 8 行

== ④ 数据比对与修复 ==
比对校验：老库[行数=8 校验和=23047124006]  新库[行数=8 校验和=19829560255]
查出不一致的行 id = [1003]
修复后：老库[行数=8 校验和=23047124006]  新库[行数=8 校验和=23047124006]
再次比对不一致行 = []

== ⑤ 切读流量 ==
【切读后】读 1003 走新库 -> user1003 / 13800000003
== ⑥ 下线双写 ==
只写新库 1009，新库现有 9 行，老库保持归档不再写入

迁移完成：业务全程没停过机。
```

可以看到：双写阶段新库只有 2 行、老库 8 行，但读一直走老库，业务完全正常；比对时揪出 `1003` 不一致并修复；切读后从新库读到的值也对得上。

## 一句提醒

**每一步都要有监控和回滚方案**。最怕的是搬到一半出错导致两边数据不一致——所以第 ④ 步的比对不能省，必要时还要用 Canal 监听 binlog 做**反向补偿**（把新库的正确值倒回老库）。另外切读别一次性全切，先切 1% 观察一阵子再逐步放大，比「一刀切」安全得多。
