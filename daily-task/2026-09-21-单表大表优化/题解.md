# 单表数据量很大怎么优化（先不谈分库分表）

## 一句话说清

一张表塞了几千万行数据，查询越来越慢、写入也越来越慢。在不拆库拆表的前提下，怎么把它救回来？

## 为什么会有这个问题

把数据库的表想象成一个**仓库**：

- 仓库里只有 100 件货的时候，你随便走两圈就找到了。
- 塞到 5000 万件，货架排到几公里长，找一件货得走半天；每进一批新货，还得把货架重新整理一遍，所以写入也变慢了。

这就是「单表数据量大」的本质：**数据膨胀之后，查询要扫的行数变多，写入要维护的索引也变多，两头都变慢。**

注意一个前提：几万、几十万行的时候，你几乎感觉不到问题；**真正开始疼，通常是数据到了千万级。**

## 怎么做（五招，从便宜到贵）

先看整体思路，再逐条解释：

| 招式 | 一句话 | 主要救什么 |
| --- | --- | --- |
| 索引要精 | 让查询走索引，别全表扫；但索引别乱加 | 查询慢 |
| SQL 要省 | 别 `select *`；翻页别用大 offset | 查询慢 |
| 大字段拆出去 | 简介、长文本单独放一张扩展表 | 查询慢（IO 大） |
| 冷热数据分离 | 老数据归档，主表只留近期热点 | 查询 + 写入都变快 |
| 读写分离 | 写走主库，读走从库，压力分摊 | 并发扛不住 |

### 1）索引设计要精准

「索引」你可以理解成**书的目录**：想找某一章，先翻目录直接跳过去，而不是从第一页读到最后。

- 目标是**让查询走索引**，避免全表扫描（等于把整本书读一遍）。
- 但索引不是越多越好：**每加一个索引，写入时就要多维护一棵 B+ 树**（B+ 树可以粗略理解成"排好序的多层目录"），插入会变慢、占空间也变多。
- MySQL 的二级索引查完还要**回表**：先按二级索引找到主键，再拿主键去主键索引里取整行数据，等于"先在目录里查到页码，再翻到那一页"。所以**主键尽量用自增整型**，主键小、回表就便宜。

### 2）SQL 要避免 select *，翻页别用大 offset

- `select *` 会把整行所有字段都搬回来（包括你根本用不到的大字段），网络和 IO 都是浪费。**只查需要的字段。**
- 分页别写 `limit 1000000, 10`。这句话的意思是"先数出前 100 万行丢掉，再取 10 行"——**前 100 万行是白扫的**。
- 正确姿势是**游标翻页**：记住上一页最后一条的 id，下一页直接

  ```sql
  where id > 上一页最后的id order by id limit 10
  ```

  因为 id 上有索引，数据库能**直接跳到起点**，不用再数那 100 万行。

### 3）大字段要拆出去

比如用户表里塞了个 `text` 存"个人简介"。

问题是：数据库是按**行**存数据的，一行里有大字段，这一行就特别"胖"。哪怕你只想查用户昵称，读取时也可能把这一大坨简介一起搬进来，白白拖慢速度。

做法：**单独建一张扩展表**（比如 `user_profile`），用用户 id 关联，把大字段"拎出去"。主表保持瘦，日常查询就快。

### 4）冷热数据分离

订单表里，**最近 3 个月**的天天被查，**一年前**的基本没人看。

那就把它们分开：老数据**归档**到另一张历史表，或者定期搬到 Hive 这类大数据平台；主表只留热点数据。

这样主表行数少了一大截，查询快、写入也快。冷数据不是不要，只是放到"冷库"里，需要时再查。

### 5）读写分离

写操作走**主库**，读操作走**从库**，主库把数据同步给从库（MySQL 主从复制）。

一台机器扛不住的读压力，分给三台从库，就是三倍。落地时常用 ShardingSphere 这类中间件帮你自动做读写路由（SQL 发给谁，中间件替你决定）。

**注意坑**：主从同步有延迟，刚写完立刻去从库读，可能读不到最新数据（叫"主从延迟"）。对一致性要求高的读（比如下单后立刻查订单状态），要强制走主库。

## 一句提醒

这五招有个共同点：**都是让"数据搬运量"变少**——少扫行、少搬字段、少存数据。所以真正的判断标准是：**这条 SQL 到底扫了多少行、搬了多少字节？** 用 `explain` 看一眼扫描行数，比凭感觉优化靠谱得多。

另外，这些手段是**延长寿命**，不是**根治**。单表真的到了几亿行，分库分表迟早要上；先做这五招，是为了让那一天来得晚一点，也让你有数据支撑去论证"确实该拆了"。
