# 线上踩坑点与同类场景拓展

## 一、线上真实踩坑点

### 1. 用 `String.hashCode()` 当哈希函数，环上节点扎堆
Java 自带的 `hashCode()` 对相似字符串（如 `10.0.0.1`、`10.0.0.2`）算出的值很接近，节点在环上挤成一团，数据严重倾斜——某台机器扛了 80% 流量被打挂。**正确姿势**：用 MD5（Ketama 做法）或 MurmurHash 这类"打散能力强"的哈希函数。MurmurHash 大白话：一种算得快、结果又足够随机的哈希算法，Guava 里就有现成的。

### 2. 虚拟节点数量拍脑袋设太少
每台只放三五个虚拟节点，均匀性跟没放差不多。经验值是**每台物理机 100~200 个**。也别无脑设几万个——环（TreeMap）本身会变大，节点上下线时增删虚拟节点的开销也变大。

### 3. 节点宕机后没有及时摘除
一致性 Hash 只解决"数据映射"，**不解决"节点健康检查"**。挂了的节点还留在环上，路由过去全是失败。要配合心跳检测：发现节点失联，调用 `removeNode` 把它的虚拟节点全部摘掉，流量自动顺时针滑给下一个节点。

### 4. 扩容后忘了"该迁移的数据其实没迁"
一致性 Hash 让"只有一小段 key 换了归属"，但**缓存场景下这段数据并不会自动搬家**——新节点上就是没有这些数据，等于这部分缓存未命中，会回源数据库。量大时（比如一次加很多台）也可能造成明显的回源尖峰。缓解办法：**分批扩容**（一次加一台，间隔观察）、低峰期操作、或者做**缓存预热**（提前把热点数据灌进新节点）。

### 5. 各客户端哈希实现不一致，同一个 key 各找各的节点
多语言团队常见坑：Java 服务和 Go 服务各自实现了一致性 Hash，但哈希函数、虚拟节点命名规则不一致，导致同一个 key 在两边路由到不同机器，缓存写了读不到。**约定必须统一**：哈希算法、虚拟节点命名格式（如 `ip:port#VN{i}`）、节点标识写法，最好沉淀成公共库。

### 6. 机器配置不同却平均分配
新采购的机器性能是老机器两倍，却分同样多的数据，老机器先扛不住。用**加权虚拟节点**：性能强的机器多放虚拟节点（如老机器 100 个、新机器 200 个），流量按能力分配。

## 二、同类场景拓展

一致性 Hash 的本质是"**在成员经常变动的集群里，让 key 到成员的映射尽量稳定**"。凡是符合这个特征的场景都能用：

1. **分布式缓存分片**（本题场景）：Memcached 客户端（SpyMemcached/Ketama）、Twemproxy 代理层，都是标准应用。
2. **负载均衡的会话保持**：Nginx 的 `hash $cookie_uid consistent;`（ketama 一致性哈希），同一用户始终打到同一台后端，后端扩缩容时也只有少量用户换机器。
3. **消息队列 / 任务分发**：把任务按业务 key 一致性哈希到固定 worker，保证同一订单的消息总被同一个消费者处理（局部有序），worker 扩缩容影响面小。
4. **分布式存储**：Cassandra、DynamoDB 的数据分区就是一致性哈希环（加了更精细的 token 分配策略）。
5. **CDN / 边缘节点选路**：同一个资源 URL 稳定映射到同一台边缘节点，提高该节点上的缓存命中率。

## 三、和 Redis Cluster 槽位方案的对比（面试加分点）

Redis Cluster 没用一致性 Hash，而是**预分 16384 个槽**：`slot = CRC16(key) % 16384`，再把槽分给节点。好处是：
- 迁移粒度是"槽"，**可以人为指定把哪些槽挪到哪台机器**，运维可控性更强；
- 槽和节点的对应关系是显式元数据，方便查看和管理。

两者思想同源——都是**加一层间接映射，让"节点变化"不直接冲击"key 的归属"**。面试时能把这层共性点出来，比单纯背算法更出彩。

## 四、一句话总结

普通 Hash 取模是"全班按人数重新分座位，人数一变全员大挪移"；一致性 Hash 是"按固定圆桌就座，来人/走人只影响邻座"；虚拟节点则是"每人多占几个分散的座位，保证谁也不会独占一大片"。
