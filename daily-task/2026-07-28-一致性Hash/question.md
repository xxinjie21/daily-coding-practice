## 9. 分布式缓存中，如何实现一致性 Hash 算法？相比普通 Hash，它解决了什么问题？

### 这道题在问什么（大白话版）

想象你开了一家连锁快递驿站，一共有 3 个网点（3 台缓存服务器），每个包裹（缓存数据）按"取件码"分配到某个网点存放。

最直观的分法是：**取件码 % 3**（普通 Hash 取模）——取件码除以 3 看余数，余 0 去 1 号网点，余 1 去 2 号网点，余 2 去 3 号网点。平时相安无事。

但某天你新开了 1 个网点，变成 4 个，规则变成 **取件码 % 4**。灾难来了：**几乎所有包裹的"应存网点"全变了**！客户拿着老取件码去新规则算出的网点，发现包裹不在（缓存未命中），只能全部回总仓（数据库）重新调货——总仓瞬间被挤爆，这就是所谓的"缓存集体失效、数据库被击穿"。

> **缓存击穿/雪崩**：大白话就是"挡在数据库前面的那层货架突然全空了，所有请求直接砸到数据库头上，数据库可能当场被压垮"。

**这道题问的就是**：有没有一种分配方案，让"增加或减少网点"时，只有一小部分包裹需要挪窝，其他包裹原地不动？

答案就是**一致性 Hash（Consistent Hashing）**。原题给出的核心思路是：

1. 把 0 到 2^32-1 这些数字首尾相接，围成一个**圆环**（Hash 环）；
2. 把每台缓存服务器（按 IP+端口 做哈希）"钉"在环上的某个位置；
3. 数据来了，对 key 做哈希也落在环上，然后**顺时针**走，遇到的第一台服务器就是它的归宿；
4. 增删节点时，**只影响环上相邻的一小段区间**，其他数据不动；
5. 为了防止服务器在环上"扎堆"导致某台机器累死（数据倾斜），再给每台物理机分身出多个**虚拟节点**，均匀撒在环上。

实际工业界的 Memcached 客户端（Ketama）、Twemproxy 等都用这套算法；Redis Cluster 虽然用的是"槽位分片"，但思想是同源的。

- 增删节点时为什么只影响一小段数据？
