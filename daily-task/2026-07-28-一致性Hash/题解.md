# 一致性 Hash：缓存服务器加一台，为什么不用把所有数据搬一遍

## ① 一句话题目
分布式缓存里，服务器数量一变（加机器或宕机），怎么让数据还找得到、而且只挪动很少一部分，而不是全乱套？

## ② 生活比喻
普通 Hash 取模像"按学号尾数分班"：尾数 0-2 去一班、3-5 去二班。一旦班里多一个人，尾数规则全变，全班得重新排座位（数据全错位 = 缓存全失效 = 请求全砸数据库）。
一致性 Hash 像"按固定圆桌就座"：来人/走人只影响邻座，其他人大体不动——新开一家快递驿站，只有附近两栋楼的住户改去新驿站，全小区其他人取件地点不变。

## ③ 怎么做
核心就一句话：把服务器和数据都哈希到一个首尾相接的"环"上，数据顺时针找第一台服务器；加机器只动邻座，别人原地不动。

主要步骤（Demo.java 演示的主方案）：
1. 把 0~2^32-1 首尾相接围成环，服务器哈希到环上成为"节点"。
2. 数据 key 也哈希到环上某个位置。
3. 从该位置沿顺时针走，碰到的第一台节点就归它管。
4. 走到环尾还没节点就绕回开头（这就是"环形"）。
5. 给每台真机分多个"虚拟节点"均匀撒在环上，防止某台扛太多（数据倾斜）。

具体例子：环上有 A、B、C 三台。key "order_99" 哈希后落在 B、C 之间，顺时针先碰到 C，就归 C。现在加一台 D 插在 B、C 之间——只有原本归 C 的"B→D 这段"改归 D，A、B 和剩下的 C 都不变；Demo 里 3 台扩 4 台，1 万个 key 约 25% 挪窝，其余原地不动。

对应代码：`ConsistentHashRouter`（路由）、`TreeMap.tailMap(p)`（顺时针找下一节点）、虚拟节点 `10.0.0.1:6379#VN0`。

> 备选：哈希函数别用 Java 自带 hashCode（分布不均会扎堆），Demo 用 MD5 对齐 Ketama 算法。

## ④ 一句提醒
一致性 Hash 只解决"映射稳定"，不解决"节点健康检查"——挂了的节点要配合心跳检测及时 `removeNode` 摘掉，否则路由过去全是失败；且新节点接管的那段数据不会自动搬家，记得缓存预热或低峰分批扩容。
