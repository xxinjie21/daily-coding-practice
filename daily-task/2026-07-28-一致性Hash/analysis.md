# 考点拆解与设计方案：一致性 Hash

## 一、这题在考什么

这是典型的**分布式系统设计基本功题**，考三层：

1. **知不知道普通 Hash 取模的坑**——扩缩容时映射关系大面积失效；
2. **会不会讲清一致性 Hash 的机制**——环、顺时针定位、局部影响；
3. **有没有工程意识**——知道数据倾斜问题和虚拟节点这个补丁，能提到 Ketama、Twemproxy、Redis Cluster 槽位等真实落地。

## 二、业务痛点：普通 Hash 为什么不行

先用生活场景把痛点讲透。

普通做法：`节点编号 = hash(key) % N`（N 是服务器台数）。这就像"按学号尾数分班"：尾数 0-2 去一班，3-5 去二班……规则简单粗暴。

**问题在于 N 一变，余数全变。**

举个具体例子：key 的哈希值是 100。
- 3 台机器时：100 % 3 = 1，存在 1 号机；
- 加 1 台变 4 台：100 % 4 = 0，得去 0 号机找——可数据在 1 号机上，找不到！

数学上可以证明：从 N 台扩到 N+1 台，**大约只有 1/(N+1) 的 key 还留在原机器**，其余全部错位。对缓存系统来说，错位 = 未命中 = 回源查数据库。上百万 QPS 的系统里，缓存命中率从 99% 瞬间跌到几乎为 0，数据库当场就跪了。

## 三、一致性 Hash 的整体设计（按原题思路展开）

### 3.1 核心数据结构：Hash 环

把 0 ~ 2^32-1 的整数空间想成一个**钟表盘**（只不过刻度有 42 亿多个），最大值走完又回到 0，首尾相接。

工程实现上，这个"环"用一棵**有序映射（Java 里就是 TreeMap<Long, String>）**来表示：
- **key**：哈希值（环上的位置）
- **value**：节点名（这个位置钉的是哪台服务器）

> **TreeMap** 大白话：一个自动按 key 排好序的字典，还能高效回答"大于等于 X 的第一个 key 是谁"（`ceilingEntry` 方法）——这正好就是"顺时针找下一个节点"的动作，一行代码搞定。

### 3.2 节点上环

对每台服务器的标识（如 `10.0.0.1:6379`）做哈希，得到一个环上位置，把 `(位置 → 节点名)` 放进 TreeMap。

**哈希函数的选择**有讲究：不能用 Java 自带的 `String.hashCode()`，它分布不均匀且只有 32 位里较集中的一段。工业界（Ketama）用 MD5，取其中 4 个字节拼成一个数。Demo 里我们也用 MD5，跟真实实现对齐。

### 3.3 key 定位节点（读写路由）

1. 对 key 做同样的哈希，得到环上位置 p；
2. 在 TreeMap 里找**第一个 ≥ p 的节点**（顺时针方向最近的那个）；
3. 如果找不到（p 比环上所有节点位置都大），**绕回环的开头**，取第一个节点——这就是"环形"的体现。

调用链非常短：`hash(key) → treeMap.ceilingEntry(p) → 没有则 treeMap.firstEntry()`。

### 3.4 为什么增删节点只影响一小段

环上每个节点只"认领"**从上一个节点到自己**这一段弧上的 key。

- **加节点 D**（插在 B 和 C 之间）：D 只从 C 手里接管"B→D"这段弧的数据，其他节点的辖区一寸没变。
- **删节点 C**：C 辖区的 key 顺时针滑给下一个节点，其他节点照旧。

好比小区新开一家快递驿站，只有附近两栋楼的住户改去新驿站，全小区其他人取件地点不变。

### 3.5 虚拟节点：治"数据倾斜"

只把 3 台物理机钉到环上，位置是哈希随机出来的，很可能挤在一起——某台机器认领了大半个环，忙死；另两台闲死。这叫**数据倾斜**。

**解法**：每台物理机分身出 N 个**虚拟节点**（比如 `10.0.0.1:6379#VN0`、`#VN1`……各自哈希上环），环上钉的密密麻麻都是分身。key 先找到分身，再由分身对应回真身物理机。

分身足够多（工程上常用 100~200 个，Ketama 用 160 个），大数定律就会让每台物理机认领的总弧长趋于均匀。这就像抽奖箱里每人多放几十张写自己名字的券，中奖比例自然接近各自的券数占比。

虚拟节点还有个隐藏好处：**机器配置不同可以配不同权重**——性能强的机器多放虚拟节点，多扛流量。

### 3.6 模块划分（如果落地成一个组件）

```
ConsistentHashRouter（路由器组件）
├─ hash(String) : long          // MD5 哈希，key 和节点共用
├─ addNode(node)                // 物理节点上环：生成 N 个虚拟节点插入 TreeMap
├─ removeNode(node)             // 物理节点下环：删掉它的所有虚拟节点
└─ route(key) : node            // 定位：ceilingEntry，找不到绕回 firstEntry
```

配置约定：虚拟节点数量做成构造参数；节点标识约定为 `ip:port`；虚拟节点命名约定 `ip:port#VN{i}`。

### 3.7 技术选型与权衡

| 方案 | 扩缩容影响 | 均匀性 | 实现复杂度 | 典型应用 |
|---|---|---|---|---|
| 普通 Hash 取模 | 几乎全部 key 失效 | 好 | 极简单 | 节点数固定的小系统 |
| 一致性 Hash（带虚拟节点） | 仅约 1/N 的 key 迁移 | 好（靠虚拟节点） | 中等 | Memcached/Ketama、Twemproxy |
| 槽位分片（预分 16384 槽） | 按槽迁移、可控 | 好 | 需要中心化元数据 | Redis Cluster |

Redis Cluster 没直接用一致性 Hash，而是先把 key 哈希到固定的 16384 个槽，再把槽分给节点——本质也是"加一层间接映射，让节点变化只挪动部分数据"，思想同源，但槽位方案迁移粒度更可控、便于运维指定。

## 四、Demo 代码怎么验证这些结论

Demo.java 按原题思路实现 `ConsistentHashRouter`，并做三组实验：

1. **普通 Hash 取模**：3 台扩到 4 台，统计 10000 个 key 有多少错位（预期约 75% 挪窝）；
2. **一致性 Hash**：同样 3 台扩到 4 台，统计错位比例（预期约 25%，即约 1/4 由新节点接管）；
3. **虚拟节点对比**：每台 1 个虚拟节点 vs 每台 150 个，看 3 台机器的 key 分布是否从"贫富悬殊"变成"基本均匀"。
