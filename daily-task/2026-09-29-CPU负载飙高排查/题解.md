# CPU Load 飙高排查：先分清「忙」和「等」，再抓出那个烧 CPU 的线程

**一句话**：CPU 负载高，就像餐厅后厨突然排起长队 —— 你要做的不是赶紧招人，而是先看清「是厨师在拼命炒菜，还是全堵在等一个坏掉的灶」。

## 一、为什么会有这个问题

先分清两个容易混的概念：

- **CPU 使用率**：CPU 有多少时间真的在干活（炒菜）。
- **Load average（平均负载）**：不只看干活的，还看**在排队等着的**（包括等磁盘、等网络的那些线程）。

所以出现一个反直觉的现象：**CPU 使用率只有 20%，Load 却能飙到 50**。这时候你去查 CPU 是查不出东西的 —— 问题在 IO。这就是排查的第一步必须同时看这两个数的原因。

> 生活比喻：Load 是「后厨里所有人和所有待做订单的总数」，CPU 使用率只是「厨师手上正在炒的那几口锅」。

## 二、排查四步走：先看系统 → 再看进程 → 再看线程 → 最后看堆栈

这是线上最稳的一条路径，每一步都回答一个问题：

| 步骤 | 命令 | 看什么 | 回答的问题 |
| --- | --- | --- | --- |
| ① | `top` | `load average` 三个数 + `%Cpu(s)` 的 `us`/`wa` | 机器整体忙不忙？是算得忙还是等 IO？ |
| ② | `top -H -p <PID>` | 进程里每个线程的 CPU 占用，按 `P` 排序 | 哪个线程在吃 CPU？（`-H` 就是展开成线程视角） |
| ③ | `printf "%x\n" <TID>` | 把线程号转成 16 进制 | 为下一步查栈做准备（jstack 里线程号是 16 进制的 `nid`） |
| ④ | `jstack <PID> \| grep -A 50 <hex_TID>` | 那个线程的调用栈 | 它到底卡在哪一行代码？ |

第①步里 `us` 高说明在算、`wa` 高说明在等 IO —— **这一个字母就能决定你后面往哪个方向查**，别跳过。

如果第④步看到栈里全是 GC 相关的帧，那方向就换了：不是业务代码的锅，是 GC 太频繁。这时用第⑤步确认：

```bash
jstat -gcutil <PID> 1000     # 每秒打一次，看 GC 次数和耗时涨得多快
```

## 三、代码是怎么把这几步「演」一遍的

`code/src/main/java/Demo.java` 用 JDK 自带的 `java.lang.management` 这套接口，把上面四步在自己身上完整跑了一遍 —— 它**不是仿真**，因为 `top` / `jstack` / `jstat` 这些命令拿到的数据，本来就是从这套接口（和它的底层）读出来的。每一步都在输出里标了它等价于哪条命令：

| 代码里做的事 | 等价于 |
| --- | --- |
| `OperatingSystemMXBean.getSystemLoadAverage()` + `getAvailableProcessors()` | `top` 顶部那行 load average 和核数 |
| `ThreadMXBean.getThreadCpuTime()` 前后两次相减，再排序 | `top -H -p <PID>` 按线程 CPU 排序 |
| `Long.toHexString(tid)` | `printf "%x\n" <TID>` |
| `ThreadInfo.getStackTrace()` | `jstack <PID> \| grep <hex_TID>` |
| `GarbageCollectorMXBean` 的 `getCollectionCount()` / `getCollectionTime()` | `jstat -gcutil <PID> 1000` |
| `ProcessBuilder` 起真实 `jcmd <PID> Thread.print` | 第⑥步：真去调一次 JDK 自带工具 |

关键的一段就是**采样两次再相减**：

```java
long delta = bean.getThreadCpuTime(ids[i]) - before[i];
```

为什么要相减？因为 `getThreadCpuTime` 返回的是「这个线程从出生到现在累计吃了多少 CPU」。只有**一段时间内的增量**才能看出「谁现在正在烧 CPU」。`top -H` 背后算的也是同一个东西，所以代码里采样窗口设成了 1.5 秒 —— 窗口太短会把一瞬间的抖动误判成热点。

为了让 CPU 真的忙起来，程序故意起了两个「坏线程」：

```java
Thread busyLoop = new Thread(() -> {
    long spins = 0;
    while (running.get()) {
        spins++;   // 原题点名的坑之一：while(true) 里没有 sleep，纯空转把一个核烧满
    }
}, "busy-loop-thread");

// 原题点名的坑之二：(a+)+$ 遇到「一长串 a 后面跟个不匹配字符」，会指数级回溯
Pattern evilRegex = Pattern.compile("(a+)+$");
```

跑起来之后，第④步打出来的栈非常有画面感 —— 全是 `Pattern$Loop` / `Pattern$GroupTail` 反复嵌套，这就是**正则回溯爆炸**现场：

```
at java.util.regex.Pattern$Loop.match(Pattern.java:4925)
at java.util.regex.Pattern$GroupTail.match(Pattern.java:4847)
at java.util.regex.Pattern$BmpCharPropertyGreedy.match(Pattern.java:4356)
```

## 四、最常见的三个「惯犯」

1. **死循环没 sleep**：`while(true)` 里干等一个标志位，把整个核烧满。改成阻塞队列的 `take()` 或加个 `Thread.sleep(1)` 就好。
2. **正则回溯爆炸**：`(a+)+$`、`(.+)+` 这种「量词套量词」的写法，遇到精心构造的输入会指数级尝试。尽量别用嵌套量词，或换成 `Pattern` 的占有量词 `(a++)+$`、给匹配长度设上限。
3. **频繁 Full GC**：GC 线程（`GC task thread`、`C2 CompilerThread` 之类）在排行里名列前茅，就该去查内存泄漏，而不是去查业务代码。

## 五、一句线上提醒

**别在线上随手敲 `jmap -dump` 做全量堆转储** —— 它会触发长时间 STW（Stop The World，整个 JVM 停住），本来只是慢，一敲就真挂了。要低开销地看内存，优先用 `jcmd <PID> VM.native_memory`（需启动时加 `-XX:NativeMemoryTracking=summary`）或 `async-profiler` 这类采样工具。

顺带一个实测坑：在 Windows 上 `jcmd` 输出的 `nid=0x...` 和 Java 的 `tid` **不是同一套编号**（Linux 上才相等），所以按 `nid` 过滤在 Windows 会扑空 —— 代码里改成按线程名过滤，两个平台都能用。
