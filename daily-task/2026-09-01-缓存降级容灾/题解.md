# 项目用了 Redis 缓存来提升并发度，假设 Redis 挂了怎么办？

**① 一句话题目（大白话）**
你的系统靠 Redis 顶着高并发，万一 Redis 突然挂了，请求全砸到 MySQL 上，数据库扛不住、整站雪崩，怎么办？

**② 为什么会有这问题（生活比喻）**
把 Redis 想成超市的「快速收银通道」，MySQL 是「人工窗口」。
平时 90% 的人走快速通道，人工窗口很闲。一旦快速通道塌了，所有人挤到人工窗口，队伍直接炸了——这就是缓存挂了之后的「缓存雪崩」。

**③ 怎么做（核心思路）**

1) 先装一个「降级开关」（配置中心 Nacos/Apollo 的一个开关）
Redis 一异常，就拨这个开关，让核心接口直接走「本地缓存 / 默认值」，先把能用的功能保住。
本地缓存像每家收银台自己备的小零钱盒——总台通道塌了，自己盒子里还有零钱能找开。

2) 用「闸机」挡住穿透（信号量 Semaphore）
Redis 挂了，所有查缓存的请求都会「穿透」到 DB。这时候布隆过滤器没用（因为数据根本加载不进来）。
用 Semaphore（就像「只允许 50 个人同时进人工窗口」的闸机），把打向 DB 的并发锁在 50 以内。宁可少接几个请求，也别把 DB 冲垮。

3) 平时就用「多级缓存」
本地缓存（Caffeine，一种放在 JVM 内存里的高速小仓库）+ Redis 集群。Redis 倒的时候，热点数据还在本地缓存里顶一阵。

4) 持久化恢复
AOF everysec：每秒落盘一次，宕机最多丢 1 秒数据，重启能续上；纯内存模式一挂全丢，恢复更久。

| 手段 | 解决什么 | 像什么 |
|---|---|---|
| 降级开关 | Redis 挂了还能保住核心功能 | 总台塌了，开自家小零钱盒 |
| 信号量限流 | 防止请求穿透把 DB 冲垮 | 限 50 人的闸机 |
| 多级缓存 | Redis 倒时本地还能顶热点 | 小金库 + 大仓库 |
| AOF 持久化 | 重启后能恢复大部分数据 | 每秒记一笔账 |

调用链：请求 →（降级开？）本地缓存 →（没中？）信号量闸机 → DB → 顺手塞回本地缓存

**④ 一句提醒**
别指望 Redis 永远在线，设计时就要按「它随时会挂」来搞；抗故障比追性能更重要。尤其 Semaphore 的限流值要设得比 DB 真实承载能力小，宁可拒绝几个请求，也别让雪崩发生。
