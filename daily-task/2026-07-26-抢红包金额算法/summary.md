# 抢红包功能：线上踩坑点 & 同类场景拓展

## 一、真实上线会踩的坑

### 1. 金额别用 double，一律用"分"（整数）算
浮点数有精度误差，`0.1 + 0.2 != 0.3`。发钱这种事，差一分钱就是资损事故。
- **做法**：全程用 `long`/`int` 表示"分"，1 元 = 100 分，展示时再除以 100。Demo 就是这么做的。
- 数据库存金额也建议用 `bigint`(单位分) 或 `decimal`，别用 `float/double`。

### 2. 最后一个人必须"兜底"，不能也参与随机
如果每个人都随机，前面因为取整东丢一分西丢一分，最后加起来就对不上总额。
- **做法**：前 N-1 个人随机，**最后一个人直接拿走账上剩余全部**。这样总额永远严丝合缝。

### 3. 上限要兜底、金额要兜底最小值
- `random.nextInt(max)` 里如果 `max` 算成 0（剩余金额比人数还少的极端情况）会直接抛异常。要保证 `max >= 1`。
- 每份至少给 1 分（`Math.max(1, ...)`），否则会出现"抢到 0 元"的尴尬。

### 4. 超发是头号大坑：并发不加控制必翻车
100 个人几乎同一瞬间点"抢"，如果流程是"查还剩几份 → 算金额 → 扣一份"，两个人可能同时查到"还剩 1 份"，结果都抢成功——**超发、资损**。
- **Demo 用一把锁**演示原子性；**真实线上用 Redis + Lua 脚本**：把"检查份数 → 弹金额 → 扣份数"打包成一个 Lua 脚本交给 Redis 执行，Redis 单线程执行脚本期间不会被插队，天然原子。
- 也可以用分布式锁（Redisson）或数据库乐观锁（`update ... where stock > 0`），但 Redis+Lua 性能最好，是抢红包/秒杀的标配。

### 5. 预生成 vs 实时计算
- **预生成**（发红包时就把 N 份金额都算好存 Redis 列表）：抢的时候直接 `LPOP` 弹一份，最快，抗高并发，微信采用这种。
- **实时计算**（每次抢时才算一份）：省一点内存但每次都要算、要锁得更久。高并发场景优先预生成。

### 6. 数据库别被瞬间流量打垮
抢到金额后要入账（写用户余额、写流水）。高峰期直接写库会压垮数据库。
- **做法**：抢的动作只在 Redis 完成（快），入账通过**消息队列（MQ）异步削峰**，慢慢落库。

### 7. 未抢完要退款
红包 24 小时没抢完，剩余金额要**原路退还发红包的人**。需要定时任务扫描过期红包，退款也要保证幂等（别退两次）。

## 二、同类场景拓展（一套思路，处处能用）

这道题的两个核心能力——**"总量随机拆分"** 和 **"高并发原子扣减"**——在很多业务里都用得上：

| 场景 | 用到的能力 | 说明 |
| --- | --- | --- |
| **秒杀 / 抢购** | 高并发原子扣减 | 库存扣减和抢红包份数扣减是一回事，都用 Redis+Lua 防超卖 |
| **优惠券发放** | 原子扣减 + 幂等 | 限量券"先到先得"，防止发超；同一人别领两张 |
| **积分/奖励随机发放** | 二倍均值法 | 抽奖发随机积分，保证总池子不超发 |
| **拼团/众筹进度分配** | 线段切割思路 | 把目标金额按参与者随机或按比例拆分 |
| **限流令牌分配** | 原子扣减 | 令牌桶本质也是"原子地取一个、没了就拒绝" |

---

## 三、两种算法怎么选

- **要绝对公平、体验稳（前后抢到的金额差距不太夸张）** → 二倍均值法（微信优化后的主流选择）。
- **要极致简单、追求刺激（金额波动更大、更有惊喜感）** → 线段切割法。
- 两种都能保证**总额守恒**，区别只在金额分布的"手感"。实际业务里二倍均值法用得更多。

---

## 四、一句话总结
抢红包 = **算法上**用二倍均值法把钱随机又公平地拆开（全程用"分"算、最后一人兜底）+ **工程上**用 Redis+Lua 保证并发抢的时候不超发、总额不出错。记住这两句，这题就稳了。
