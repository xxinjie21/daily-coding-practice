## 40. 如果要实现一个抢红包的功能，红包金额是如何计算的？

### 一句话看懂这题在问什么

老板发了一个 100 元的群红包，说"发给 10 个人抢"。你点进去手一抖，抢到 23.66 元，别人有的抢到 0.01 元，有的抢到 30 多元。**问题来了：这几个人抢到的钱，程序是怎么算出来的？** 要满足两个硬性要求：

1. **加起来必须正好是总额**——10 个人抢到的钱一分不多、一分不少，加起来就是 100 元，不能超发也不能少发。
2. **每个人抢到的金额要随机、但要合理**——不能第一个人就把 99 元抢走，剩下 9 个人分 1 元只能抢到一分钱；也不能大家都抢一样多（那还叫什么抢红包）。

### 原题给出的两种经典算法

原题明确说了，业界常见就两种做法，我们这次就照着这两种来实现。

**1）线段切割法（切绳子）**

把总金额想象成一根绳子。100 元就是一根长 100 的绳子，要分给 10 个人，就在这根绳子上随机"切 9 刀"（9 个切点），绳子被切成 10 段，每一段的长度就是一个人抢到的金额。

- 具体做法：在 `[0, 100]` 区间里随机取 9 个不重复的点，排好序，然后算相邻两点之间的距离，就是每个人的金额。
- 好处：因为是切同一根绳子，所有段加起来天然等于总长（总额），**总额绝对不会错**。
- 缺点：如果几个切点凑得很近，就会切出很小的一段（有人抢到超小金额），运气成分更大、波动更明显。

**2）二倍均值法（期望值控制法）**

这是微信后来优化用的思路，核心一句话：**每个人能抢到的上限，是"当前剩余人均金额"的 2 倍。**

- 举例：还剩 50 元、还有 8 个人没抢，那下一个人最多能抢 `(50 / 8) * 2 = 12.5` 元，然后在 `[0.01, 12.5]` 里随机取一个数。
- 为什么要乘 2？因为随机值平均下来大概是上限的一半，也就是 `人均金额` 左右，这样**抢完前面的人后，后面的人也大概率还能分到接近人均的钱**，不会出现"前面吃饱、后面饿肚子"或"最后几个人只能抢一分钱"的尴尬。
- 最后一个人不用随机，直接把剩下的钱全给他，保证一分不差。

### 原题给的代码骨架（核心就是控制随机范围）

```java
Random random = new Random();
double leftAmount = total;
for (int i = 0; i < count - 1; i++) {
    double max = leftAmount / (count - i) * 2;   // 上限 = 剩余人均 * 2
    double amount = Math.max(0.01, random.nextDouble() * max);
    // 分配金额...
    leftAmount -= amount;
}
// 最后一人拿完剩余
```

### 顺带一提（工程落地）

原题最后提到：微信早期用线段切割，后来优化成改进版的期望控制策略，兼顾公平和体验。真实线上系统里，为了防止"两个人同时抢导致算重、超发"，还会用 **Redis + Lua 脚本**保证扣减库存和分配金额这一串操作是"原子"的（要么全成功、要么全失败，中间不会被别人插队）。这次的 Demo 会用大白话把这个原子性的思路也演示一下。
