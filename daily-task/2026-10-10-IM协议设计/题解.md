# WebSocket 与 IM 协议设计：让「聊天」这件事不丢、不乱、不掉线

## 一句话
WebSocket 只解决了「电话能接通」，真正难的是接通之后：消息**不能丢**、**不能乱**、连接**不能悄悄断**——这几条规矩加起来，才叫 IM（即时通讯）协议。

## 为什么会有这个问题
把两种通信方式摆在一起看就懂了：

- **HTTP 像寄信**：你寄一封，对方回一封，每次都要重新打招呼、重新建立关系。
- **WebSocket 像打电话**：握手一次之后线路一直开着，两边随时都能说话（这就是「全双工」）。

但打电话也有打电话的麻烦：

- 对面没听清，你得让他「复述一遍确认」——否则话就丢了；
- 两句话顺序听反了，意思就变了——所以要给每句话**编号**；
- 手机早就没信号了，你还以为在通话——所以要**每隔一会儿喂一声**（心跳），确认对面还在。

IM 协议就是在这三条之上再加两件工程上的事：**谁能打进来（鉴权）**、**别让慢活堵住接线员（异步解耦）**。

## 五件事，一件件说

| 要操心的事 | 不处理会怎样 | 做法 | Demo 里在哪 |
|---|---|---|---|
| 连接鉴权 | 谁都能连上来冒充别人 | WebSocket 握手本来就是一次 HTTP 请求，先查 `token`，不对直接回 401 | `AuthHandler` |
| 消息有序 | 同一个人的两句话收到反了 | 服务端按「会话」统一编号 `seq`，客户端按 `seq` 排序后再展示 | `ImMessageHandler` |
| 不丢消息 | 网络抖一下消息就没了 | 服务端收到就回 `ACK`，客户端等不到回执就重发 | `ACK\|seq\|内容` |
| 连接保活 | 网线拔了、NAT 超时，双方都以为还连着 | 客户端定期发心跳；服务端一段时间收不到任何数据就判掉线、关连接 | `IdleStateHandler` |
| 别被慢活拖死 | 一落库就变慢，接线员（IO 线程）全被堵住 | 消息先扔进消息队列，落库、路由这些慢活交给下游慢慢做 | RabbitMQ |

其中「会话」是个关键词：**单聊（A→B）和群聊（A→群）是两个不同的会话，各编各的号**。所以你会看到 `1001->1002` 的两条消息是 `seq=1、2`，而 `1001->group-888` 的第一条又是 `seq=1`——这不是 bug，是「每个会话内部有序」的正常表现。

## 消息在系统里怎么走

```
客户端 --WebSocket--> Netty 服务端
                        │
                        ├─ AuthHandler      先验 token，不对就 401，压根不让升级成 WS
                        │
                        └─ ImMessageHandler 给消息分配 seq ──> 立刻回 ACK 给客户端
                                             │
                                             └─ basicPublish ──> RabbitMQ ──> 下游消费者落库 + 路由
```

注意 ACK 和落库是**分开**的：客户端拿到 ACK 时，消息可能还没落库。这在 IM 里是刻意的——**ACK 只表示「服务端收到了」，不表示「已经存好了」**。真正的可靠性靠 MQ 的重投 + 落库端的幂等来兜。

## 关键代码（与 `code/src/main/java/Demo.java` 完全一致）

**① 鉴权必须放在协议升级之前**，否则连接已经变成 WebSocket 了再拦就晚了：

```java
ch.pipeline()
        .addLast(new HttpServerCodec(), new HttpObjectAggregator(65536))
        .addLast(new IdleStateHandler(0, 0, IDLE_SECONDS))   // 心跳超时检测
        .addLast(new AuthHandler())                          // 先验 token
        .addLast(new WebSocketServerProtocolHandler(          // 再升级成 WebSocket
                "/ws", null, true, 65536, false, true))
        .addLast(new ImMessageHandler(mq));
```

**② 按会话编号 + 立刻回 ACK + 投 MQ**，三件事一气呵成，不让 IO 线程等落库：

```java
String session = in.from() + "->" + in.to();
long seq = seqBySession.computeIfAbsent(session, k -> new AtomicLong()).incrementAndGet();

// 回执：告诉客户端「收到了，序号是 seq」
ctx.writeAndFlush(new TextWebSocketFrame("ACK|" + seq + "|" + in.content()));

// 投 MQ：落库、路由这些慢活交给下游，IO 线程立刻解放
try (var channel = mq.createChannel()) {
    channel.basicPublish("", QUEUE, null, stored.toMqText().getBytes(StandardCharsets.UTF_8));
}
```

**③ 心跳超时：服务端真的断开**，不能只发不校验：

```java
public void userEventTriggered(ChannelHandlerContext ctx, Object evt) {
    if (evt instanceof IdleStateEvent) {
        System.out.println("[心跳] 超过 " + IDLE_SECONDS + " 秒没收到任何数据，判定掉线，关闭连接");
        ctx.close();
    }
}
```

## 还有两件常被追问的事

**用户不在线，消息去哪了？** 照常落库，另外记一份「未读」。用户下次上线时，按 `seq` 拉自己所有会话的未读消息——因为有序号，客户端拼起来不会乱。

**怎么扛百万连接？** 两个前提：**网关无状态**（连接本身不存业务状态，登录态、路由信息放 Redis），**消息按用户 ID 分片**（同一个用户的消息总是落到同一台存储上，方便保证有序）。这样加机器就能线性扩。

## 一句提醒
**心跳间隔一定要小于中间设备（Nginx、负载均衡、NAT）的空闲超时**。链路中间任何一跳空闲久了都会悄悄把连接掐掉，而两端都以为还连着——这种「假连接」是 IM 线上最典型的坑。常见做法是心跳 30 秒、连续 3 次没响应才判死，本 Demo 为了当场看到效果压缩成了 3 秒。
