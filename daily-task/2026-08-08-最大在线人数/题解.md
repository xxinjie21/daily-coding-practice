# 最大在线人数：一堆登录日志，怎么求出峰值和它撑了多久

> 原题（后端场景面试题 71）：一天内的大量日志，每条记录 `{userid, login_time, logout_time}`，时间单位是秒。
> 怎么求出一天内的最大在线人数？以及维持最大在线人数的最长持续时间？

## 一句话题目

给你一堆「谁几点进来、几点走」的记录，问：**同一时刻最多有多少人同时在线？这个最高纪录连续撑了多少秒？**

## 为什么会有这问题

想象你开了家网吧，一天下来有一沓刷卡记录：

```
用户1  [0, 10)      用户2  [3, 8)      用户3  [5, 12)
用户4  [8, 15)      用户5  [20, 25)
```

（写成 `[进, 出)` 是因为**登出那一秒人已经走了，不算在线**，这个细节后面会咬人。）

老板想知道「今天最挤的时候有多少台机器在用」，好决定要不要加机器。

最笨的办法：把一天 86400 秒挨个数一遍，每一秒去翻所有日志看谁在线。100 万条日志 × 86400 秒 = 天文数字，跑到明天也出不来。

**关键的转念**：你其实不用一直盯着屋里，只要盯着**门口**就行了。有人进 +1，有人出 -1，手里捏个计数器，人数的最高点自然就冒出来了。

这就是所谓的**扫描线**（也叫事件驱动扫描）——把「一段一段的时间区间」压平成「一条时间线上的进出事件流」。

## 怎么做

### 第一步：把每条日志拆成两个「门口事件」

一条日志 = 一进一出，两个事件。n 条日志变成 2n 个事件：

```java
for (LoginLog log : logs) {
    events.add(new Event(log.loginTime(), 1));    // 进门，+1
    events.add(new Event(log.logoutTime(), -1));  // 出门，-1
}
```

### 第二步：按时间排队，同一秒里「先出后进」

```java
events.sort(Comparator.comparingInt(Event::time)
                      .thenComparingInt(Event::delta));  // -1 排在 +1 前面
```

为什么同一秒要先处理出门的？因为登出那一秒人已经不在了。如果先算进门的，就会出现「A 还没走 B 就进来了」的**假重叠**，人数虚高一个。

### 第三步：扫一遍，计数器记峰值

```java
int online = 0, maxOnline = 0;
for (Event e : events) {
    online += e.delta();
    maxOnline = Math.max(maxOnline, online);
}
```

拿上面 5 条日志跑一遍，时间轴长这样（Demo 实验一的真实输出）：

```
第  0 秒：进 1 出 0 -> 在线 1 人  #
第  3 秒：进 1 出 0 -> 在线 2 人  ##
第  5 秒：进 1 出 0 -> 在线 3 人  ###   <- 冲顶
第  8 秒：进 1 出 1 -> 在线 3 人  ###   <- 有走有来，人数没变
第 10 秒：进 0 出 1 -> 在线 2 人  ##    <- 掉下来了
第 12 秒：进 0 出 1 -> 在线 1 人  #
第 15 秒：进 0 出 1 -> 在线 0 人
第 20 秒：进 1 出 0 -> 在线 1 人  #
第 25 秒：进 0 出 1 -> 在线 0 人
```

峰值 3 人，从第 5 秒撑到第 10 秒，**维持 5 秒**。整个过程 O(n log n)，瓶颈在排序。

### 第四步：数据量再大，连排序都能省 —— 差分数组

一天满打满算就 86400 秒，**时间范围是固定且已知的**。那还排什么序？直接摆 86400 个格子：

> **差分数组**是啥：好比记账时不记「今天总共几人」，只记「今天比昨天多几人」。
> 想知道某天的实际人数，从头一路加过来就行。

```java
changeAtSecond[log.loginTime()]  += 1;   // 这一秒开始多一个人
changeAtSecond[log.logoutTime()] -= 1;   // 这一秒开始少一个人
// 然后从左到右累加一遍，每格的累加值就是那一秒的在线人数
```

复杂度 O(n + 86400)，不用排序。Demo 实验四用 50 万条日志实测：

| 方法 | 耗时 | 适用场景 |
|---|---|---|
| 事件扫描线（排序 100 万个事件） | **332 ms** | 时间跨度大 / 不确定（跨年、毫秒级） |
| 差分数组（86401 个格子累加） | **4 ms** | 时间范围固定且不大（一天、一年按天） |

快了 **83 倍**，差的就是那次排序。两者答案完全一致（都是 10689 人）。

## 两个真会踩的坑

原题给的参考代码，**求最大人数是对的，但求「维持时长」有两个 bug**。Demo 实验五用 200 轮随机数据对拍，原版**错了 153 轮**：

**坑 1：同一秒有人走也有人来，峰值被拦腰截断。**
上面第 8 秒，用户2 走、用户4 来，人数纹丝不动还是 3 人。但如果**一个事件一个事件**地处理，先算 -1 就闪现了一个「在线 2 人」的假瞬间，程序以为峰值断了，只记了 `8-5=3` 秒，正确答案是 5 秒。

> 修法：**把同一秒的所有事件打包成一次净变化**再判断。

**坑 2：一天出现两段一样高的峰值，只认第一段。**
上午 `[0,100)` 有 2 人，下午 `[200,400)` 又有 2 人。原版只在 `online > maxOnline`（破纪录）时才记起点，下午再冲到 2 人时不算破纪录，它压根没开始计时，结果报 100 秒，实际最长是 200 秒。

> 修法：加一句 `online == maxOnline 且当前没在计时 -> 重新记起点`。

修正后的核心逻辑（完整可运行版见 `code/Demo.java`）：

```java
online += netChange;                       // netChange 是这一秒的净变化
if (online > maxOnline) {                  // 破纪录：之前记的全作废
    maxOnline = online;  peakStart = currentTime;  longest = 0;
} else if (online == maxOnline && peakStart == -1) {
    peakStart = currentTime;               // 又爬回峰值，重新计时
} else if (online < maxOnline && peakStart != -1) {
    longest = Math.max(longest, currentTime - peakStart);  // 掉下来，结算
    peakStart = -1;
}
```

## 一句提醒

**这类题最容易翻车的不是算法，是边界语义。**动手前先确认三件事：区间是 `[进, 出)` 还是 `[进, 出]`？同一秒的进出算不算重叠？跨零点的会话（23:50 登录、次日 0:10 登出）算哪天？

尤其是跨天这条 —— 线上日志里这种会话一定存在，不处理的话凌晨那段人数会凭空少一截，而且**不报错、只是数字偏小**，最难查。

顺带一提，这套「把区间摊平成事件流」的思路不只用来数人头：会议室排期冲突检测、Flink 的窗口聚合、CPU 占用峰值统计，本质都是同一道题。
