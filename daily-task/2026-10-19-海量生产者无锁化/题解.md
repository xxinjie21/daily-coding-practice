# 两百万个生产者、一个消费者：别设计锁，让锁不需要出现

## 一句话题目
两百万个生产者同时发消息，只有一个消费者来收——问锁怎么设计才高效？答案是：**别指望把锁设计得多精巧，要从根上让锁不出现**。

## 为什么会有这个问题（先讲个比喻）
想象一栋写字楼里两万人同时刷门禁开工卡，门口只开一条窄通道，还挂了一台「一次只准过一个人」的闸机（这就是全局锁）。人越多，大家的时间越花在「等闸机」上，真正走过去反而占少数；邮差（消费者）来取文件，也得跟两万人抢同一道闸机，自然快不起来。

所以原题说得很直白：两百万生产者竞争同一把锁，系统早就崩了——**问题不在锁怎么调，而在「让所有人挤一扇门」这个设计本身**。

## 怎么做（三步，对应原题答案）
1. **生产者先分片**：按生产者 ID 取模（或 hash、轮询），把两百万个生产者分散到 64 个独立队列，各写各的。就像把一扇门禁改成 64 个，按手机号尾号分流。Kafka 的 Partition、RocketMQ 的 MessageQueue 干的就是这件事。
2. **队列内部用无锁结构**：用 `ConcurrentLinkedQueue`——底层是 CAS（比较再交换：先看一眼「位置还是我预期的样子吗？是就坐下，不是就重看」）。多个生产者同时写不用互相申请、互相等待，也就没有锁可抢。
3. **消费者轮询所有分片，消费速度是关键**：捞不过来，队列就会堆积；真跟不上就得评估扩容消费者——哪怕题目说「一个消费者」，也要评估它到底扛不扛得住。

## 代码怎么演示（code/src/main/java/Demo.java）
程序把同一批 200 万条消息用三种结构收发（消费者每条消息做固定处理，模拟真实负载），分别计量「生产耗时」和「总耗时」：

| 方案 | 做法 | 生产耗时 | 总耗时 |
|---|---|---|---|
| 方案一 | 全局一把 `ReentrantLock` + 一个共享队列，32 个生产者和 1 个消费者全抢这把锁 | 约 70 ms | 约 560 ms |
| 方案二 | 按生产者 ID 分 64 片，每片一个 `ConcurrentLinkedQueue`，1 个消费者轮询 | 约 19 ms | 约 510 ms |
| 方案三 | 同样分 64 片，8 个消费者各认领 8 片并行消费 | 约 40 ms | 约 130 ms |

三个数字说明三件事：
- **生产侧**：分片 + 无锁比全局锁快 3~4 倍——锁堵住了本来能并行的写入；
- **消费侧**：一个消费者是硬上限（总耗时被它拖到约 0.5 秒，而生产只要 0.02 秒）；
- **扩容**：8 个消费者并行后总耗时降到约 0.13 秒，接近生产耗时——分片正是让「加消费者」成为可能的前提。

三种方案收到的消息完全相同（生产者 ID 合计都是 1999999000000，程序会打印校验和），差别只在收发结构。

关键代码就三处：全局锁版 `lock.lock() → queue.add() → lock.unlock()`；分片版 `shards.get(producerId % 64).add(producerId)`（一行，没有任何锁）；并行消费版 `for (int s = id; s < 64; s += 8)`（每个消费者认领固定的几个分片，互不重叠）。

（耗时在本机实测，换机器会有出入，但三个结论不变。）

## 一句线上提醒
**「只有一个消费者」往往不是设计目标，而是没评估过的假设**：队列要有界、监控堆积深度，消费者真扛不住时就该扩容（Kafka 里就是消费者组按 Partition 分工）。另外多个消费者别共用一个计数器（会缓存行乒乓），各数各的反而更快——程序里每个消费者就用的私有计数器。
