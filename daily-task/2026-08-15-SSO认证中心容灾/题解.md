# SSO 系统中，如果认证中心挂了怎么办？如何保证已登录用户不受影响？

## ① 一句话题目（大白话）
SSO（单点登录）的认证中心要是突然瘫痪，那些已经登录、正在用系统的用户，会不会被"请出去"重新登录？

## ② 为什么会有这问题
把 SSO 想成"公司大门 + 各楼层门禁"，认证中心就是门口的"总登记处"。如果每次员工进楼层，都要跑回总登记处问一句"这人合法吗？"，那总登记处一停电，全公司谁都进不去——哪怕你十分钟前刚登记过。

问题就出在：**我们把"每次进门"的验证，错误地绑定到了"总登记处在线"这件事上**。正确思路是让各楼层（业务系统）自己能认出"这人确实买过票"。

## ③ 怎么做（三招，核心是"让业务系统自己能认人"）

**招式一：发"自带防伪章的票"——自包含令牌（JWT）**
认证中心登录成功后，发一张**自带签名**的票（JWT）。票上写着"用户ID + 有效期"，并用只有中心和各业务系统共有的秘钥签了名。业务系统拿到票，**用同一把秘钥自己验签名**，根本不用回头找认证中心。
> 小贴士：JWT 就是 `Header.Payload.Signature` 三段 base64，Signature 是用秘钥对前两段算出的指纹。别人改不了内容，业务系统一验便知真假。

**招式二：本地缓存一份"已登录花名册"**
各业务系统用 Redis 存一份 `token → 用户信息` 的映射，TTL（存活时间）设得和 Token 有效期一样长。中心出问题时，先翻本地花名册扛一阵，避免所有请求都堵死。

**招式三：中心本身做高可用（集群 + 主备切换）**
用 Keepalived 搞 VIP（虚拟IP，主机挂了自动漂到备机），或上 K8s 的 readiness probe 自动摘掉异常实例，数据库也要主从高可用。这招是"降低挂的概率"，但**真正兜底的还是招式一、二**——中心一旦真挂，已登录用户靠本地校验照样能进。

**小对比表：**

| 验证方式 | 中心正常 | 中心宕机 | 结论 |
|---|---|---|---|
| 每次请求都远程验（反例） | 放行 | 全部重登 | 千万别这么设计 |
| 自包含 Token 本地验（推荐） | 放行 | 无感放行 | 日常访问主力 |
| 本地缓存花名册兜底 | 放行 | 撑一阵 | 与 Token 互补 |

**调用链（重点一句）：** 在线验证只发生在"登录 / 刷新 Token"那一刻；日常每次请求，靠"自包含 Token + 本地校验"兜底。所以中心挂了，已登录用户完全无感。

## ④ 一句提醒
别把"每次请求都去认证中心验一次"当成默认设计——那是把全公司的门禁都焊死在总登记处。正确做法：登录走中心、日常靠本地验签。另外，Token 过期该重登还是得重登，本地校验只保"没过期就不打扰你"，不保"永生"。
