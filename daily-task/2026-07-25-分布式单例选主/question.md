## 32. 让你实现一个分布式单例对象，如何实现？

### 一句话题目
在**很多台服务器**组成的集群里，怎么保证「某个对象/某段逻辑」在整个集群中**同一时刻只有一份在干活**？这就是「分布式单例」。

### 先说清楚「单例」在单机和集群里的区别

- **单机单例**：我们在一个 Java 程序（一个 JVM）里写个单例（比如经典的饿汉/懒汉写法），保证整个进程里这个对象只 new 一次。这很好办，因为大家共用同一块内存。
  - 打个比方：一个办公室里只有**一把公章**，谁都用这把，不会有第二把。

- **分布式单例**：现在把同一个程序**部署到了 5 台服务器**上，每台机器都是一个独立的 JVM，**内存互相隔离**。你在代码里写的单例，其实变成了「每台机器各有一份」，一共 5 份，根本不是「唯一」。
  - 还用公章比喻：现在开了 5 个分公司，每个分公司都想刻一把公章。如果 5 把公章都能盖章，就乱套了（比如 5 台机器同时去跑同一个定时任务、同时初始化同一份配置）。

所以题目的**真正诉求**不是「让一个对象的内存跨机器共享」（那几乎做不到也没必要），而是：
> **通过一个「大家都信服的裁判」，选出唯一一台机器来"当家做主"（执行那段单例逻辑），其他机器待命。**
> 这在分布式里叫 **Leader Election（选主）**。当家的这台叫 **Leader（主节点）**，其余叫 **Follower（从节点）**。

### 原题给出的三种落地思路（后面文档就按这三种展开）

1）**借 Redis 抢锁**：用 `SET key value NX` 命令抢一把「分布式锁」。
   - `NX` = "not exists"，意思是「这个 key 不存在时我才写得进去」。**谁第一个写进去，谁就抢到了锁**，就由它来初始化对象、对外服务；其他节点抢不到，就当备用/只读。
   - 比喻：一群人抢**唯一一个空车位**，`SET NX` 就是"车位空着我才能停，停进去别人就停不了"。
   - 适合：配置中心、定时任务调度这类场景。简单可靠。

2）**借 ZooKeeper 选主**：利用它的「临时顺序节点 + Watcher（监听）」机制自动选出主节点。
   - 大家都去同一个目录下排队创建节点，**号最小的当 Leader**；Leader 挂了，它的临时节点会自动消失，下一个人被通知（Watcher）后补位。
   - 像 Dubbo 注册中心、Kafka 的 Controller 都是这么选主的，是**高可用的「伪单例」**。

3）**注意本质**：以上都不是让对象真的跨进程共享，而是**用协调机制保证同一时间只有一个实例在工作**。如果业务还需要让各节点的**状态保持一致**，就再配上消息队列（如 RocketMQ）**广播状态变更**。

### 原题给的代码片段（工程里别自己造轮子）

实际项目里不用手写选主，直接用 Apache Curator（ZooKeeper 的客户端库）的 `LeaderLatch` / `LeaderSelector`：

```java
LeaderSelector selector = new LeaderSelector(client, "path", (leader) -> {
    // 成为 leader 后执行的逻辑，相当于单例初始化
    initSingletonService();
});
selector.start();
```

### 那本目录的 Demo 要演示什么？

因为 Demo 要能**独立编译运行、不连真的 Redis/ZooKeeper**，所以我们用一个「内存里的模拟协调中心」把上面**第 1 种思路（Redis SET NX 抢锁选主）**的核心机制原汁原味地演出来：
- 一个 `CoordinationStore` 模拟 Redis，提供 `setIfAbsent`（就是 `SET NX`）；
- 多台 `ServerNode`（用多线程模拟多台机器）同时抢锁；
- **只有一台抢到锁、成为 Leader 并初始化单例服务**，其余待命；
- Leader「宕机」后，锁到期释放，**其他节点自动补位重新选主**（对应第 2 种思路的 failover 效果）；
- 顺带用一个简单的广播演示第 3 种思路的「状态同步」。
