# 分布式单例：线上踩坑 & 拓展（大白话版）

## 一、生产上最容易踩的坑

### 1. 「双主」——最要命的坑
- **现象**：明明说好只有一个 Leader，结果某段时间出现了两台机器都以为自己是 Leader，同一个定时任务被跑了两遍。
- **原因**：Leader 干活太久，锁到期被自动释放，另一台抢到成了新 Leader，而老 Leader 还没干完、还以为自己是老大。
- **怎么防**：
  - **给锁续期（watchdog / 看门狗）**：Leader 只要还活着，就后台定时把锁过期时间往后延（Demo 里的 `renew` 就是这个思想）。生产直接用 **Redisson**，它自带看门狗自动续期，不用自己写。
  - **业务侧做幂等**：即使万一双主，同一个任务重复执行也不会造成脏数据（比如发账单前先查"今天是否已发"）。这是最后一道保险。

### 2. 锁没设过期时间 → 死锁
- Leader 突然断电宕机，锁却没有过期时间，于是**永远没人能再抢到**，整个功能瘫痪。
- **铁律**：分布式锁**必须带过期时间**（Demo 里的 `LOCK_TTL_MILLIS`）。宁可让它到点自动放开，也不能永久占用。

### 3. 误删别人的锁
- A 的锁过期了，B 抢到了；这时 A 慢悠悠地执行"释放锁"，把 **B 的锁给删了**。
- **解法**：锁的 value 存自己的唯一 id，**释放前先判断"这把锁还是不是我的"**（Demo 的 `releaseIfOwner` 就是干这个）。生产上用 Lua 脚本把"判断 + 删除"做成一个原子操作。

### 4. 协调中心单点故障
- 只用一台 Redis / 一台 ZK，它一挂，整个选主机制全废。
- **解法**：Redis 用集群 / 哨兵；ZK 本身就是集群部署（奇数台，过半存活即可用）。对一致性要求极高时可用 Redlock，但 Redlock 也有争议，强一致场景更推荐 ZK。

### 5. 时钟漂移 / GC 停顿导致的"假死"
- Leader 发生一次很长的 Full GC（几秒卡住），期间没续上期，锁被别人抢走，GC 结束后它却毫不知情继续干活 → 又是双主。
- **缓解**：TTL 别设太短、续期间隔要远小于 TTL（Demo 里 TTL=1.5s、续期=0.5s，留足冗余）；关键业务叠加幂等兜底。

## 二、同类场景 & 拓展方案

- **定时任务只跑一份**：正是分布式单例最典型的用途。除了自己选主，也可直接用 **XXL-JOB、Elastic-Job** 这类分布式任务调度框架，它们内部就帮你做了选主/分片。
- **主从热备**：Leader 干活，Follower 待命；Leader 挂了秒切。数据库主从、Redis 哨兵、Kafka Controller 都是这个模式的变体。
- **配置中心 / 元数据管理**：由 Leader 统一维护，变更后广播给全体（对应方法 3 的 MQ 广播）。
- **从"单例"到"分片"**：如果一个 Leader 忙不过来，可以把任务**按 key 分片**，让多台机器各管一部分（每片内部仍是单例）。这是从"1 个负责人"演进到"多个负责人各管一摊"，能力翻倍又不冲突。

## 三、一句话记忆点

> 分布式单例的本质不是"造一个跨机器共享的对象"，而是**"选出唯一一台机器来干活"（选主）**。
> 落地就三件套：**抢锁/选主（保证唯一） + 过期&续期（防死锁、防双主） + 故障自动切换（保证高可用）**，需要时再加 **MQ 广播（状态同步）**。
> 工具选择：有 Redis 且一致性要求不极端 → Redis SET NX（+Redisson 看门狗）；要强一致 → ZooKeeper + Curator LeaderLatch。

## 四、本目录 Demo 说明
- Demo 用「内存 Map 模拟 Redis + 多线程模拟多机」把方法 1 完整演了一遍：**唯一选主 → Leader 干活并续期 → Leader 宕机 → 他人自动补位**，并附带一次状态广播。
- 它是教学示例，**没有**接入真实 Redis、没有 Redisson 看门狗、没有 Lua 原子释放、没有集群容错——这些在上面「踩坑」里都点明了，生产落地时请按需补齐。
