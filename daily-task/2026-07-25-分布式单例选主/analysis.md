# 分布式单例：考点拆解 + 实现方案（大白话版）

## 一、这道题到底在考什么？

面试官抛出「分布式单例」，其实想看你有没有想明白三件事：

1. **概念纠偏**：你知不知道「单机单例」在集群里会失效？（每台机器一份，根本不唯一）
2. **换个角度**：你能不能把「造一个唯一对象」这个伪命题，翻译成「**选出唯一一台机器来干活**」这个真命题（也就是选主 / Leader Election）。
3. **落地能力**：你能不能说出 Redis、ZooKeeper 这些具体工具怎么做，以及主节点挂了怎么办（高可用）。

一句话总结考点：**分布式单例 = 分布式锁/选主 + 故障自动切换 +（可选）状态同步**。

---

## 二、业务里为什么需要它？（真实痛点）

不搞唯一控制会出什么乱子？举几个新手也能秒懂的场景：

- **定时任务重复跑**：一个「每天凌晨 1 点给用户发账单」的任务，部署在 5 台机器上。如果 5 台都跑，用户会收到 **5 份账单**。我们要的是：**只有 1 台跑**。
- **配置/缓存重复加载**：某份很重的全局配置，只该由一台机器加载并对外提供，5 台都加载既浪费又可能不一致。
- **消息重复消费**：某类必须串行处理的消息，只能有一个「主消费者」在处理，否则顺序乱、数据错。

这些场景的共同点：**这件事在整个集群里，同一时刻只能有一个「负责人」**。这就是分布式单例要解决的。

---

## 三、整体架构：三层来理解

可以把方案拆成三个角色（无论用 Redis 还是 ZK 都是这套骨架）：

```
        ┌─────────────────────────────────────────┐
        │        协调中心 (裁判)                     │
        │   Redis 的一把锁  /  ZooKeeper 的目录      │
        │   —— 谁能抢到这个"标记"，谁就是 Leader     │
        └─────────────────────────────────────────┘
             ▲          ▲          ▲          ▲
             │抢锁      │抢锁      │抢锁      │抢锁
        ┌────┴───┐ ┌────┴───┐ ┌────┴───┐ ┌────┴───┐
        │ 机器A  │ │ 机器B  │ │ 机器C  │ │ 机器D  │
        │(Leader)│ │(待命)  │ │(待命)  │ │(待命)  │
        │ 干活🟢 │ │ 睡觉😴 │ │ 睡觉😴 │ │ 睡觉😴 │
        └────────┘ └────────┘ └────────┘ └────────┘
```

- **协调中心**：一个所有机器都能访问的「公共裁判」。它必须自己是可靠的（Redis 集群 / ZK 集群）。
- **抢锁 / 选主**：所有机器同时去协调中心「登记」，规则保证**只有一个能登记成功**。
- **Leader 干活 + 其他待命 + 故障切换**：登记成功的当 Leader；Leader 挂了，登记标记消失，剩下的重新抢，选出新 Leader。

## 四、三种实现方法（按原题思路逐个讲清「怎么做」）

### 方法 1：Redis `SET key value NX`（抢锁式选主）—— 本目录 Demo 采用

**核心命令一句话**：
```
SET singleton_leader 机器A的id NX EX 30
```
- `NX`：key 不存在时才写入。**多台机器同时发这条命令，Redis 单线程串行执行，只有第一条能成功**，天然保证唯一。
  - 比喻：`NX` 就像「车位空着我才停得进去」，一旦停进去（写入成功），后面来的都停不进（写入失败）。
- `EX 30`：给锁设 30 秒过期时间。**这是防止 Leader 突然宕机后锁永远不释放**（死锁）。到期自动放开，别人才能补位。

**关键数据流 / 调用链**：
1. 每台机器循环尝试 `SET NX`；
2. 成功 → 我是 Leader → 执行单例初始化 + 干活；同时**开一个后台线程定时"续命"**（给锁续期，证明我还活着）；
3. 失败 → 我是 Follower → 待命，隔一会儿再来抢（等 Leader 挂掉后的机会）；
4. Leader 宕机 → 不再续命 → 锁到期消失 → 某个 Follower 抢到 → 成为新 Leader。

**要注意的坑（analysis 必须点出）**：
- **锁的 value 要写自己的唯一 id**，释放时先判断「这把锁还是不是我的」再删，避免误删别人的锁。
- **续期（watchdog）机制**很重要：任务没干完但锁到期了会被别人抢走，导致"双主"。生产上常用 Redisson 的看门狗自动续期。
- **单点问题**：单机 Redis 挂了协调中心就没了，生产用 Redis 集群 / 哨兵；对一致性要求极高时用 Redlock 或直接换 ZK。

**适合场景**：定时任务选主、配置中心、轻量级"谁当家"控制。简单、性能好。

---

### 方法 2：ZooKeeper 临时顺序节点 + Watcher（选举式选主）

**机制一句话**：所有机器在同一个目录（如 `/singleton`）下创建**临时顺序节点**，谁的编号最小谁当 Leader；Leader 挂了它的临时节点自动消失，下一个人被 Watcher 通知后补位。

- **临时节点（Ephemeral）**：机器和 ZK 的连接断了（宕机），这个节点**自动删除**。这就是自动故障发现的关键——不用心跳轮询，掉线即消失。
  - 比喻：像「上班打卡的电子工牌」，人一走（掉线）工牌自动失效。
- **顺序节点（Sequential）**：ZK 给每个节点自动编号（0001、0002……），**天然有了排队顺序**。
- **Watcher（监听）**：每个节点只监听「排在我前面那一个」。前面的消失了，才轮到我检查是不是我最小。这样避免"惊群"（一个节点变化惊动所有节点）。

**调用链**：创建顺序临时节点 → 查自己是不是最小 → 是则当 Leader → 否则监听前一个节点 → 前节点消失被通知 → 重新判断 → 补位。

**优点**：一致性强、故障切换干净（掉线即感知），是 Dubbo 注册中心、Kafka Controller 的选主方式。**缺点**：ZK 运维比 Redis 重，写性能相对低。

**工程落地**：别手写，直接用 Curator 的 `LeaderLatch`（简单：只关心"我是不是 Leader"）或 `LeaderSelector`（可反复交接领导权）。原题代码就是这个：

```java
LeaderSelector selector = new LeaderSelector(client, "/singleton", (client2) -> {
    initSingletonService();   // 成为 leader 后的单例初始化逻辑
    // 这个方法返回即代表放弃领导权，所以里面通常要阻塞住持续干活
});
selector.autoRequeue();       // 让出后自动重新排队竞选
selector.start();
```

### 方法 3：配合消息队列做状态同步（补充手段，不是选主本身）

前两种只保证「同一时刻只有一个在干活」，但**没保证各机器的内存状态一致**。如果 Follower 也需要知道 Leader 改了什么（比如切主后新 Leader 要接着干），就让 Leader 把状态变更**广播**出去（如 RocketMQ 广播模式），各节点收到后更新本地。

- 比喻：班长（Leader）做的决定，用**班级群**（MQ 广播）通知全班，这样万一班长请假，副班长接手也知道进度。

## 五、三种方法怎么选？（决策表）

| 维度 | Redis SET NX | ZooKeeper / Curator | 说明 |
|---|---|---|---|
| 上手难度 | 简单 | 中等 | Redis 一条命令，ZK 要理解节点模型 |
| 一致性 | 一般（需续期防双主） | 强 | 强一致选 ZK |
| 故障切换 | 靠锁过期，有几十秒延迟 | 掉线即感知，快 | 对切换速度敏感选 ZK |
| 运维成本 | 低（多数系统已有 Redis） | 高 | 没有 ZK 就别为它单独引一套 |
| 典型场景 | 定时任务、轻量选主 | 注册中心、强一致选主 | — |

**新手结论**：项目里已经有 Redis、对一致性要求不极端 → 用 **Redis SET NX + 续期**（就是本目录 Demo 演示的）；要强一致、已经有 ZK → 用 **Curator LeaderLatch**。

## 六、本目录 Demo 的设计对照

为了能不依赖外部中间件就把「方法 1」讲明白，Demo 里：
- `CoordinationStore`：内存版「Redis」，提供 `setIfAbsent`（= `SET NX`）、带过期时间、`renew` 续期、`releaseIfOwner`（判断是自己的锁才删）。
- `ServerNode`：一台机器，循环抢锁；抢到就初始化 `SingletonService` 并启动续期线程干活；抢不到就待命重试。
- `main`：起 4 个节点线程并发抢 → 观察只有 1 个当选；再让当选者「宕机」（停止续期）→ 观察锁过期后另一个节点自动补位。
- 顺带一个 `broadcast` 打印，演示方法 3 的状态广播思想。

这样一个小而完整的例子，就把「选主 + 唯一性 + 故障切换 + 状态同步」四件事都点到了。
