# 滑动验证码：怎么判断"拖滑块的是人还是机器"

## 一句话题目

做一个"拖动小拼图补上缺口"的验证码，还要让写脚本的机器人过不了这一关。怎么设计？

## 为什么会有这个问题

想象你在小区门口，保安要确认你是住户还是推销员。

- 最笨的办法：问一句"你是住户吗？"——推销员也会说"是"。
- 稍微聪明点：让你按门禁密码——密码泄露了就没用。
- 真正管用的：保安看你走路的姿势、掏钥匙的熟练度，一眼认出"这人天天来"。

滑动验证码就是第三种。**光看"你有没有把滑块拖到正确位置"是拦不住机器的**——机器用图像识别算出缺口在哪，一步到位拖过去，位置比人还准。所以真正的防线不在"位置对不对"，而在"你拖的这个过程像不像人"。

先解释两个词：

- **滑块**：那块要被你拖走的小拼图。
- **缺口**：背景图上被抠掉的那个洞，滑块要正好补进去。

## 怎么做

### 第 1 步：每次生成的图都要不一样

后端出题时，缺口的横坐标 `gapX` 随机、缺口形状也随机（半圆、锯齿、不规则边）。

为什么？如果缺口永远长一个样、永远在固定几个位置，机器把模板存下来一比对就破了。**这就像门禁密码天天换，偷看一次不管用。**

还要在背景图上加**噪声点**（随机小色块）、轻微**扭曲**，滑块边缘做**模糊**。目的是让机器的"找边缘"算法不好使——人眼看着还是一眼能认出缺口在哪，机器却容易算偏。

### 第 2 步：前端不能只传"我拖到哪了"

用户按住滑块拖动的过程中，前端把每一次鼠标移动都记下来，攒成一串**轨迹点**：

```
[ {x:0,  y:0,  t:0},     ← 刚按下
  {x:5,  y:1,  t:32},    ← 32 毫秒后挪了 5 像素，手抖了 1 像素
  {x:14, y:0,  t:71},
  ...
  {x:118,y:2,  t:1240} ] ← 松手
```

`t` 是相对开始的毫秒数。提交时把**整串轨迹**连同一次性凭证一起发给后端，而不是只发一句"我到 118 了"。

### 第 3 步：后端做三层判断

| 层次 | 判断什么 | 通不过说明 |
|---|---|---|
| ① 凭证 | token 是否存在、没过期、没用过 | 重放攻击 / 超时 |
| ② 位置 | 落点和真实缺口差值是否 ≤ 容差（如 5px） | 没拼对 |
| ③ 行为 | 轨迹像不像人拖的 | 机器脚本 |

**token 是什么？** 后端出题时随手生成的一串随机字符串，好比"排队小票"。取号时给你，验证时收回，**用完即废**。存 Redis 设 5 分钟过期。没有它，机器可以把一次成功的请求录下来无限重播——这叫**重放攻击**。

第 ③ 层是重点，按原题给的三条规则判：

1. **轨迹点少于 10 个** → 机器。人拖 100 多像素怎么也得挪几十次，机器可能"啪"一下就一个点。
2. **平均速度超过 50px/100ms** → 可疑。人拖那么快手会飞出去。
3. **轨迹太平滑** → 可疑。真人会**犹豫**（中途停一下）、**抖动**（y 坐标上下差个一两像素）、**变速**（开始慢、中间快、快到位又慢下来找准）；机器往往是标准匀速直线，每一步间隔一模一样、y 恒为 0。

判"平滑"的土办法：算相邻两步的时间间隔，看它们的**波动**。人的间隔是 28、35、31、47、22……机器是 10、10、10、10。波动小到反常，就判机器。

### 第 4 步：风控兜底

同一个 IP 五分钟内失败超过 5 次，直接封一段时间或升级成短信验证。**这就像同一个人反复在门口试密码，保安该出来问话了。**

### 整体调用链

```
用户点验证框
   ↓
后端 出题：随机 gapX + token → 存 Redis(5min)
   ↓
前端 显示图，用户拖动，采集轨迹点
   ↓
前端 提交：token + 落点 + 整串轨迹
   ↓
后端 校验：token 有效？→ 位置对？→ 行为像人？
   ↓          （任一不过就失败，IP 失败数 +1）
删除 token（用完即废）→ 返回结果
```

## 一句提醒

**千万别把"正确答案 gapX"下发给前端**。见过真实事故：后端把缺口坐标塞在接口返回的 JSON 里，前端拿来画图——机器人连图都不用看，直接读接口就知道答案。**答案只能留在服务端，前端只负责采集行为、后端负责判决。**

另外，规则判定只能挡住脚本小子，挡不住模拟真人轨迹的高级机器人。大厂（极验、腾讯云滑块）在这一步换成了机器学习模型，输入同样是轨迹，输出"是真人的概率"。思路一样，只是判官更聪明。
