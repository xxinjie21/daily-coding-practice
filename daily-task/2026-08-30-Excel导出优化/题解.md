# 10. 项目上有个导出 excel 场景发现很慢，怎么优化？

## 一句话题目

页面上有个「导出 Excel」按钮，数据一多就转圈半天、甚至直接报错崩掉，怎么把它救回来。

## 为什么会慢：先看看它到底在干什么

想象你在仓库当发货员，客户说「把我这 20 万件货打包成一个大箱子寄给我」。你会经历两件苦活：

1. **把货从货架上搬下来**（数据库查询）
2. **把货一件件装进箱子封好**（生成 Excel 文件）

慢就慢在这两步，而且新手写的代码通常是最笨的做法：

- 一次 `select` 把 20 万行全捞出来，堆在院子里（应用内存）；
- 然后用 POI 把这 20 万行全摊在客厅里排好版，再一次性封箱。

> `POI` 是 Java 里读写 Excel 最常用的库（Apache POI）。它默认的 `XSSFWorkbook` 会把整张表格的每个格子都变成 Java 对象放在内存里——相当于「客厅里摊满了货」。

院子和客厅都是有限的，货一多就装不下，于是要么卡半天，要么直接 `OutOfMemoryError`（内存溢出，JVM 举手投降）。

所以优化的思路很朴素：**别一次性搬完，改成一小批一小批地搬；也别攒着再装箱，改成边搬边装边封**。

## 怎么做：四步走

### 第 1 步：查询改成「游标分页」，别用 OFFSET

很多人第一反应是分页查，一次查 1000 行，这是对的。但写法容易踩坑：

```sql
-- ❌ 越翻越慢
select * from orders where user_id = 7 order by id limit 100000, 1000;
```

`limit 100000, 1000` 的意思是「跳过前 10 万行，取 1000 行」。数据库没有「瞬移」这种能力，它得**老老实实把前 10 万行数出来再丢掉**。就像客户要第 100001 号货，你却每次都从 1 号开始数——翻到后面几乎不动了。

正确做法是**游标分页**：记住上一批最后一条的主键 ID，下一批直接从这个 ID 往后拿。

```sql
-- ✅ 每一页都一样快
select * from orders where user_id = 7 and id > 100000 order by id limit 1000;
```

> **游标（cursor）**：说白了就是「书签」。上次读到 100000 号，就把 100000 记下来，下次从书签处接着读，不用重新翻前面的页。因为 `id > 100000` 能直接走主键索引定位，数据库一步跳到位置，不再做无用的数数动作。

| 写法 | 第 1 页 | 第 100 页 | 原因 |
|---|---|---|---|
| `limit offset, size` | 快 | 很慢 | 每次都要扫描并丢弃 offset 行 |
| `where id > 上次最大id limit size` | 快 | 一样快 | 靠索引直接定位，只扫这一批 |

### 第 2 步：文件生成改成「流式写」

POI 提供了一个专门解决这个问题的类：`SXSSFWorkbook`。

> `SXSSFWorkbook` 和 `XSSFWorkbook` 的区别，就是「边封箱 vs 攒着封箱」。它内存里**只保留固定行数**（比如最近 100 行），写满就把这批刷到磁盘临时文件里，然后腾出内存装下一批。所以不管导 10 万行还是 50 万行，内存占用基本是一条平线。

```java
// 内存里只留 100 行，超出的自动落到临时文件
SXSSFWorkbook workbook = new SXSSFWorkbook(100);
```

再配合第 1 步，就能做到**查一批 → 写一批 → 丢掉这批** 的流水线：

```
数据库 --游标查1000行--> 内存(只有这1000行) --写入--> SXSSF窗口(只留100行)
   ^                                                        |
   |______________ 循环，直到查完 _______________            v 写满就刷盘
                                                        临时文件 -> 最终 .xlsx
```

全程内存恒定，这是最关键的一步。

### 第 3 步：改成异步导出 + 通知

即使快了，导 30 万行也要几十秒。让用户盯着转圈的页面等，体验很差，HTTP 连接还容易超时断掉。

做法像**快递柜取件**：用户点导出，后台立刻返回一个「任务号」，页面提示「正在生成，完成后会通知你」；后台线程池（或者丢进 RocketMQ 这样的消息队列）慢慢跑，跑完把文件传到对象存储，再发一封邮件或站内信告诉用户「你的文件好了，这是下载链接」。

> **消息队列（如 RocketMQ）**：可以理解成后厨的点菜单夹子。前台接单就把单子夹上去马上招呼下一位客人，厨师按顺序取单做菜，谁也不用等谁。

任务状态放 Redis 里（`导出任务:{taskId} -> RUNNING/SUCCESS/FAIL`），前端轮询这个状态即可。

### 第 4 步：加一层并发限流，保护自己

导出是重活。如果 20 个人同时点，20 个线程一起狂查数据库、狂写磁盘，整个系统会被自家的导出功能打垮。

所以要限制**同时最多跑几个导出任务**（比如 2 个），多出来的排队等待，实在太多就直接告诉用户「导出任务繁忙，请稍后再试」。

> Java 里最简单的实现是 `Semaphore`（信号量）——像商场试衣间只有 2 把钥匙，拿到钥匙才能进去，出来把钥匙还回去给下一个人。

## 一句提醒

**最容易忽略的坑是「分页了但用的是 OFFSET」**——写了分页却越翻越慢，还以为是数据库不行。另外，`SXSSFWorkbook` 用完一定要调 `dispose()` 清理临时文件，不然磁盘会被慢慢塞满；异步导出的文件也要设置过期清理，别让它们在服务器上越堆越多。

---

配套代码见 `code/Demo.java`，用可运行的小例子演示了上面四件事。20 万行数据的实测结果：

- **分页写法**：结果都是 20 万行，但 `OFFSET` 让数据库扫了 **2030 万行**，游标只扫了 **20 万行**——白干了约 101 倍的活。
- **文件生成**：两份文件字节数完全一致，内存峰值从 **20 万行** 降到 **100 行**（相差 2000 倍，代价是刷盘 2000 次）。
- **异步导出**：提交后 3 ms 就返回任务号，用户不用等；轮询到 `SUCCESS` 再发站内信。
- **并发限流**：8 个任务全部成功，但同时在跑的最多只有 **2 个**，其余在门口排队。
