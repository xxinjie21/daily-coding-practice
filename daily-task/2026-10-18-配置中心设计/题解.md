# 微服务配置中心设计：集中存储 + 长轮询推送 + 本地缓存兜底

## 一句话题目（大白话）

服务一多，配置散在各台机器的配置文件里，改一个参数要登几十台机器去改，还容易改漏。**配置中心**就是所有服务的「统一配置后台」：配置集中存一处，服务启动来拉，运行中改了能**马上通知到每一台服务**，而且后台挂了服务也不能跟着挂。

## 为什么会有这问题（生活比喻）

把配置中心想成**连锁饭店的中央厨房 + 对讲机**：每家门店（一台微服务）开业时从中央厨房领一份配方（启动拉全量）；营业中中央厨房改良了配方，通过对讲机喊一嗓子（长轮询推送），各家马上换新配方做菜；万一中央厨房电话占线/断线，门店就按自己贴在墙上的那份旧配方继续营业（本地缓存兜底），绝不歇业。

要解决三件事，一件都不能少：

1. **配置存哪**：集中、可靠、支持「有人改就通知」
2. **启动怎么拿**：服务启动时拉一份全量
3. **变更怎么通知**：运行中改了，实时推到所有服务

## 怎么做（核心思路 + 调用链）

整体链路就八个字：**集中存储 + 长轮询 + 本地缓存**。

```
   改配置(运营)                配置中心                    微服务实例 x N
       │  POST /publish          │                            │
       │────────────────────────▶│ ①写MySQL落库                │
       │                         │ ②换内存最新副本             │
       │                         │ ③叫醒挂着的长轮询            │
       │                         │◀───────────────────────────│ ④启动: GET /config 拉全量
       │                         │◀───────────────────────────│ ⑤GET /listen 挂住(最长30s)
       │                         │─────新配置立刻推回────────▶│ ⑥更新本地缓存+热加载
       │                     (挂了？实例用本地缓存继续跑)
```

四个关键设计，逐个说：

**① 配置存 MySQL，内存里再放一份最新副本**
存储要可靠，直接上 MySQL 真实建表持久化（`config_item(gkey, value, version)`，`gkey = 组名/配置名`）。但每次读都查库扛不住高并发，所以内存里再维护一份最新配置——这正是 Nacos「MySQL 持久化 + 内存最新副本、读写分离」的简化版。运行时改配置走「先落库、再换内存、最后推」。

**② 启动拉全量，简单直接**
服务启动时发一次 `GET /config` 把全量配置拉回来，这一步就是普通 HTTP 请求，没什么花样。

**③ 变更推送用长轮询，不用定时轮询**
定时轮询（比如每秒问一次「配置变了没」）延迟大还浪费资源。主流做法是**长轮询（long polling）**：客户端发一个请求挂住不动，服务端 hold 住最多 30 秒；这期间一旦有人改配置，服务端**立刻**把新值回给这个请求；没人改就等快超时了返回「没变」，客户端再挂下一次。相当于「电话别挂，我一有消息就告诉你」，比「你每秒打一个电话来问」省得多。Nacos 客户端就是这个套路。

代码里服务端就一个「挂着等」的核心（`Demo.java` 的 `awaitChange`）：把当前请求登记进等待队列，配置一发布就 `CompletableFuture.complete` 把它叫醒：

```java
// 客户端：GET /listen?group=gray&key=app.yml&version=1，请求会被挂住
// 服务端：hold 住这个请求，直到配置版本变化或 10 秒超时
future.get(POLL_TIMEOUT_SECONDS, TimeUnit.SECONDS);
```

**④ 灰度推送 + 本地缓存兜底**
- **灰度**：别一改配置几百个实例全炸。给配置按 `group` 分组，改动只推给灰度组（本次演示只发 `gray` 组，默认组的客户端挂在那儿完全不受影响），验证没问题再全量。生产上按 namespace / 标签分组是同一个道理。
- **兜底**：客户端本地永远存一份最新配置。配置中心宕机时请求发不出去，客户端 catch 住异常，用本地缓存继续跑——这就是「配置中心挂了服务也不雪崩」的降级。

## 一句线上提醒（易错点）

- **版本号要比对，不能只比值**：推送必须带版本号（`version+1`），客户端发现自己落后才更新，防止旧配置把新配置覆盖回去（乱序推送的经典坑）。
- **长轮询的超时要短于客户端的读超时**：服务端 hold 30s，客户端读超时设 35s，否则客户端先超时断开，白等一场。

代码演示见 `code/src/main/java/Demo.java`（MySQL 持久化 + 启动全量 + 长轮询推送 + 灰度分组 + 宕机降级，一条链路全跑到）；Spring 侧「收到变更自动刷新 Bean」由 `@RefreshScope` 完成，属框架接线，不在本演示范围。
