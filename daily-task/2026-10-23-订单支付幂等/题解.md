# 订单支付幂等：微信和支付宝同时付款，怎么保证只成功一次

## 一句话题目（大白话）

一笔订单，用户在微信和支付宝**同时**点了「确认支付」，两边几乎同一时刻通知你的系统「我付成功了」。系统要是不长脑子，两边都认，订单就被记成两笔收款——用户明明只付了一次钱（或者被扣了两次），账全乱了。本题就是问：**怎么保证一笔订单不管从哪个渠道来、来几次，最终只被记一次成功的支付。**

## 为什么会有这个问题（生活比喻）

把支付系统想成超市收银台：一张购物小票（订单），顾客排了两条队（微信队、支付宝队）同时结账。如果两个收银员各自为政，都会在小票上盖章「已结账」——货被发两份、钱被记两笔。所以收银台必须有一本**公共的结账台账**：谁先盖上「已结账」章，后面的人一看台账就知道「这单已经结过了」，把顾客劝退、钱原路退回。

先认识两个名词：

- **幂等**：同一个操作执行一次和执行一百次，结果一模一样。就像电梯按钮，按一次升一层，按一百层…还是升一层。支付回调必须做成幂等的——渠道方（微信/支付宝的服务器）网络抖动时会**重发**通知，你不能当两笔。
- **回调**：支付成功后，由渠道方的服务器反过来主动通知你的系统「用户付钱了」。注意这是「别人家的服务器」发来的消息，可能重发、延迟、乱序，全都得防。

## 怎么做：三道防线，层层兜底

原题给的三招，按「先挡后落」的顺序排好：

1. **先查状态/缓存，已支付直接返回成功**——不往后走流程。用 Redis 缓存支付结果（key 如 `pay:result:<订单号>`），像收银台门口的小黑板，命中就不翻台账。
2. **状态机条件更新**——`UPDATE t_order SET status='PAID' WHERE order_no=? AND status='WAIT_PAY'`。订单状态只允许「待支付 → 已支付」单向走，数据库保证同一行同一时刻只有一个线程能改成功，另一个线程**影响行数是 0**，说明「已经被别人处理了」。
3. **唯一索引兜底**——支付流水表建 `UNIQUE(order_no, channel)`（订单号 + 渠道），同渠道想插第二条流水，MySQL 直接报 `1062 Duplicate entry`，这是数据库层面的最后底线。

调用链长这样：

```
微信回调 ─┐
          ├→ ① Redis 查支付结果 ──命中──→ 直接返回「已支付」
支付宝回调┘        │未命中
                   ▼
        ② UPDATE ... WHERE status='待支付' ──影响 0 行──→ 返回「已支付」，拒绝
                   │影响 1 行（我是赢家）
                   ▼
        ③ INSERT 支付流水（唯一索引兜底） + 写 Redis 缓存
```

代码核心几行（完整版见 `code/src/main/java/Demo.java`，与下面的写法完全一致）：

```java
// ① 前置缓存：付过就直接返回成功，不打数据库
if (jedis.get("pay:result:" + orderNo) != null) return "已支付";
// ② 状态机条件更新：只有「待支付」能改成「已支付」
int updated = update("UPDATE t_order SET status='PAID' WHERE order_no=? AND status='WAIT_PAY'", orderNo);
if (updated == 0) return "已被处理，拒绝";
// ③ 赢家落流水；同渠道重插会被唯一索引 uk_order_channel 拦下
update("INSERT INTO t_pay_record(order_no, channel, amount) VALUES(?,?,?)", orderNo, channel, 100);
jedis.setex("pay:result:" + orderNo, 600, "PAID");
```

实测结果（`docker compose up -d` 起好 MySQL 3307 + Redis 6380 后 `mvn exec:java`，退出码 0）：

| 场景 | 结果 |
|---|---|
| 不设防，双渠道并发回调 | 两边都返回成功，订单留下 **2 条流水**（重复收款，问题暴露） |
| 三道防线，双渠道并发回调 | 只有 1 个渠道抢到状态更新，另一个被拒，订单 **1 条流水** |
| 回调重发（缓存还在） | 第一道门命中，直接返回，不打数据库 |
| 缓存失效后重发 | 状态机拦截（影响 0 行），照样拒 |
| 绕过状态检查强行补流水 | 唯一索引报 `errorCode=1062`，拒之门外 |

> 哪家渠道胜出取决于线程调度，两次实跑分别是 WX 和 ALI 赢——这正是我们要的效果：**赢家随机，但「只有一个赢家」是确定的**。

## 一句线上提醒

最稳的顺序是**「先挡（缓存/状态判断）再落（唯一索引）」**：唯一索引是数据库的最后底线，但别把它当第一道门——并发下靠抓重复键异常处理业务，逻辑很容易绕晕。另外对渠道方拒绝重复支付时，按接口约定返回成功或约定应答，否则它会一直重发通知，把回调队列打满。
