# MySQL SQL 调优：一条慢 SQL 该怎么一步步救回来

## 一句话说清

SQL 调优不是「凭感觉改语句」，而是**先量出来慢在哪 → 再看执行计划 → 再动索引**。顺序反了，改半天也白改。

## 为什么会有这个问题

把数据库想成一个**巨大的图书馆**。

- 你要找「张三 2023 年之后的所有借书记录」。
- 如果没有目录卡片（**索引**），管理员只能从第一排书架开始，一本一本翻到底 —— 这就是**全表扫描**（执行计划里 `type=ALL`）。10 万行还能忍，上亿行就是灾难。
- 如果有卡片，按「姓名 + 日期」排好，管理员直接跳到张三那一格往后翻几页就完了 —— 这就是**走索引**（`type=range` / `ref`）。

所以调优的本质，就是**想办法让数据库少翻几页**。而要知道它到底翻了多少页，就得先学会看它的「翻书报告」——慢查询日志和执行计划。

## 怎么做：五步走

演示代码在 `code/src/main/java/Demo.java`，它建了一张 10 万行的 `orders` 订单表，然后一步步把一条慢 SQL 救回来。前置条件是先起中间件：

```bash
cd code && docker compose up -d     # MySQL 127.0.0.1:3307 (root/root, 库 demo)、Redis 127.0.0.1:6380
```

### 第 1 步：开慢查询日志，先知道「慢在哪」

调优的第一步永远不是改 SQL，而是**把慢 SQL 捞出来**。线上默认只记录超过 `long_query_time`（默认 10 秒）的语句，演示时把它调成 0 好让每条都记下来：

```java
st.execute("SET GLOBAL slow_query_log = ON");
st.execute("SET GLOBAL log_output = 'TABLE'");   // 写进 mysql.slow_log 表，方便用 SQL 读
st.execute("SET GLOBAL long_query_time = 0");
st.execute("SET SESSION long_query_time = 0");   // 关键：判定用的是会话值，只设 GLOBAL 不生效
```

> ⚠️ **这是本 Demo 踩过的坑**：`long_query_time` 同时有全局和会话两个作用域，判断「这条 SQL 算不算慢」用的是**当前会话**的值。只写 `SET GLOBAL`，你自己的连接依旧是 10 秒阈值，结果一条都记不下来（第一次实跑就是这个现象）。

跑一条明显会慢的语句（`remark` 没索引，`LIKE '%...%'` 也用不上索引），再去慢日志表里读：

```sql
SELECT sql_text, query_time, rows_examined FROM mysql.slow_log
WHERE start_time > NOW() - INTERVAL 30 SECOND ORDER BY start_time DESC LIMIT 3
```

实跑结果：`SELECT COUNT(*) FROM orders WHERE remark LIKE '%remark-999%'` 耗时 24ms、**扫描行数 100000**。慢查询日志的价值就在于这个 `rows_examined` —— 它一眼告诉你「全表翻了一遍」。

### 第 2 步：EXPLAIN 看执行计划

找到慢 SQL 后，在它前面加 `EXPLAIN`，看数据库打算怎么执行。最该盯的是三个字段：

| 字段 | 看什么 |
|---|---|
| `type` | 访问方式。`ALL` = 全表扫描（最差），`index` = 扫全索引，`range` / `ref` 才是好结果 |
| `key` | 实际用了哪个索引，`null` 就是没用上 |
| `Extra` | 出现 `Using filesort`（额外排序）、`Using temporary`（用临时表）基本就有问题 |
| `rows` | 预估要扫描多少行，越小越好 |

Demo 里对同一条 SQL 做了加索引前后的对比：

```sql
SELECT * FROM orders WHERE user_id = 123 AND create_time > '2023-06-01';
CREATE INDEX idx_user_time ON orders(user_id, create_time);   -- 按查询条件建联合索引
```

实跑结果（`code/src/main/java/Demo.java` 的 `step2Explain`）：

| 场景 | type | key | rows | Extra |
|---|---|---|---|---|
| 加索引前 | `ALL` | null | 100000 | Using where |
| 加索引后 | `range` | `idx_user_time` | 57 | Using index condition |

同一个查询，预估扫描行数从 **10 万降到 57**，这就是索引的全部意义。

### 第 3 步：最左前缀原则 —— 联合索引少用左列就废了

联合索引 `(user_id, create_time)` 像一本按「姓 + 名」排序的电话簿：**先有姓，才能顺着找名**。如果你跳过 `user_id` 直接查 `create_time`，这本电话簿就完全用不上了。

实跑对比：

| 查询条件 | type | key | rows |
|---|---|---|---|
| `WHERE user_id = 123` | `ref` | `idx_user_time` | 76 |
| `WHERE create_time > '2023-06-01'` | `ALL` | null | 100000 |

第二条明明有索引却退化成全表扫描 —— 这就是最左前缀。**建联合索引时，把等值查询的列放左边。**

### 第 4 步：ORDER BY 与覆盖索引

排序也是性能大户。如果 `ORDER BY` 的字段不在索引里，数据库查完还得**额外排一次序**，`Extra` 里会出现 `Using filesort`。

实跑对比：

| 查询 | Extra |
|---|---|
| `SELECT id, amount ... ORDER BY amount` | `Using filesort`（额外排序） |
| `SELECT user_id, create_time ... ORDER BY create_time` | `Using index`（索引里就有，连排序都省了） |

第二种叫**覆盖索引**：查询要的列全在索引里，数据库只读索引就够，根本不用回表取原始数据。所以**别动不动 `SELECT *`** —— 它天然无法被覆盖。

### 第 5 步：热点数据上 Redis 缓存

索引再快，同一个热点查询被高并发反复打过来也是浪费。原题最后也提到：热点数据（如商品信息）可以放 Redis。Demo 用真实 Jedis 做了「先查缓存、未命中回源并写回」：

```java
long count = queryOrderCount(conn, 123);          // 缓存未命中 → 查库
jedis.setex(cacheKey, 60, String.valueOf(count)); // SETEX = 带 60 秒过期时间写入
String cached = jedis.get(cacheKey);              // 下次直接读缓存
```

实跑结果：第一次（回源数据库）2656μs，第二次（命中 Redis）922μs，`TTL=60s`。单次差距不算夸张，但**高并发下省掉的是成千上万次重复的解析 + 执行**，这才是缓存的价值。注意缓存本身也有坑：过期时间要合理、空值也要缓存（防穿透），否则压力又会全砸回数据库。

## 一句提醒

调优的优先级是：**先加索引（成本最低、收益最大）→ 再优化 SQL 写法 → 再考虑缓存 → 最后才轮到分库分表**。

分库分表（ShardingSphere / MyCat）是最后手段 —— 数据量真到上亿、单表优化到顶了才用。它带来的代价很大：**跨库 JOIN 和分布式事务都变成难题**，得从业务设计上绕开。索引也不是越多越好，写多读少的表索引太多会拖慢插入更新；`TEXT` 这类大字段别直接进索引，用前缀索引或单独拆表。
